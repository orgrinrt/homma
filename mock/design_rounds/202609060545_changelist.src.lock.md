# src changelist

Three files, all of them the consequence of git-shook setting
`core.hooksPath` in repositories homma also has a hand in.

## `crates/homma-engine/src/cmd/gates.rs`

CHANGE: the adoption check stops counting a `core.hooksPath` that points at
git-shook's dispatcher directory.

The check counted the setting being non-empty. That read the setting as
mockspace's because mockspace was the only thing that set it, and git-shook's
own clone, with no `mock/` and no pin, scored one surface of three and had
every commit in it refused with an instruction to run `homma agent regen`,
which has nothing to regenerate there. Measured on that clone before the fix.

The comparison is against `<git-common-dir>/shook/hooks` resolved by git,
never a spelling, since a repository is free to keep a directory called
`shook`. Where the resolution fails the path counts as before, which is the
old behaviour rather than a new hole.

Two arms. `gate_e2e_a_git_shook_hooks_path_is_not_a_mockspace_surface` fails
before the change, shown by pointing the comparison at a literal nothing
matches and watching it deny. `gate_e2e_a_hooks_path_that_is_not_git_shooks_still_counts`
is the boundary and passes on both sides of the change, which is what says the
excuse is that one directory and not a hooks path in general.

## `crates/homma-core/src/hooks/install.rs`

CHANGE: `Reach` gains `Shook`, and `reach` returns it where the hooks path is
git-shook's dispatcher directory.

`Foreign` says git will not run the entrypoint until that tool chains to the
repository's own hooks. git-shook does not chain: it runs the entries the
repository's manifests declare, and there is no state in which it starts
reaching a file in `.git/hooks`. So the message was advice about something
that will not happen, and the report now names the manifest, which is what a
reader can act on.

`Shook` is not reached, so an install under it still exits non-zero and still
writes the entrypoint. Writing it is what makes the install reversible: the
file is what git runs again the moment `git shook uninstall` clears the path.

`shook_hooks_dir` asks git for the common git directory for the same reason
`hooks_dir` does, so a linked worktree resolves to the clone's rather than its
own, which is the directory git-shook's one `core.hooksPath` names.

One arm, `git_shooks_hooks_path_is_its_own_kind_and_names_the_manifest`, shown
failing first with the comparison pointed at a path nothing sets. It carries
the lookalike case, a `shook/hooks` under a directory that is not the git
directory, which is still `Missing`.

## `shook.toml`

CHANGE: the comment says what homma does with `core.hooksPath`, which is
nothing.

It said homma takes the path to install its hooks. `hooks_dir` asks git for
the common git directory and appends `hooks/`, with a doc comment saying never
the `core.hooksPath`, and `the_hooks_dir_is_the_common_git_dir_whatever_the_hooks_path_says`
pins it. The reason to declare the hooks in a manifest is that a dispatcher
does not chain, so a manifest is the only way in where one owns the path.

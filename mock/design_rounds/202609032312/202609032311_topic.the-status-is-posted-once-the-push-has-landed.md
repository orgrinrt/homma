# the-status-is-posted-once-the-push-has-landed

## What was found

The design says a green run posts its status before the push proceeds, so a
branch never reaches the remote without its status. That sentence cannot be
true: a `pre-push` hook runs before git sends a single object, the forge has
never heard of the sha, and every post answers `422 No commit found for
SHA`. Seen on every push since the hook landed, each one leaving the line
`the status was not posted ... homma release gate --post <sha> posts it`,
and each one wanting a hand-run afterwards that nobody remembers, so the
ruleset that requires `homma/gate` on a pull request's head holds every
merge until somebody runs it.

The hook is handed one line per ref being pushed, and `pushed_tips` takes
the local sha of each. A `--follow-tags` push carries the branch and an
annotated tag on the same commit as two lines with two shas, the commit's
and the tag object's, so the same commit is gated twice and recorded twice.
Seen on the description-gate pushes: four records for one commit.

## What the design has to say instead

A green run writes its record before the push, and its status is posted
once the push has landed. The hook cannot wait for that itself, since git is
waiting on the hook, so it leaves a poster behind: a detached process that
asks the forge for the commit until the forge has it, then posts the
recorded status, and gives up after a bound, ten minutes, saying so in the
record. `homma release gate --post <sha>` stays for the case the poster
never landed. A red run refuses the push and leaves no poster, since there
is nothing for the forge to be told about.

The tips a hook is handed are peeled to commits before they are deduplicated,
so a tag and the branch it sits on are one run.

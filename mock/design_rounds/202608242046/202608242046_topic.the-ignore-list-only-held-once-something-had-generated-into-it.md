# The ignore list only held once something had generated into it

Eight generated paths are ignored, and `every_generated_path_is_ignored` asserts
it. Both are true in this working tree and neither is true in a fresh clone.

Six of the eight patterns carried a trailing slash. A `dir/` pattern in a
gitignore matches only a path that exists **as a directory**, so before anything
has generated into them git reports every one unignored. The test then fails,
and because it is a `#[test]` in a crate the whole workspace run aborts on it:
three tests run, and the other four hundred and eighty never execute.

So a fresh clone, and anything running one, sees a red suite for a reason that
has nothing to do with the code.

## The measurement

In a throwaway repository with a `.gitignore` naming `/.claude/rules/` and
`/.claude/skills`, and neither directory created:

```
.claude/rules   check-ignore exit 1   (not ignored)
.claude/skills  check-ignore exit 0   (ignored)
```

Create both, and each answers 0. One character decides it.

## What the property actually is

That these paths are ignored **whether or not they are there yet**. A repository
that has just been cloned and has not run the generator is the ordinary state,
not an edge, and the whole reason the entries exist is so that the moment the
generator writes into them nothing appears untracked.

The slashless form says that. The directory-only form says something weaker that
happens to be true whenever anybody looks.

## Why the existing test could not see it

It runs `git check-ignore` against the repository root, where the directories
are already present because the generator has run there. The condition it needs
in order to fail is precisely the condition it never runs under.

A test for this has to construct the clean state rather than observe whatever
state the tree is in, which means a temporary repository carrying the same
ignore file and none of the generated output.

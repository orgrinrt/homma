# Topic: the tools a workspace has and homma does not

## What was asked for

Op, verbatim, and this is the whole of the intent:

> One thing we'll want to do is, pipe those datas into `homma status`. And the
> suggestions for context cleanup and such. And it should also hook up with the
> agenda and show pending tasks that relate to the repos in current workspace.
> And because these tools aren't in homma, they are our own tools in clause-dev,
> the mechinery on homma's side has to be some way to attach tool outputs to the
> status, with optional formatting/post-processing on it. So something like this
> in homma.toml: ```[[status.inject]] tool = "foo", format = "some shell command
> perhaps or whatever might be most suitable here", process = "another bash
> maybe or something else not sure"``` and those would then append to the status
> printout in order of definition

The intent is the first half and the last clause: a workspace has tools that do
not live here, homma has to be able to attach their output to the status, there
is optional shaping on the way, and the blocks come out in the order the
manifest declares them. The three named consumers are the context fill, the rule
corpus cost with its cleanup suggestions, and the agenda filtered to the
repositories cloned in the current workspace.

The `[[status.inject]]` shape is his vehicle, and the two hedges in it are his
own: "or whatever might be most suitable here" on one key and "not sure" on the
other.

## Why homma is the right place at all and the tools are not

None of the three belongs here. What fills a session's context window is a fact
about a session, what the rule corpus costs is a fact about a rule corpus, and
the agenda is a tracker. Homma knowing any of them would be homma growing an
opinion about a thing that is not its own.

What homma does own is the one place somebody looks to ask where a workspace is
at, and that is the whole argument for the feature: the answer to "where is this
workspace" spans more than the manifest, and the rest of it lives in programs
the operator wrote.

## `tool`, and why it is not a shell line

`token_cmd` settled this once already and wrote the reason down: an argument
list rather than a shell string, because a shell turns a substituted placeholder
into something that can be quoted out of, and nothing there needs a pipeline.

Only the second half of that reason carries over, since nothing is substituted
into a `tool`. It carries far enough on its own. A tool entry names a program to
run, a program invocation is what an argument list is, and the manifest spelling
op wrote (`tool = "foo"`) still works because a bare string reads as a one word
list.

## `format`, and why it *is* a shell line

The opposite case, and the inconsistency is only apparent. A format is a
pipeline over text: `head -3`, `sed`, `grep -v`, `tr`. That is what a shell is
for, and expressing it as an argument list would mean the ordinary case cannot
be written at all.

## The `format` and `process` pair collapses to one

Neither op nor this round could say which of the two was which, and his own
wording says he could not either. Two keys whose difference nobody can state get
used interchangeably and then disagree about what they meant, which is a worse
outcome than one key that does less.

The options considered were: (1) keep both with a data-versus-render split, so
`process` produces what the JSON carries and `format` produces what a human
sees; (2) collapse to one transform and let homma own the title and the
indentation; (3) keep both as written and document them as equivalent.

(1) is a real design and answers a real question, which is what a tool should do
when it has structured output for a machine and prose for a person. It has no
use case behind it yet: none of the three tools op named emits structured
output, and building the two-stage pipeline on a guess is how a key nobody uses
ends up in a schema that denies unknown fields. (3) is the failure described
above with documentation on top.

So (2), and the question (1) asks stays open for whoever brings the use case.

## A failing tool is carried, not raised

`homma status` is the cheapest look anybody takes at a workspace, and it is
offline by design: no network, no git. A foreign script exiting non-zero is one
of the things worth finding out from a status, and it is not a reason to refuse
to print the forges.

So a block that could not run says so on its heading and carries the first line
the tool put on stderr, everything else prints, and the command still exits
zero. The first line rather than all of it, because a status block is not the
place for a backtrace and the operator can run the thing themselves.

## Where a tool runs, and where a relative path anchors

Both are the workspace root, and deliberately the same directory.

The config loader already has two anchors: `settle_token_commands` and
`settle_deny` both take the manifest's own directory. The root is the same thing
wherever `workspace.path` is left at `.`, which is the ordinary case, and where
it is not the two disagree about which `tools/` was meant. A tool addressed from
the root that also runs in the root cannot have that problem.

## What this does not do

There is no timeout. A tool that hangs hangs the status, which is what
`token_cmd` has always done, and adding a watchdog is a mechanism this round has
no evidence it needs.

The agenda injection op named needs a repository filter the agenda does not have
(`now`, `blocked`, `leverage`, `standing`, `open`, and nothing takes a repo).
That is work on the clause-dev side, not here.

The manifest itself cannot be wired until this lands. `Config` denies unknown
fields, so an engine without this refuses a `[status]` table outright.

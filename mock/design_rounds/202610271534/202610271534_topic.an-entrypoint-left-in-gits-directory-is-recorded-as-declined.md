# an-entrypoint-left-in-gits-directory-is-recorded-as-declined

A ninth review found that registering with git-shook deletes homma's own entrypoint from git's hooks directory, and the copy git-shook kept of it. After `git shook uninstall`, git reads that directory again and finds nothing of homma's, and uninstall has no kept copy to give back, so the hooks table, the `pre-push` release gate included, stops running until somebody runs `hook doctor` and installs again.

Git-shook now has a convention for exactly this case: a hook it leaves in place because a manifest registers what it does is recorded under `declined/<event>` as a copy, and a tool that chains to the repository's own hook, mockspace's gate, skips the file while it equals the record. Homma's entrypoint is that case, since the manifest it generates runs the same command.

So the registration stops deleting the entrypoint. Where the file in git's own directory is exactly the text homma writes it stays, and a `declined/<event>` record of that text is written beside the registry, so the chain still runs the table once. The kept copy git-shook made of the same text and its `00-existing` entry are still removed, since that entry would run the table beside the registered one. Anything else at that path stays untouched and unrecorded.

## Left as they are

A full git-shook install keeps a declined hook as an entry again when no manifest registers what it runs any more, and that holds for homma's entrypoint as for any other: the hooks table then runs through the kept entry until the next registration.

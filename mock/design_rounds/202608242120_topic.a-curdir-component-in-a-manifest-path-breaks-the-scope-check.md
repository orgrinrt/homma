# A `./` in a manifest path makes the wrapper inert again

**Date:** 2026-08-24
**Phase:** TOPIC
**Scope:** `homma` (the binary crate)

## What was measured

The previous round made the aggregated wrappers workspace-relative. Running the
rebuilt binary against this workspace and then running an emitted wrapper by
hand, with a real absolute target, the scope check does not fire:

```
REPO_REL='./homma'
REPO_ROOT=/Users/.../kamu-canon/./homma
target   =/Users/.../kamu-canon/homma/src/x.rs
          NO MATCH
```

The manifest declares `local_path = "./homma"`. That `.` survives every step:
`strip_prefix` removes the workspace prefix and leaves the rest as written, and
the wrapper joins it to `$WS` textually. The comparison against the target is
also textual, and `/ws/./homma` is not a prefix of `/ws/homma/...`.

So the wrapper reaches the same resting state the round before it fixed: it
loads, runs, matches nothing, exits 0, and no signal distinguishes that from a
guard that ran and approved. Same outcome, different cause.

## Why the round's own tests did not see it

Every one of them passes a path with no `.` component: `wrapper_script("arvo",
"arvo", ...)`, and an end-to-end fixture whose repo directory is `arvo`. The law
is asserted over the shapes that already work, which is the sampling failure
rather than a missing case.

The defect is only reachable through a manifest, and the manifests in this
workspace write `./<name>`.

## Where the normalisation belongs

At the point the relative path is produced, not in the emitted script. A `.`
component carries no information, and every consumer downstream of that point
compares textually: the wrapper's `case`, the gate's repo-table lookup, and
anything later that joins the same value. Normalising in bash would fix one
consumer and leave the rest, and would have to be written twice.

The gate has the same exposure by a different route: it reads `local_path`
straight off the manifest, so `./homma` lands in its repo table untouched.

## Correction: the manifest does not carry the `.`, the config anchoring does

Written after the fix, when its negative control passed and so proved the test
above measures nothing.

The manifest writes `local_path = "arvo"`, with no `.` anywhere. And Rust's
`Path::components` drops a `.` on its own, so `"/ws".join("./arvo")` and every
`strip_prefix` over it already render as `/ws/arvo`. There is no route by which
a manifest path puts a `.` into the emitted wrapper.

What does: `homma status` reports this workspace's resolved path as `"."`.
`Config::from_path` anchors a relative `workspace.path` on `path.parent()`, and
`Path::new("homma.toml").parent()` is `Some("")` rather than `None`, so the
`unwrap_or(".")` fallback never fires and the join leaves the path relative.
`resolve_local_path` then finds it is not absolute, says so in a comment, and
falls back to `workspace_root.join(repo_path)`, which is `"." + "/" + "arvo"`.
The `./` is that fallback's fingerprint.

So there is one defect, not two, and it is the one the previous round moved out
of scope on the grounds that nothing here depended on it. That was wrong: the
whole emitted path depends on it.

The same anchoring was found independently by a reviewer against the open
`feat/a-forge-token-can-come-from-a-command` branch, from the other consumer of
the same line. Two instances, one cause.

Both fixes land in this round, and the normalisation is kept rather than dropped
as redundant. It is not: it makes the emitted path canonical whatever produced
it, which is worth having in the one string that four textual comparisons are
made against. What it is not is the reason the wrapper was inert.

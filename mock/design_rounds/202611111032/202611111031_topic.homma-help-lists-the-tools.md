# homma-help-lists-the-tools

The workspace's tools are discoverable from homma's own help and errors. Op, 11 November 2026, verbatim: "the check is likely in homma tools and those aren't listed in homma help. But they need to be, otherwise they aren't discoverable".

## Current state

`homma --help` lists the built-in commands only. A tool is listed by `homma tools`, which nobody reads the help to find. An unknown word ends in "there is no command or tool named `check`; `homma --help` lists the commands and `homma tools` the tools", with no hint of the near miss (`checkup`).

A test of homma-core, `a_crate_publishes_with_the_token_in_its_own_environment_and_waits`, asserts the token variable is unset in the ambient environment, so it is red wherever the variable is set.

## Changes proposed

- `homma --help` and `homma help` end with a `Tools:` section, one line per tool of the workspace, name and summary, after the built-in commands. The workspace is the one `--dir` or `--config` names. Where no workspace or no tools directory is found the section is absent, a broken descriptor is listed by name as broken, and help never fails. Off unix there is no section.
- An unknown word is refused with `did you mean `homma <name>`?` when exactly one built-in command or tool name is close: a prefix of three letters or more either way, or a small edit distance. Several equally close names, or none, give no suggestion.
- The homma-core test compares the variable's value before and after the call instead of asserting it unset.

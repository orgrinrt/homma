# release-check-catalogue

The patchworks half, from the same tickets as the auth topic.

## What is there

`.shared/scripts/release/patchworks` carries a catalogue of 126 checks over jsr packages, about 100 implemented,
plus a jsr backfill publisher, a dry-run probe and a readme example type-checker. The design already says the
release check carries the catalogue's blocking set and that "the rest of the catalogue ... is reported at `warn`
and does not block, and each carries the same id it had before"; source carries the blocking set and a handful
more.

## Decisions

- Port the git-only rows, at warn, by their ids: `tree.uptodate`, `tree.stash`, `tree.worktrees`, `branch.trunk`,
  `branch.merged`, `branch.stale`, `branch.orphan`, `branch.unmerged`, `remote.pushurl`, `tag.stray`,
  `tag.bump.once`, `tag.order.matches`, `ref.filterrepo`, `hist.workflow.past`, `hist.secret.tree`, `hist.env`,
  `hist.large`, `hist.conflict`, `hist.byline`, `doc.readme.exists`, `doc.licence.file`, `doc.emdash`, and the
  sequence rows `semver.parses`, `semver.gaps.tags`, `semver.gaps.closable`, `reg.sandwiched`.
- `reg.sandwiched` reads a yanked version as published: its slot is taken. The registry layer keeps the yanked
  versions it already drops, beside the live ones.
- Not ported, into the backlog: the rows that read a built bundle or a tarball (`reg.hash`, `reg.filelist`, the
  `bld.*` set), the jsr backfill publisher and its probe, the readme example checker, `branch.pr` (a forge read),
  the deno manifest rows that judge `exports` and `include`, and the `both.*` rows beyond `both.sameset`. Each
  needs a source homma does not have yet (a bundle build, a forge pull request listing), and the jsr backfill is a
  second publish path beside `release run`.

# Src changelist: homma owns the rule and skill corpora

## homma-api

**ADD `frontmatter`**, the `---` block and the body under it. Shared, because a
rule and a skill declare different fields in the same syntax and two copies of
the fence walk would eventually disagree about where the body starts.

**`list` and `required_list` are separate calls.** Absent and empty are
different mistakes: telling an author their list is empty when they never wrote
the key sends them to look at a line that is not there. The shared helper lost
that distinction when the rule reader moved onto it, and the rule reader's own
test caught it.

**ADD `skill`**, what a skill declares about itself. `name` and `description`
are the corpus's own and both are required; the host's fields
(`allowed-tools`, `model`, `license`, `disable-model-invocation`) are taken and
round-tripped rather than refused, so a skill legitimately using one is not
blocked. Anything else is refused by name.

**The description is the field with a bound on it and the body is not**, because
the listing carries every description on every session while a body is fetched
on demand. An over-budget description is dropped by the host rather than
refused, so the skill keeps its name and loses the sentence that made it
findable.

**ADD `rule`**, the vocabulary a rule declares about itself and the reader for
it. `RuleMeta` carries `topics`, `fires`, `kind` and an optional `paths`;
`RuleKind` is `reflex` or `discipline`; `Parsed` splits a file into its meta and
its body, and splits that body at `ELABORATION_MARKER` into the card and the
elaboration.

**The reader takes `key: scalar` and `key: [a, b]` and refuses everything else
by name and line.** A YAML parser would accept nested maps, anchors, block
scalars and multi-document streams, and the generation pass can render none of
them, so each would be a file that parses and then produces something nobody
asked for. It also keeps a yaml crate out of a dependency graph that has none,
which `deny.toml` would otherwise have to carry.

**`score` matches a query term against a topic as a substring in both
directions**, so `writing` reaches `writing-style` and `readme-format` reaches
`readme`. Equality answers neither, and that is the whole failure the field
exists to prevent: a query in the question's words against a corpus written in
the answer's.

No I/O, per the crate's own rule.

## homma-org

**ADD `rules`**, the corpus. `Corpus::load` reads every `<name>.md.tmpl` under a
directory, `about` ranks by how much of a query each rule answers, `render_cards`
writes the card prefix per rule, and `render_full` puts both halves back
together for a fetch.

**Three refusals rather than skips**, each for the same reason: skipping
produces a smaller, healthier-looking corpus than the one on disk, which passes
every check and governs less than it claims. A meta that will not parse refuses
the whole load and names its file; a template naming something the meta does not
have is refused, which is what the engine's strict undefined handling buys; and
a missing directory is refused rather than read as a workspace with no rules.

**A rule's name carries no dot.** Without that guard `x.card.md.tmpl` strips to
a rule named `x.card`, which then fails to parse and refuses the corpus for a
file that was never a rule. Permanent, not migration scaffolding.

**ADD `skills`**, the skill corpus. A skill is a directory rather than a file,
so this is a walk: `.md.tmpl` is rendered and loses the suffix, everything else
is copied with its mode, and each skill's generated directory is rewritten whole
so a file dropped on the authored side does not survive on the generated one.

**A script is copied rather than templated.** Templating one would mean a shell
script could not carry a brace without escaping it, and three of the corpus's
scripts do.

**The walk reads `file_type` rather than `is_dir`, so it does not follow a
symlink.** A skill may link to a sibling repository, and following one copies
that repository into the generated tree: measured at 944 files from a single
link into `nutshell`, against the 9 that skill owns. The link is recreated as a
link, which keeps a relative one pointing where it did, since the authored and
generated trees sit at the same depth under the workspace root.

**A directory in the generated tree that no authored skill claims is reported
and left alone.** It is either a skill not moved across yet or something else
entirely, and this pass cannot tell which, so deleting what it did not write is
not its call.

**`bearing_on` takes a backticked filename or a `[[link]]`, never a bare word.**
The bare form matches prose using the same words as a rule's title, which on a
corpus this size is most of them.

**DEP `mockspace-template`**, the engine every `mock/*.md.tmpl` already renders
through. A second templating language for this would be a second language for
rule authors to know and a second one to carry the planned extensions.

## homma-engine

**ADD `cmd::rules`** and the `Rules` command with `about` and `render`.

**An empty `about` says nothing matched the topics, not that nothing governs the
subject.** The second is a claim the search cannot support: a rule may govern it
and simply not say so, and reporting otherwise sends the caller away certain.

**`about` names the skills bearing on each rule it returns**, so a session
already in the domain is told what to read next rather than having to know the
skill exists. **Derived from citations, never declared**: a `skills` field on a
rule would be a second copy of what the skill already says and would go stale
alone. The skill corpus is optional here, since a workspace may have rules and
no skills and refusing to answer what governs a subject would be the wrong
refusal.

**ADD `cmd::skills`** and the `Skills` command with `list` and `render`.

## What is not here

**No `budget` and no `size`.** The nutshell tool in the workspace holds those
and whether they are homma's is a separate question from whether the corpora
are. Moving them because the neighbouring half moved is the reasoning
`a-homeless-document-is-a-design-problem` rejects.

**No hook, and no refusal of a hand-edited generated card or skill.** Both want
a mechanism that says what generated means at the tree level, which is the next
unit rather than this one.

## Tests

**258 across the two crates**, and the refusals are most of them, which is what
a narrow reader should produce.

**The symlink test carries its negative control.** With the walk put back to
`is_dir`, it is the only test in either crate that goes red, which is what makes
it worth its length: nothing else in the suite notices a generated tree that
swallowed a repository.

One fixture defect worth recording because it invalidated a whole run: the
fixture keyed its directory on the process id, and the tests in one binary are
threads sharing one, so each test's setup deleted the others' out from under
them. Nine of eleven failed on that race rather than on anything they asserted.

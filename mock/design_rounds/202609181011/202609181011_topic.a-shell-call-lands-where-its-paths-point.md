# a-shell-call-lands-where-its-paths-point

## Where a shell call lands

The previous round's design says a shell call is narrowed by "the directory the
host says the session is in, then any path the call carries". The wrappers read
that as a fallback chain, one jq expression taking the first non-empty of the
written file, the host's `cwd` and a `cwd` inside the tool input, so a shell
call always has a `cwd` and the paths it carries are never read at all.

The case that matters is a session sitting at the workspace root and running
`cargo test --manifest-path engine/mock/Cargo.toml`, or `git -C engine commit`.
The call lands in `engine`, the `cwd` says the root, and every hook narrowed to
`engine` declines. A guard whose job is to refuse exactly that call never sees
it, and nothing reports it, since a declining wrapper exits `0` like an
approving one.

So the design means a union rather than a chain: a shell call lands wherever
its directory is and wherever any path it names points, and a hook narrowed to
a repository sees the call when any one of those is under it.

Reading a command is reading shell, and a wrapper is not a shell. What it can
do cheaply and without a false negative on the cases above:

- split the command on anything that cannot be part of a path, which takes the
  quotes, separators, redirections and the `=` in `--flag=path` or `VAR=path`
  apart;
- read each piece as a path, relative to the call's directory unless it is
  absolute, with `~/` as the home directory;
- treat a piece climbing with `..` as landing anywhere, since normalising it
  properly is work and running a guard more often than needed costs one
  process, where skipping one costs what the guard is for;
- search the whole command for a repository's absolute root as well, which
  catches an absolute path with a space in it.

What it does not see, and the design says so rather than implying it does: a
relative path with a space in it, a path spelled through a variable, and
anything a script the command runs goes on to do. A guard that needs those
reads the command itself, as the workspace's own does.

## Three more findings on the same branch

- `hook_file_named` reads the first word of a command, so a registration of
  `bash .claude/hooks/check.sh` names no hook, the hook is reported as
  registered nowhere, and it is not carried. The host runs that registration,
  so the pass should too: the file is the first word naming `.claude/hooks/`,
  what precedes it is the program that runs it, and what follows is its
  arguments. A hook run through a program does not have to be executable, and
  a hook that two registrations run through two different programs cannot be
  one wrapper, so it is reported.
- The design does not say that a hidden file under `.claude/hooks/` is skipped,
  or that a registration naming a managed file which is no longer there is
  swept. The code does both. Both belong in the design.
- `aggregate.rs` is 1264 lines, most of it the test module, and the wrapper
  text sits in two files that each carry their own copy of the narrowing.

# The shared tool configs, and blocking a commit that ships without them

Round: 202609022159
Subject: how a repo declares which shared tool configs it wants, and what
refuses a commit in a repo that is missing one.

## What was asked for

The workspace keeps one canonical copy of each tool config every repo is meant
to share. Today that is `rustfmt.toml` and `deny.toml`, under `.shared/configs/`
in the content repository. `homma agent regen` reads them, decides which repos
want each one, and places what is missing.

The ask is a gate: the commit and push path should refuse when a repo has not
shipped a config it is meant to have, and the refusal should name the command
that fixes it. The list of what to check should come from what is in the
templates directory rather than from a list written into homma, so that adding a
template is enough to block every repo that lacks it.

Two things the ask left open on purpose, and both are settled below: what the
command is called, and how a template says which repos it belongs in.

## What is already here

`homma-org` carries `configs.rs`, which is most of the enumeration. `templates`
reads the directory, `Applies` decides which repos a template belongs in,
`ensure` places what is missing and `Finding` reports. It is called from one
place, the middle stage of `agent regen`.

`homma-engine` carries `gates.rs`, which generates a workspace-level hook script
that intercepts `git commit` and `git push` from inside a member repo and
refuses when that repo's mockspace bootstrap is incomplete. It resolves which
repo the call came from, decides, and emits a refusal naming the fix.

So both halves of the ask exist and neither knows about the other. The gate
checks bootstrap and says nothing about configs; the config comparison runs only
during a regeneration nobody is obliged to run.

## Where applicability lives today, and why it has to move

`Applies::of` is a match on the file name, in Rust:

    "rustfmt.toml" => NightlyRustRepo,
    "deny.toml" | "clippy.toml" => RustRepo,
    ...

That is the list the ask says to delete. Adding a template means editing homma,
releasing it, and rebuilding, and until that happens the new template is
`Unknown` and reaches nobody. The applicability has to travel with the template.

The vehicle proposed was frontmatter: a block at the top of each template
carrying tags, stripped before the file is deployed. Tags rather than one label,
because they carry two things at once, which ecosystem the template is for and
how hard a rule it is, `rust_required` against `deno_suggested`, with a table of
giveaway artifacts saying what makes a repo Rust or deno or node.

The tag idea is right and is kept whole. The carrier is not, for three reasons.

Frontmatter needs a comment syntax and the ecosystem axis is exactly where that
runs out. `deno.json` and `tsconfig.json` are the deno and node configs this is
being built for, and JSON has no comments. A carrier that cannot express the
case it was designed for is the wrong carrier.

Frontmatter forces a strip step, and a strip is a byte transformation between
the stored file and the deployed one. The comparison this whole directory exists
for is a byte comparison. A strip that is off by one newline reports every repo
in the workspace as drifted, and the failure looks like drift rather than like a
parser.

And the directory's own README promises that each file is named exactly as it is
deployed so there is no mapping to drift. Frontmatter keeps the name and breaks
the bytes, which is the same promise broken one level down.

## The carrier that is kept instead

The tag is the directory the template sits in.

    .shared/configs/rust_required/deny.toml
    .shared/configs/rust_nightly_required/rustfmt.toml
    .shared/configs/any_suggested/some-editor-config

The stored file is byte-identical to the deployed file, so the comparison stays
a comparison and there is no strip. It works for any file type, JSON and binary
included. Adding a template stays what the ask wanted it to be, dropping a file
into a directory. And applicability is readable from `ls` without opening
anything.

Grammar: `<ecosystem>_<severity>`, several joined with `+`. Severity defaults to
`required`, so `rust/` and `rust_required/` are the same thing. A template two
ecosystems want lives in one directory naming both, `rust_required+deno_suggested/`,
rather than in two directories, because two copies of one file is the drift the
directory exists to prevent.

A file sitting loose at the top level carries no tag. It stays what it is today,
applicability unknown, reported for a person and placed nowhere. That is also
the migration path: homma can ship this before the content repository moves its
two files, and nothing changes until it does.

## Ecosystems, and whether nightly is one

Each ecosystem is a name and a giveaway, something on disk that says a repo is
one:

    any           every repo
    rust          Cargo.toml at the root or under mock/
    rust_nightly  rust, and a rust-toolchain.toml naming a nightly channel
    deno          deno.json, deno.jsonc or deno.lock
    node          package.json

`rust_nightly` was worth an argument, because it is not a different language and
it looks like it wants a second axis. It does not. The axis is not what a repo
is written in, it is which repos a template belongs in, and every entry above is
a name plus a giveaway on disk. Rust repos pinned to a nightly is exactly that
shape, with `rust-toolchain.toml` as the giveaway, so it is an ecosystem in the
only sense the mechanism uses. It also preserves what `NightlyRustRepo` does
today, which the existing tests pin: the shared `rustfmt.toml` sets options that
do not exist on stable, so a stable repo given it formats to the defaults and
warns once per option while doing so.

## Opt-outs, and why there are none

The severity axis carries how hard a rule is. It does not carry a repo saying
no, and the question was whether anything should.

One written opt-out has ever existed here. kamu gitignored its `deny.toml` with
the reason inline, that the check it configures could not run in a workspace
that is virtual with no members. It was wrong. `cargo deny check` runs in that
tree and reports advisories, bans, licenses and sources all fine. It sat there
for months describing a state the repo had already left, nothing checked it, and
it died the moment somebody ran the check by hand.

Set against that, every refusal that has turned out to be legitimate is derived
rather than written. tassu cannot take the nightly-only `rustfmt.toml`, and
nothing in tassu says so: the tag mechanism works it out from the absence of a
nightly pin, every time it runs. A derived refusal cannot rot, because it is
recomputed from the repo's own state on every run. A written one can, and the
only one we have did.

So there is no prose opt-out field. When a refusal turns up that is not
derivable, the fix is to make it derivable, a new giveaway or a new tag, both of
which are data. If it genuinely cannot be, it is a finding for a person, which
`Finding::needs_a_human` already carries and `agent regen` already prints.

This is the answer to what stops an opt-out rotting. Nothing has to, because
there is nothing written down that could.

## What blocks, and what only reports

The gate refuses on one thing: a template tagged `required`, whose ecosystem
this repo is in, that the repo does not have.

Everything else reports and lets the commit through.

A config that differs from the shared copy does not block. That position is
inherited from `configs.rs` and it now has a reason of its own: blocking would
mean the only way to commit is to overwrite the difference, which makes the gate
a worse `git checkout` over somebody's deliberate edit. It is reported, as it is
today.

A `suggested` template that is missing does not block. That is what the severity
is for.

A template whose applicability is unknown does not block. It is a fault in the
templates directory rather than in the repo, and refusing a repo's commits over
the workspace's own configuration punishes the wrong party. It is reported
loudly, where it already is, in `agent regen`.

## The gate does not place anything

Placing a config has consequences past the file existing. When `deny.toml`
landed in kamu, the pre-push gate ran `cargo deny check` across every tree
mockspace owns and refused the push, because a probe directory under
`mock/research/` violates. The placement was right and its cost landed in a
directory nobody was thinking about.

A gate that runs on every commit and writes into the tree it is inspecting hands
somebody that at the worst possible moment. So the gate reads and refuses, and
never writes. Placement is a command a person runs when they choose to, and
facing what turning the check on reveals is part of running it.

That is the split between placing a config and enforcing it, and it did not need
a mechanism. It falls out of the gate being read-only.

`agent regen` keeps placing, because a regeneration is already a deliberate act.

## Where the gate lives

In the workspace gate script that already exists, which already intercepts
`git commit` and `git push` from inside a member repo, already resolves which
repo the call came from, and already refuses with a payload naming the fix.

Three alternatives were considered and dropped.

Per-repo git hooks, through `core.hooksPath`, is what the ask literally
described. mockspace owns that path in every consumer it manages, so this would
be a second owner of one hook path. It is also worth less exactly where it is
needed most: kamu's `core.hooksPath` was unset entirely, so its per-repo hooks
were not firing at all until a regen wired them, and nothing reported that.

A mockspace lint cannot see `.shared/configs/`, which sits in the content
repository one level above any repo. mockspace is per-repo by construction. To
check a repo against the canonical bytes it would have to be handed them, which
means shipping a copy of every template into every repo, which is the drift the
single directory exists to prevent. This belongs in homma because homma is the
only thing here that spans repos.

Baking the template list into the gate script at generation time was dropped
because it fails the ask. Adding a template is supposed to block every repo that
lacks it, and a baked list keeps letting them through until somebody reruns the
generation.

So the script asks homma instead, running `homma repo config check` for the repo
the call came from, and the rule lives once in Rust rather than twice. When the
command cannot be run at all the gate refuses, which is what the same script
already does when `jq` is missing, for the reason argued there: a gate that
cannot look must not be indistinguishable from a gate that looked and found
nothing.

## The command

`homma repo config check` reads and reports, exits non-zero when something
blocks. `homma repo config init` places what is missing. Both take an optional
`--repo`, defaulting to every member, which is the shape `agent` already uses.

The name is the one the ask sketched. Two subcommands rather than one because
the gate needs a read that cannot write, and that is the whole of the split
above.

The refusal names `homma repo config init --repo <name>` exactly, and running it
places the file.

## What this leaves undone

The templates directory lives in the content repository, so moving the two files
into tag directories is a change there and not here. This round ships the
mechanism and the migration path: until the move happens, both files are
untagged, nothing is `required`, and the gate blocks nothing.

`rust-toolchain.toml` was named first in the ask and is not a template today.
Making it one is a data act once this lands, and it needs a template to be
satisfiable by more than one path, because vehje tracks only `mock/rust-toolchain.toml`
while others track the root. A template therefore declares the paths that
satisfy it and places at the first. Presence is what that gates. Sameness is
not, and a stale pin surfaces as a difference for a person, which is the same
answer as everywhere else here.

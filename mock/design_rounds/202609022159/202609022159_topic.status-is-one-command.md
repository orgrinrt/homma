# One status command, and the hook wiring nothing was reporting

Round: 202609022159
Subject: what `homma status` answers, which populations it covers, and how it
stays readable while covering them.

## What was asked for

The git hook wiring should be a reported fact, in `homma status` and in
`homma agent status`. `homma status` should print the agent status too, and
generally all of the statuses, so that a person running the plain status is not
expected to know which other verbs exist.

The last clause is a sketch rather than a specification, so what counts as all
of them is worked out below.

## The hook wiring, and why it belongs to the other subject too

kamu had `core.hooksPath` unset entirely. Every per-repo git hook mockspace
installs there was inert, for as long as that was true, and nothing anywhere
said so. It was found by hand.

`homma agent status` probes five surfaces per repo, `mock/`, `mock/agent/`,
`.claude/`, `.github/instructions/` and the `cargo mock` alias, and rolls them
up into configured, partial or not configured. Hook wiring is not among them, so
a repo with every one of those five present and no `core.hooksPath` reports as
configured, which is what kamu did while its hooks were dead.

The workspace gate already reads `core.hooksPath` and already refuses a commit
over it. So the fact was known to the thing that blocks and unknown to the thing
a person reads, which is the wrong way round: the gate tells you at the moment
you are stopped, and the status is where you would have looked first.

It matters to the config gate in the same round for a plainer reason. A gate
that lives in a hook is worth nothing in a repo whose hooks are not installed,
so the hook wiring is the precondition for every per-repo gate here, and a
precondition nothing reports is a gate that can be silently absent.

So `Surfaces` gains the probe, `roll_up` counts it, and a repo missing it is
partial rather than configured.

## What all of the statuses means

homma can already report five populations, in four verbs: the workspace and its
forges, per-repo git worktree state, the agent surfaces, the doc surfaces, and,
after the other subject in this round, the shared tool configs.

Concatenating all five into `homma status` is the literal reading and it is the
wrong one. Five populations across thirty members is a wall of output, and a
status nobody reads is worse than one verb nobody knew about.

The principle taken instead comes from what the command is for. `homma status`
answers what state this workspace is in, and the useful answer to that is what
is wrong, not an inventory of what is fine. So:

`homma status` covers every population and reports, by default, only what is
not in its expected state. A repo where everything is as it should be
contributes one line saying so. The narrower verbs keep printing everything
about their own population, fine and not fine alike, and that is what they are
for.

`--full` prints every population in full, which is the concatenation the ask
sketched, for when that is what somebody wants.

This scales the right way. Thirty healthy members is thirty lines. Thirty broken
ones is thirty blocks, which is what you need to see precisely when you need to
see it.

## What is in, and what is left to the narrower verbs

In, because each can be wrong in a way that stops work:

  workspace and forges   already there, and the header of the command
  agent surfaces         including the hook wiring, per above
  shared tool configs    what is missing that this repo is meant to have
  git worktree           dirty or clean, and which branch

Left out, deliberately: the doc surfaces. `homma docs status` reports which of
`README.md`, `docs/` and the design templates each repo has, and a repo missing
one is not in a state that stops anything. It is a survey rather than a fault,
so it stays where surveys live and `--full` does not pull it in either. If that
turns out wrong it is one field.

Also left out: anything that costs a network round trip. `homma status` is
offline today and stays offline, which is what makes it the command you run
first. `homma verify --forge` is where the round trip lives and it is opt-in
there for the same reason.

## The JSON document

`--output json` is contracted as one document per command, and folding
populations together changes the shape of the one `homma status` emits.

Two decisions, both narrow.

The document grows fields rather than being restructured. `workspace`, `forges`,
`repos` and `injected` keep their names and their shapes, and the new
populations arrive beside them under new keys. Anything reading the document
today keeps working and simply does not look at the new fields.

And JSON is never summarised. The exceptions-first shape above is a property of
the human rendering, because it exists so a person is not made to read past
what is fine. A machine has no such problem and a machine reading a document
that silently omits the healthy members would be reading a lie about the
population. So JSON emits every population in full, whatever `--full` says, and
`--full` is documented as affecting the human output only.

## What this does not do

It does not change what any narrower verb prints. `homma agent status` gains the
hook wiring, which is the ask, and is otherwise untouched, and `homma repo
status` and `homma docs status` are untouched entirely.

It does not merge the verbs away. The ask is that a person need not know they
exist, not that they stop existing, and the narrow verb is still the right thing
to run when the question is narrow.

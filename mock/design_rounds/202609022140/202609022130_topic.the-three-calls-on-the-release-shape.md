## Where the badge json lives

Asked between an orphan `badges` branch per repo, a file on `main` committed by the release, and a json per repo in the workspace content repo:

> Probably just orphan refs yeah, makes sense. Similar pattern is used for the mockspace v2 design (not yet implemented or finished design though), so that is already going to be a part of the per-repo workflows. As I understand, the orphan branches don't get pulled into any clones in any usual git calls, right? So it's only a burden on the remote host itself, which is fine, it's all just text files

Settled: an orphan branch named `badges` in each repo, holding only the json, one file per measured thing, rewritten by every release and never merged. The readme's badge url is the shields endpoint badge pointing at the raw file on that branch.

On his question, answered in the session: a clone's default refspec fetches every `refs/heads/*`, so the branch's objects do arrive in every clone, a few kilobytes and never checked out. A ref outside `refs/heads/`, the `refs/mock/*` shape mockspace v2 designs for, would stay out of clones, but raw.githubusercontent.com resolves only branches, tags and shas, so a badge url needs a branch. That cost is accepted.

## How the version bump is decided

Asked between reading the level off the conventional prefixes since the last tag with a `--level` override, always asking with no inference, and patch by default with a flag for more:

> Always ask, no inference

Settled: `homma release run <repo> --level <patch|minor|major>` is required, and a run without it refuses. The plan step still prints the commits since the last tag with their prefixes, so the person choosing sees what the commits say, and the tool never chooses.

## The changelog

Asked whether a changelog also lives in the repo as a file, between the GitHub release body only, both with a `CHANGELOG.md` on `main`, and a file only where one already exists:

> Hmm. We could and should perhaps keep a CHANGELOG.md file, that's just convenient. However, I wonder how long we should keep it? What's the standard play there? Because would seem a bit too much if we keep everything, or is that the common practice?

Told that the common practice, keepachangelog.com and the large crates alike, is to keep every release newest first and that trimming to the releases page is the exception, and asked between keeping everything, keeping the current major with a link for the rest, and keeping the last ten:

> Keep everything (Recommended)

Settled: `CHANGELOG.md` on `main` in every released repo, newest first, one block per release, generated from the commits between the two tags and grouped by prefix, never trimmed. The same block is the GitHub release body. The release merge carries the new block, so the file is part of what the tag points at.

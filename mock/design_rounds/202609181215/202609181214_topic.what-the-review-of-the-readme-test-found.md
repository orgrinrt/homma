# what-the-review-of-the-readme-test-found

The previous round split checking the readme between the two binaries: the
engine's suite drops every span naming a command the launcher answers, and the
launcher's suite checks the launcher's rows. The review of that branch found the
handoff does not close, in three places, and one sentence of the design that the
round left stale.

## The `config` row is dropped by one half and checked by neither

The engine now drops `homma config` spans, since `renki` answers that word before
the engine runs. The launcher's half only asserts a row for `config` exists. The
row names five verbs, `path`, `schema`, `get`, `set` and `edit`, and the prose
further down names `homma config schema`, and nothing checks any of them. Before
the split those spans went red; after it they are unchecked, and a verb renamed
in renki leaves the readme stale with the suite green.

The launcher's suite has the binary, so it can ask it. `homma config` with no
verb is refused with a message listing the verbs it takes, which is the live set
rather than a copy of it, and each verb can be run against a settings directory
the test owns: `path`, `schema` and `get <key>` read, `set` writes into that
directory, and `edit` runs whatever `VISUAL` names, which a test can make `true`.

## The two halves read different sets of spans

The engine reads every `homma ...` span: table cells, prose, and the bare lines
of a shell fence. The launcher reads the table row. A `homma workspace frob`
written in prose or in the usage block would be dropped by the engine and never
seen by the launcher.

So the engine's half asserts that every span it drops is one the launcher's row
for that command already names: the span's first word after the command is the
first word of a form in the row, or the span has no word after the command. The
launcher then checks every form in the row. Together that is every dropped span,
checked once, by the binary that answers it.

## The third check restates the filter

`the_launchers_commands_are_not_the_engines` ends by computing the spans the
filter dropped and asserting each names a launcher command. The parser always
makes the second word of a span its first path word, so that asserts the filter's
own condition back at it. The check above replaces it.

## Smaller

`row_for` matches on a prefix with no boundary, so `row_for("work")` finds the
`workspace` row. The name wants a space or a backtick after it.

The word `config` and renki's condition for answering it are written in both
test files, each under a `FIXME:`. The fix is upstream, in renki exporting
`config::query::SUBCOMMAND` and `is_the_config_query`; an agenda row names it so
the two markers have somewhere to point.

`mock/Cargo.lock` moved `tempfile` from `getrandom 0.3.4` to `0.4.3` in the
merge from `dev`, a re-resolution the round did not ask for. It is stated in the
source changelist rather than dropped, since reverting a lockfile entry by hand is
selecting one side of a resolution.

## The design says one command and there are two

`mock/DESIGN.md.tmpl` opens the paragraph on `homma workspace` with "One command
is the launcher's rather than the engine's". `homma config` is answered before
the engine too, by renki for any tool carrying settings, and the design already
says a paragraph later that `homma config` reads and writes the settings file. The
sentence wants to say two, and say why the second is the launcher's.

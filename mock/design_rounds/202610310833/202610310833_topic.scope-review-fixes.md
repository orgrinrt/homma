# Scope review fixes

Follows the round `202610310822`, whose branch review found five blockers. This round records the decisions they need.

## What the review found, and what is settled

A clone outside the scope is not a member, and its git hooks still run. The installed entrypoint is `homma hook run <event>`, run with the clone as the working directory, and it found its clone through `cfg.repos`, which the scope now narrows. The hook run finds the clone through git when the manifest does not list it (`util::clone_of`), and the commit and push gates keep the property the design already states: they have no reason to refuse over the scope.

A hook row narrowed to a repository outside the scope is skipped without a word in `agent regen`. The work is not this clone's, and the old message said the workspace had no such repository, which is false.

Naming a clone outside the scope on a command line says that it is outside the scope, and not that it is not a repository.

The earlier tests of `homma what` and the stray-build walk compared the rows returned, which a command that does all the work and then filters passes too. Each now records what it touched (`repos_probing`, `collect_visiting`), with the unscoped run beside it as the control.

The earlier design sentence claimed no command touches an out-of-scope repository. That is a claim over every command and it is false: the launcher's workspace survey (`launcher/src/workspace/status.rs`) runs `git status` and reads HEAD in every clone, and the stray-build walk lists the `.worktrees` directories of every repository, since a worktree is not a top-level clone. The sentence is narrowed to what the scope guards, and those two are named as not scoped. Whether the survey and the reap should be scoped is not settled here: they arguably need to see everything so that nothing is removed unseen, and the call is op's.

The README row for `homma local` now says that `repos` limits the commands and that `status` names a scoped repository that is not cloned.

## Open

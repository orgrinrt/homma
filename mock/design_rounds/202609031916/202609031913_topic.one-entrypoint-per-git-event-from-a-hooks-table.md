# one-entrypoint-per-git-event-from-a-hooks-table

## What was found

The docs first. `homma-core/DEEPDIVE_release.md.tmpl`, section "The hook",
says `homma release hook install <repo>` writes one fixed `pre-push` hook that
calls `homma release gate --hook`, and refuses in three cases: a
`core.hooksPath` outside the repository, which it names as the mockspace case
and says is gated at release time only "until mockspace's pre-push delegates
to homma"; a hooks directory the repository tracks; and a foreign `pre-push`
already there. The root `mock/DESIGN.md.tmpl`, in the paragraph after "That
path is the gate", says the config check lives in a workspace-level hook
rather than a per-repository git hook "because mockspace owns `core.hooksPath`
in every repository it manages, and a second owner of one hook path is a
fight neither wins". Both are true of the tree as it stands and both rest on
mockspace not chaining, which has moved: mockspace's durable gate and its
generated per-repository hooks now run the repository's own
`.git/hooks/<event>` after their own checks, with the same arguments and, for
`pre-push`, the same refs on stdin (mockspace #118). So `.git/hooks/<event>`
is reached in every managed repository, and the two refusals that rested on
it not being reached are refusing the one place the chain goes.

The source, read after the docs. `homma-core/src/release/hook.rs` holds the
script as a constant, `install` with the three refusals, and `is_installed`.
`homma-engine/src/cmd/release/gating.rs` reads the pushed refs off stdin under
`--hook` and gates every distinct local sha. `homma-core/src/repo/hooks.rs`
answers whether `core.hooksPath` is set at all, which `homma status` reports
as the hooks being wired. `homma-core/src/config.rs` carries `[markers]` as
`homma_api::Markers`, the precedent for a table with defaults every workspace
has without writing them and rows a workspace adds. Nothing reads a
`[hooks]` table, nothing installs a `pre-commit`, and the prose gate the
voice tool wants, `vibecheck check` over the staged prose, has no way in.

## What op ruled

From `.data/op-responses/202609031319_hooks-through-homma-and-integrate-scoring.md`:

> So, uh, those hooks. Homma already installs hooks, so, all the hooks should smartly get consolidated into one hook script. Or be sourced and ran from one entrypoint hook script. Does homma already have a thing for this, or? Homma.toml could contain hooks.pre-commit field for example that takes path globs as array?

> o wait, mockspace can't delegate to homma, because mockspace can't know about any homma. All things are isolated. So it has to be homma that integrates with mockspace, detects if mockspaces exist, and then call their hooks natively

Asked which tool-agnostic extension point mockspace should offer, among
[chain to `.git/hooks/<event>`; a generic `[hooks]` list in `mockspace.toml`;
homma owning `core.hooksPath`], he chose the first with no free text.

The intent, in his words: one entrypoint script per git event, installed by
homma, configured in `homma.toml`, with path globs per entry. The vehicle he
sketched, `hooks.pre-commit` taking an array of globs, is the shape below with
one addition he did not spell out: each entry also names what to run, since a
glob alone says when and not what.

## What this round does

A `[hooks]` table in `homma.toml`, one array of entries per git event, each
entry a command and the globs that decide whether it runs:

```toml
[[hooks.pre-commit]]
run = ".shared/scripts/voice/vibecheck check {paths}"
paths = ["**/*.md"]

[[hooks.pre-push]]
run = "homma release gate --hook"
```

The release gate is the row every workspace has without writing it, on
`pre-push`, first, the way `Cargo.toml` is a marker without a `[markers]`
table. Declared entries follow it in the order written. An entry without
`paths` runs on every invocation; one with `paths` runs when at least one path
the event touches matches a glob, and `{paths}` in `run` expands to those
matching paths, quoted, so a checker that takes files gets exactly the files
that made it run. The event names are git's own and a name git has no hook
for is refused when the manifest loads, naming the row, as a bad marker
signal is.

`homma hook install <repo>` writes one entrypoint per event that has entries,
into the repository's git directory's `hooks/` and nowhere else: `exec homma
hook run <event> "$@"`, a few lines that never drift from the binary. It
refuses a tracked hooks directory and a foreign hook exactly as the old
install did. It no longer refuses a `core.hooksPath` outside the repository,
because the chain reaches `.git/hooks/` under one; what it does instead is
say how git will reach the entrypoint, directly where the path is unset, by
mockspace's chain where the path is mockspace's, and not at all where the
path is some other tool's, which is a line and a non-zero exit like the other
refusals so a sweep goes on.

`homma hook run <event> [args...]` is what the entrypoint calls: it captures
stdin once, works out what the event touches, the staged paths for
`pre-commit` and `commit-msg`, the union of what every pushed ref adds over
its remote for `pre-push` with a new branch or an unknown remote widening to
everything the tip carries, selects the entries whose globs match, and runs
them in order through `sh -c` with git's own arguments appended and stdin
replayed, stopping at the first non-zero and exiting with it. Each entry gets
one line naming it and how it went. No entries for the event is a pass that
says so.

`homma release hook install` goes, with `HookError::HooksPathOutside`; the
deep dive's "The hook" section becomes "Hooks" and says the above, and the
root design's paragraph about not owning a per-repository hook says what is
true now, that the entrypoint lives in git's own directory and mockspace
chains to it. `homma status` keeps reporting whether `core.hooksPath` is set,
which is still the difference between mockspace's gate running and not, and
gains nothing this round; whether homma's own entrypoints are installed is
`homma hook install`'s to say.

## What was weighed and not taken

A single entrypoint reading the table itself, in shell, so no binary is
needed at hook time: rejected, since the release gate already needs the
binary and a shell copy of the glob logic is the drift the gate script was
written to avoid.

The gate posting its status after the push lands, which the pre-push shape
cannot do and which fails with a 422 today: out of this round, its own row in
the agenda, since it is about when the gate posts and not about how hooks are
wired.

A `[hooks]` table that replaces the default rather than extending it: rejected,
since a workspace that forgot the gate row would push ungated and nothing
would say so. The gate is not a row anyone can drop by omission.

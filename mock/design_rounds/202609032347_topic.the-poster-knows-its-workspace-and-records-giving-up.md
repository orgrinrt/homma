# the-poster-knows-its-workspace-and-records-giving-up

## What was found

The review of the poster round `202609032312` found that the poster does
not work in the deployment it was written for, and six smaller things
around it.

The poster is this binary again with `release gate <repo> --post <sha>
--await` and nothing else. It inherits the hook's working directory, the
member repository's root, and the launcher's `--dir` is not inherited, so
the poster looks for `homma.toml` beside a member clone, finds nothing, and
dies on its first line. Its streams are null, so nothing says so: the hook
prints that a poster will post the status, and the status is never posted,
which is the symptom the round was opened to remove. Reproduced with the
built engine from a member root, and again with `--dir`, which posts.

The topic says the poster gives up after ten minutes saying so in the
record. The design paragraph derived from it says only "saying so", and
the code says so on stdout, which for a poster is `/dev/null`. The tiers
drifted between DOC and IMPL and nothing recorded the weaker sentence.

`leave_poster` has no test, and the source changelist's verification for it
was a `grep -c` on the function's name, which counts that a function exists
and says nothing about whether it works. The one test of `poster_args`
compares its literal output to the literal it was written to return.

The trait doc and the design say the read is `GET
/repos/{owner}/{name}/commits/{sha}` on both forges. Forgejo's is
`/git/commits/{sha}`, which the code has right; measured against the live
hosts, GitHub answers 422 for a sha it has not received and Forgejo 404.

Both clients fold 404 into "the commit is unknown". On GitHub a 404 from
that endpoint is the repository, absent or invisible to the token; on
Forgejo it is either. A wrong owner, a rename or an expired token therefore
produces a poster that asks for ten minutes and then reports the commit
unknown.

The poster for the first tip is left inside the loop, before the second tip
is gated, so a `--follow-tags` push with a red second tip is refused and a
poster asks after a commit that will never land.

`AWAIT / PAUSE` gives 120 tries with the pause skipped after the last, so
the bound is 595 seconds against the ten minutes every document names, and
no test pins the two together.

## What changes

The poster is handed the resolved config path, `--config <absolute path>`,
rather than `--dir`, because the store the run was recorded in is derived
from the config path too and the poster has to read the store the hook
wrote. The argv is parsed back through the CLI in a test, asserting the
subcommand, the repository, the sha, the await and the config it names.

A poster that gives up appends a `poster-gave-up` record to the store
beside the runs, with the repository, the sha, when it gave up and how long
it waited. That is what "saying so in the record" means, and the design
says it in those words.

The design and the trait doc name both paths, and say a 404 that is the
repository rather than the commit ends the wait as an error. GitHub's 404
is that error outright; Forgejo's 404 is read as the commit unknown when
the repository answers and as the error when it does not.

Posters are left after every tip has been gated, and only when every tip
is green.

The wait pauses after every miss, so ten minutes of asking is ten minutes,
and a test holds the try count and the pause to the bound.

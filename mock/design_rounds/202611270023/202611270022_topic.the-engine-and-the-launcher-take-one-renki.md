# The engine and the launcher take one renki

## The ask

homma is two builds that each link renki: the launcher for the pin, the cache and the handover, and the engine for the host half of the extension api the tools run on. They take two renkis. The launcher takes renki and renki-config from renki's git at one revision, because the fix it needs, a moved branch pin building that pin's own engine, is not in a published release. The engine takes the published renki 0.0.3 and renki-dirs 0.0.1. So a machine that builds homma builds and keeps two renkis, the tools read their cache root through a renki-dirs older than the one the launcher resolved it with, and a fix to renki reaches one half and not the other.

## Taken

The engine takes the launcher's renki: the same source and revision for renki and renki-dirs, so one renki is resolved for both and both move together. While that source is git, the engine may take it, since the engine is not published; the launcher's own move back to a published renki, which its publishing test waits on, moves the engine with it.

The renki-dirs of that revision renames the trait of a directory's kind, whose constants the engine reads the cache root's variables through, from `Kind` to `DirKind`. The engine names the new one; nothing else of renki or renki-dirs that the engine uses has changed between the two, and renki's extension api only gained items.

Options weighed:
- The launcher back to a published renki now: the published release lacks the fix the launcher took the git revision for, so a moved pin would build a stale engine again.
- The engine on the newest published renki and the launcher on git: still two renkis, only nearer each other.
- One renki, at the launcher's revision (taken).

## What the design says

The tools section says the engine reaches renki through its extension api. It gains that the engine and the launcher take one renki, at one source and revision, and move together.

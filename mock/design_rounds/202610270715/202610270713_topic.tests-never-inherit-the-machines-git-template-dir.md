# tests-never-inherit-the-machines-git-template-dir

`hook_install_writes_one_entrypoint_per_event_and_says_how_git_reaches_them` in `homma-engine`'s `cli_release` fails on `dev` at `tests/cli_release.rs:168`, asserting "no entries, no entrypoint": a `commit-msg` file exists in the hooks directory of a repository whose table names no `commit-msg` entry.

Which side is wrong. Neither the code nor the test's intent. `homma_core::hooks::install` writes one entrypoint per key of `Hooks::events()`, the gate's `pre-push` and what the manifest declared, and the unit test in `crates/homma-core/src/hooks/install.rs` asserts `commit-msg` absent. The file is not homma's. The machine's git config sets `init.templateDir`, here to a directory holding a `commit-msg` hook (the byline guard the bootstrap installs), and `git init` copies every template into a new repository, so the test repository starts with somebody else's hook. Measured: a bare `git init` in an empty directory on this container lists `commit-msg` under `.git/hooks` before homma runs anything. The design is silent on the git environment the tests run in, as it was for the identity variables in round 202610231252. The test's intent, that an event with no entries gets no entrypoint, is the claim kept, and it is checkable only on a repository that begins with no hooks.

The class is wider than the one test. Every test that makes a repository with `git init` or `git clone` copies the template directory, and a template hook that refuses (a byline check, a lint) refuses the commits those tests make. One live case under the real guard is `crates/homma-core/tests/membership_is_detected.rs`, which carries its own copy of `clone_at` with a bare `git init -q`. A flag at each `git init` site leaves every site written later exposed again.

There are two ways a machine names a template directory: the `init.templateDir` key in a configuration file, and the `GIT_TEMPLATE_DIR` variable, which outranks the key. The answer has to hold against both.

The answer: the test environment is pinned in one place. Cargo's `[env]` table in a `.cargo/config.toml` at the repository root reaches every test process and every `git` they spawn, whether `cargo mock test` runs from the root or a member runs from its own directory. It sets `GIT_TEMPLATE_DIR` to the empty value, which outranks `init.templateDir` (measured against the real config here: `git init` then creates no hooks directory), and it sets it with `force = true`, because without that cargo leaves a variable the machine already exports as it is, and the pin would lose on exactly the machines that name their template directory that way. A test commits the class: it builds a template directory whose hooks fail, points a global configuration at it, and has a repository made by `git init` and another by `git clone`, and committed in the way every test does, inheriting the process environment; it fails without the pin and passes with it. Run with the variable exported to the guard's real directory, it is the check that the force holds.

The pin reaches only what cargo starts. An installed `homma` is unaffected, which is the point: the production verb keeps using the user's template directory. A `cargo run` of the launcher inside this checkout is cargo-started, so it clones without the user's templates; that is acceptable for development and is named here so it is not a surprise.

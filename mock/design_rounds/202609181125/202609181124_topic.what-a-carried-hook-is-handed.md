# what-a-carried-hook-is-handed

A review of the round that made a shell call land on every path its command
names found that the headline case still does not reach a guard in practice.
`git -C engine commit` typed at the workspace root now reaches `engine`'s
wrapper, and the wrapper `exec`s the hook, but every hook mockspace generates
runs its own scope check first, `_scope_or_allow` in
`.claude/hooks/mockspace-write-guard.sh`, and that check reads `pwd` and looks
for the repository's absolute root in the command. A call typed at the workspace
root with a relative path satisfies neither, so the guard allows it. Reproduced
by the reviewer: `cp a mock/design_rounds/x/foo.md` is denied from `homma/`,
and the same call spelled `homma/mock/...` from the root is allowed.

## Which half is homma's

The design says where a call lands and that the wrapper hands off to the hook.
It is silent on what the hook is handed and where it runs, and that silence is
where the misunderstanding lives.

A wrapper could run the hook from the repository's root instead of where the
session is. That would satisfy a guard that asks `pwd`, and it would break every
guard that reads a relative path out of the payload, because the path is
relative to the session's directory and the hook would resolve it against a
different one. `cp a mock/x` typed in `homma/` would be read as
`homma/mock/x` either way, but `cp a homma/mock/x` typed at the root would be
read as `homma/homma/mock/x`. So the hook runs where the session is, and is
handed the payload exactly as the host sent it. That is what the source already
does; the design says it now, with the reason.

What follows for a hook: its own scope check has to read the payload's `.cwd`
and the paths in the command the way `LANDS_IN_SH` does, rather than asking
`pwd`. That is mockspace's change, to the guards it generates, and it goes to
mockspace as its own work. homma reaching the guard is necessary for it and not
sufficient, and the commit that claimed otherwise said more than it had.

## The rest of the review, in this round

- A test that runs a `case` the test wrote itself and no homma code, which
  checks bash rather than the wrapper. It goes.
- A runner is put into `exec` as written, so `FOO=1 .claude/hooks/x.sh` becomes
  `exec FOO=1 ...`, which exits 127, and `cd "$D" && .claude/hooks/x.sh`
  becomes `exec cd ...`, which on macOS runs `/usr/bin/cd` and exits 0, reading
  as an approval. A runner carrying shell syntax, an assignment or a separator,
  is refused by path the way two runners for one hook are, since the wrapper can
  run a program with arguments and cannot run a shell line.
- An over-fire is not only a process. For a hook that observes, it is; for a
  hook that denies, a bare word equal to a repository's path, `echo engine`, is
  a call landing there, and a guard that denies on it denies a call that did not
  touch the repository. The design says so rather than calling it free.
- A file path carrying `..` is compared as written, so `/ws/other/../engine/x`
  misses `engine`. A file path that climbs lands everywhere, as a command's
  piece already does.

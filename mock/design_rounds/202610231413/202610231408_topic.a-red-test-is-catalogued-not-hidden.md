# a-red-test-is-catalogued-not-hidden

The round `202610231252` made `provisioned_commit` pass on a container exporting
`GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL` by removing those four
variables from the `git` the test spawns. The review of that change found the
removal hides a defect. Without it, `a_commit_in_a_provisioned_workspace_carries_the_registrys_two_identities`
fails at its author-name assertion with the left side `O. R. Toimela` and the right
side `Onni Armas`: a workspace that `provision` stood up committed as the
machine's identity and not the registry's.

That is the failure `crates/homma-org/DESIGN.md.tmpl` names, "the first sign is a
commit landing under whoever the machine's global configuration names", and the
six configuration keys it adds close the machine's configuration files and not
its environment. The round topic's sentence "Nothing in the code under test is
wrong" is therefore not what the design supports, and it is rewritten in
`202610231252_topic.tests-pin-their-own-git-setup.md` to say what the design leaves open.

The decision recorded here is about the test. A test is not made to pass by
removing the input that breaks it. `provisioned_commit` now sets the four
variables and a `GIT_CONFIG_COUNT` entry to hostile values, as `hostile_config`
does for the configuration files, so that it fails on every machine and not only
on the ones that export them. It is marked a catalogued red, `#[ignore]` with a
reason and a `FIXME`, which is how the rest of this repository marks a case the
design has not yet settled, and the assertions keep stating the intended
behaviour. What the code should do is the other open topic,
`202610231408_topic.how-a-provisioned-workspace-defends-its-identity-against-the-environment.md`.

The four variable names were written three times, in `git_impl.rs`,
`provisioned_commit.rs` and `support/mod.rs`. They are one list in
`homma_core::testing` now, with the helpers that remove them and that set them to
hostile values.

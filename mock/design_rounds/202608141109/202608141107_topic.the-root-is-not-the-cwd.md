# The root is not the current directory, and origin is not the content repo

**Phase:** TOPIC
**Scope:** `homma-api`, `homma-core`, `homma-org`, `homma`

A second review found that standing an identity up clones whatever repository the
operator happens to be standing in. Reproduced before acting:

```
$ cd <an unrelated member clone>
$ homma --config <root>/homma.toml org up paja
paja ./.shared/hands/paja
exit=0
$ git -C <ws>/paja remote get-url origin
.../member          <- the wrong repository
$ ls <member clone>/.shared/hands/paja
exists              <- and it wrote into somebody else's tree
```

Two independent defects, and the second is worse than the report says. The
workspace root defaults to the current directory and ignores `--config`, so the
origin read is of an arbitrary repository. And because the root is also where the
directories and definitions are written, standing up from inside another Hand's
workspace writes into it, which deny item 2 forbids outright.

## The reasoning that produced it was false, and that is the part worth keeping

The previous round derived the clone URL from the root's `origin` and justified it
like this: a configuration key for the URL would be "a second place for one fact
to live and therefore a second place for it to be wrong".

**`content_repo` already existed and is required.** So there was never one place
for the fact; there were two, and the round added a third derivation that consults
neither. The justification was not merely weak, it asserted the opposite of what
was true, and it read well enough to survive being written down in a design
document.

**The lesson is narrow and worth stating.** An argument for not adding a second
source of truth is only sound after checking whether the first one exists. That
check is a grep.

## What the round does

**The root is the configuration file's own directory.** That is the workspace
homma was invoked for, it is what `--config` already names, and it makes the
current directory irrelevant. An explicit `--root` still overrides, because
standing a workspace up somewhere else on purpose is a real thing to do.

**The origin is verified against `content_repo` rather than trusted.** Both facts
exist, so the honest move is to use both and refuse when they disagree, naming
both values. A root whose origin does not name the content repository is not the
workspace this configuration describes, and cloning from it is the defect above.

**An existing workspace has its remote checked before it is skipped.** Standing up
twice is the same answer only when the thing already there is the right thing. A
workspace cloned from the wrong repository is currently permanent: re-running
reports "already there" and exits 0.

**The identity is read back after it is written.** The crate's design document
claims "after standing up, that clone reports the identity's own email", and
nothing read it: `Git::identity` had no caller outside its own tests, while its
doc comment said it existed "so setting it can be asserted rather than assumed".
That is the previous round's defect, recurring inside the round convened to fix
it, in the same sentence.

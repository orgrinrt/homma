# Topic: one anchor for a relative deny entry

**Date:** 2026-08-25

A relative `deny` entry resolves against a different directory depending on
which command reads it.

The documented anchor is the directory the manifest sits in, which is the same
one `local_path` uses, and two of the three call sites pass it. The
aggregation passes the workspace root instead. Those are the same directory in
the ordinary arrangement and stop being the same the moment `workspace.path`
points somewhere else, which is a thing the manifest allows and which the
regen tests already construct.

So `deny = ["scratch"]` means one directory to `org add` and another to
`agent regen`, and nothing says so. An operator would find out by having a
place they denied written into, which is the failure the key exists to
prevent.

## The shape of the fix

Passing the right base at the third call site would work and would leave the
class open: the anchor would still be a thing each caller supplies correctly or
does not, and there would still be no way to tell by looking at a `Denied`
which of them it got.

`Config::from_path` already computes that directory and already uses it to
anchor `workspace.path` and every token command, for the same reason and with
the reasoning written down. Anchoring the deny entries there too means nothing
relative survives the load, so the base a caller passes stops being able to
disagree with anything.

That leaves the base argument meaningful only for a config parsed from a string,
which is what the unit tests do, and where the caller genuinely is the only
thing that knows.

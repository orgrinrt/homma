# release-reads-nut-toml

Workspace ticket 58f3f840efa4. `homma release plan the-whole-shebang --level minor` ends
`Error: manifest: no manifest`. nutshell and the-whole-shebang keep their version in `nut.toml` under
`[package] version`, with no `Cargo.toml` or `deno.json`, and the workspace declares `nut.toml` a `content`
marker, so release reads them as content, finds no manifest that carries a version, and refuses. Both fall to
the by-hand path, which the release rules forbid. Op asked for both released ("Rehouse, then release both").

## What the design says

`DEEPDIVE_release.md.tmpl`, The gate: `[markers]` maps a file to one of `cargo`, `deno` or `content`, and a
repo's kind is the set of signals its root carries. `content` adds no gate calls and carries no version, so a
content repo can be gated and never released.

## Decision

- A fourth signal, `nut`: a nutshell package. Like `content` it adds no gate calls and publishes to no
  registry, since a nutshell library is imported by its git uri at a tag. Unlike `content` it carries a
  version, `[package] version` in `nut.toml`, which a release reads, bumps in place and commits as it does
  `Cargo.toml`'s.
- The kind gains `nut`. A root carrying `nut.toml` beside `Cargo.toml` or `deno.json` is that manifest's kind
  and its `nut.toml` is not versioned by a release; no repo carries both, and the kind is a closed list of
  combinations rather than a set (follow-up ticket for the set).
- Which files carry the version is one list per kind, in `version.rs`, read by the plan, the bump commit and
  the check's walk of bumps on `main`, so none of them names a file of its own.
- The workspace's `[markers]` row for `nut.toml` becomes `nut` once a homma that reads the signal is
  installed; an older binary refuses the word.

# The fixes failed in the manner they were fixing

Second review of this branch. Ten findings, and the reviewer's own summary is the
part worth keeping:

> Three of the ten findings above are the previous round's fixes failing in the
> manner they were fixing.

## The tautology, which is the worst of them

The previous round replaced a hand-written field list with a derived check,
because the list could not see a field nobody added to it. The test written to
prove the derived version works compares `reported` against `corrupted`, and
**both are produced by calling the same walker on the same value**. It cannot
fail for any implementation of that walker.

Reproduced here rather than taken on the reviewer's word: deleting the
`toml::Value::Array` arm, so the one array field is never scanned at all, leaves
the test passing.

The reviewer measured a second mutation to the same effect, excluding a named
field, also green. The only thing standing was `corrupted.len() >= 10` against
eleven corruptible strings, so it tolerated exactly one field vanishing.

`the-test-gate.md` names this exactly: "a result compared to the same
computation". It is not a weak test, it is not a test. And it replaced something
that did work, so the round shipped a stronger-looking claim over strictly less
coverage.

**The derived walk in `unsafe_strings` stays.** That part is a genuine
improvement and the reviewer says so. What goes is the assertion that cannot
fail.

## Two more of the same shape

`Identity::committer_name` was added this round because the unit named it and
only the email had shipped. It reaches nothing: ignoring the registry field
entirely leaves the suite green. It shipped as unread plumbing, which is the
exact shape U-3.1 exists to prevent.

`user.name` and `user.email` are written deliberately, with a comment explaining
that a later tool reading only those keys would otherwise see nothing, and
deleting both fails no test.

## And a fix that reintroduced its own defect one method down

The previous round fixed two concatenated doc blocks on `set_identity`, and the
same edit produced concatenated doc blocks on `identity`, whose summary line now
describes a return type it no longer has.

## The measurement that was scoped too narrowly

Two new clippy warnings, both introduced by this diff, on the five-tuple fields
in the test doubles. The check run was `cargo clippy -p homma-core`, which is the
one crate that does not carry them. `--workspace` reports both.

The fix is the one this branch already built and then did not use: the write side
takes four consecutive `&str` while the read side returns a `CommitIdentity`.
Passing the type both ways removes the positional hazard and the warnings
together.

## A silent semantic change

The read-back lost `.filter(|s| !s.is_empty())` when it was widened. A clone with
empty configured values now returns four empty strings where it returned
`None`. Nothing tests either case and the trait doc still says "if any".

## What the round owes upward

Roadmap U-3.1's Produces names three config keys. The code writes six, correctly,
because a global `author.name` beats a local `user.name`. The code is right and
the roadmap is behind it, and that is a design-tier edit in the workspace rather
than something to fix here.

# A check that could not run says so, rather than blaming the repository

Subject: the commit gate reads one exit code for two different things, and the
advice it gives is right for one of them.

## Current state

The gate runs `homma --dir <ws> repo config check --repo <name>` and branches on
whether the exit code is zero. Every non-zero is read the same way: each line of
the output becomes a problem, and the refusal ends with

    Run `homma repo config init --repo <name>` to place what is missing.

`homma` produces that non-zero from two places. `Outcome::ReportedFailure` is
the command running and finding that the repository owes a config, which is what
the advice is for. An `Err` is the command not running at all, and the commonest
one on this path is the workspace manifest failing to parse, since
`load_config` sits ahead of every repo subcommand. Both leave `main` returning
`ExitCode::FAILURE`, so the gate cannot tell them apart.

The second case is worse than an unhelpful message. `init` loads the same
manifest through the same function, so a person following the advice gets the
same failure with a different verb, and nothing in either message names the
manifest that is the actual fault.

The last round found this from the other side without naming it: its fixture
wrote `content_repo` alone, the parse failed, and its own changelist records
that the error points at line 1 column 1 and says nothing about what is missing.

## The decision

Split the exit codes, and let the gate read the split.

`ExitCode::SUCCESS` for a command that ran and found nothing to say. `1` for one
that ran and reported. `2` for one that could not run, which is every `Err`
reaching `main`. That is the whole of the change on the command side, and it is
a contract rather than a special case for this gate: any caller reading a
`homma` exit code wants the same distinction, and none of them can currently
make it.

The gate then has two arms. Exit `1` is unchanged, since that is the case its
present wording was written for. Anything else non-zero says the check could not
run, gives the output as the reason, and names the workspace manifest rather
than a command that will fail identically.

It keeps denying in both. A check that could not run must never be
indistinguishable from one that ran and found nothing, which is the reasoning
the missing-`jq` and missing-`homma` arms already carry.

## What this does not do

Nothing about the parse error's own wording. Pointing it at the missing table
rather than at line 1 is a fault in the manifest's diagnostics and belongs with
whatever owns those, exactly where the previous round left it.

Nothing about `init`. It fails the same way on an unparseable manifest and
should, since it cannot know what to place either. What changes is only that
nobody is sent to it for a fault it shares.

## Provenance

Derived, under the autonomous mandate, from a review finding against this
branch. No human was in the loop at the time of writing.

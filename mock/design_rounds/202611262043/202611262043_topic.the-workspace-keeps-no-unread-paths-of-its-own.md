# The workspace keeps no unread paths of its own

## The defects

A review of the round that names the `[paths]` keys the engine does not read found two:

- `Workspace::paths_unread` is computed on every parse and read only by a test. The status computes the same list from the raw table with `Paths::unread`, so the field is a second copy of a fact the status already reads where it is held.
- A key probe that fails is propagated by `Workspace::parse`, which then refuses the whole manifest, and swallowed by the status, which says the probe failed in its `reads` line. One fault, two answers.

## The fix

- `paths_unread` and the probe in `Workspace::parse` go; the parse is the typed parse alone, as before the round. `Paths::unread` stays as the one place the list is worked out, and the status stays its one reader.
- That settles the second: the probe runs only in the status, where a failure is the `reads: not known` line it already prints, and the manifest's parse no longer depends on it. Propagating it from the status instead would fail `homma status` on a fault of the tooling, which is what the line was made to avoid.
- Landing B, the refusal, is not part of this; when it comes it refuses in the typed parse, through `deny_unknown_fields`, and needs no list kept on the workspace.
- The api crate's design passage on `paths_unread` is rewritten to name `Paths::unread` and its reader, the status. The tests on the field are rewritten against `Paths::unread`, and one keeps that a manifest with unread path keys parses.

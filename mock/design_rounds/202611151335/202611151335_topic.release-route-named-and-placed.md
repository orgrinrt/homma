# release-route-named-and-placed

A follow-up to round 202611151306. Its review, `mock/research/202611151330_release-forge-routes-review-2/review.md`, left two findings that change the design rather than the code under it.

## Current state

- `forge_route_of` resolves the path `forge_route` names and does not look whether anything is there. A manifest naming a route that is missing reads as a route, and the release fails at step 6 as a command that cannot be run, after `main` was pushed: the same failure after `main` has moved that made an unreadable manifest an error in round 202611151306 (review 2, finding 3).
- In `DEEPDIVE_release.md.tmpl` the paragraph on `ReleaseForge` sits between steps 7 and 8 and splits the numbered run in two; the doc changelist of round 202611151306 placed it after the steps (review 2, finding 8).

## Changes proposed

- A route the manifest names that is not a file is an error at `forge_route_of`, read once per run before any repo runs, with the manifest and the path it named. A test names a manifest whose route is missing and is shown failing without the check.
- The `ReleaseForge` paragraph moves below step 9, and says that a named route that is not there is an error with the unreadable manifest, and that the fetch after step 6 compares the remote's tag before it writes it into the clone.
- The rendered `docs/` are regenerated with the round, so `docs/DESIGN.md` and `docs/CORE_RELEASE.md` match their templates (review 2, finding 1).

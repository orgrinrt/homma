# Release reaches the registries and every clone of the workspace

Two tickets filed by the coordinator on 3 November, both found by its release sub-agent in a cloud container: `homma_release_cannot_reach_crates_io_or_github_through_the_p` and `homma_release_check_refuses_repos_outside_the_clone_s_repos`. The intent is that `homma release check`, `plan` and `run` work in a cloud container, for any repository of the workspace, whichever repositories the clone's local file names.

No flat topic is open on the trunk. Every other ref was read for flat topics and round directories this branch cannot see: `work/homma-hook-red` holds earlier copies, under the `202610270710` stamp, of three topics that the closed round `202610311627` already consumed under their `202610270717` stamps, and `main` holds one old source changelist of `202608251651`. Nothing there needs this round.

## Finding one: the registry and forge requests trust only the bundled roots

A cloud container sends every outbound HTTPS request through a proxy whose certificate authority is a bundle at the path `SSL_CERT_FILE` names. `homma-core` asks the registry indexes (`release/registry.rs`) and the forges (`forge/github.rs`, `forge/forgejo.rs`) with `ureq` 2, declared with the `tls` feature and not `native-certs`. In `ureq` 2.12.1, `rtls.rs`, the two features differ in one place: without `native-certs` the root store is `webpki_roots::TLS_SERVER_ROOTS`, with it the store is what `rustls_native_certs::load_native_certs()` returns. The bundled roots read no environment, so a request through the proxy is refused as an unknown issuer, and `release check` and `release run` fail before they have looked at the repository.

The roots should be the system's, and where `SSL_CERT_FILE` or `SSL_CERT_DIR` is set, the ones it names. The three call sites build their agents separately and keep their own timeouts and headers, so the change is the one dependency feature that all three inherit, and not a copy of a loader in each.

A test has to fail without the feature, so it serves a local TLS endpoint with a certificate made for the test, and asks it once with `SSL_CERT_FILE` naming that certificate and once without. The request with the file succeeds and the request without it is refused as an unknown issuer.

## Finding two: a named repository outside the scope is not found

`Config::from_path` reads the scope from `homma.local.toml` beside the manifest and `detect_members` skips every clone the scope does not admit, by name and before the directory is touched. `homma release check renki` in a clone whose local file names other repositories answers "`renki` is outside this clone's scope", reproduced in this container. The scope narrows what a clone works on, and the root design says a command that works on the members never opens a clone outside it. A release of a repository is not that work: which repositories a clone serves says nothing about which can be released from it.

The settled shape is that every release verb finds its repository among every clone of the workspace, whether the repository is named or is the one the working directory is in, and the one verb that names none and means all, `release run` with no repository, stays within the scope. The sweep is the one place where widening would be harmful, since a container attaches clones it only reads and a sweep over every clone would try to release them. The gate verb is in the widened set: it measures the clone it is given, and the pre-push entry of a clone outside the scope is a clone that still has its hooks.

The config therefore has a second way in beside `Config::from_path`, `Config::from_path_whole`, which is the same load with the scope taken as everything, and the release command uses it for every operation except the sweep. Both loads share one body that takes the scope as a function of the manifest's directory, so there is no bare flag choosing between them.

## What is not changed

`status`, `what` and every other command keep the scoped config. A name that is not a directory of the workspace still says there is no such repository, and a scope that does not name a clone still leaves it out of every other walk.

## Tests that must fail

For the roots: the pair above, and a check that the request without the file is the unknown issuer and not some other failure. For the scope: a workspace of two clones whose local file names one, the config loaded whole holds both, the scoped load holds one, `release check` of the one outside finds it by name and from its own directory, and `release run` with no repository still leaves it out.

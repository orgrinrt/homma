# capture-long-paths-and-the-harness-evidence

The review of round `202609242321` left three things, and all of them are about
how well the capture knows where the harness keeps a transcript.

The spelling of the project directory was asserted without anything in the
repository showing it. It is read out of the installed harness now, version
2.1.282, and the lines are kept in
`mock/research/202609242353_harness-project-directory/extracted.txt`:

```js
function TX(t){let e=0;for(let n=0;n<t.length;n++)e=(e<<5)-e+t.charCodeAt(n)|0;return e}
var hte=200;function Le(e){return Math.abs(TX(e)).toString(36)}
function k(e){return e.replace(/[^a-zA-Z0-9]/g,"-")}
function fx(e){let n=k(e);if(n.length<=hte)return n;return`${n.slice(0,hte)}-${Le(e)}`}
```

The regex has no `u` flag, so it replaces per UTF-16 unit, which is what the
design already says. What it does not say is the second half: a name longer
than two hundred units is cut at two hundred and gets `-` and a hash of the
whole path, the 32-bit string hash `h*31 + unit` over the path's UTF-16 units,
wrapped, its absolute value in base 36. `store::escaped` does neither, so
without a session id a capture under a long path finds no directory and says
so; with an id it finds the transcript anyway, since it looks in every project
directory. The injector in the workspace has the same gap and there it is
silent: no record, and its lines quoted as the person's.

`TX` has a second minified definition in the same binary, over a message rather
than a string, and the one beside `hte` is the string one; its arithmetic is
what a test pins, so a harness that changes it shows up as a red test rather
than as a wrong directory.

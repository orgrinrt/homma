# one-planting-crate-every-test-binary-reaches

Extends rounds 202611251443 and 202611261602, which made `cmd::planted::script` the one way a test
of `homma-engine`'s binary plants a script it will run.

## Where the planting helper lives

`cmd::planted` is a `#[cfg(test)]` module of `homma-engine`'s binary. The binary's integration
tests are other crates and cannot reach it, and neither can the tests of `homma-core` and
`homma-org`. Thirteen places in those still write a script in the test process, mode it and run it.
Under a test runner that runs tests as threads of one process, a fork on another thread while the
script is open for writing makes the run fail as busy, the same race the earlier round closed for
the binary's own tests.

The alternatives:

- A copy of the helper in each crate's `tests/common`, and one in each library's test modules.
  Rejected: four copies of one thing, which is the failure the earlier round named when it moved
  every helper of the binary onto one.
- A public module behind a `test-support` feature of an existing crate, `homma-core` the lowest one
  that does I/O, taken as a dev-dependency of itself and of the crates above. Rejected: a library
  crate would carry test machinery in its public surface, and `homma-core` would hold a thing that
  is not its own.
- Including the binary's source file into each test binary by path. Rejected: a test reaching
  into another crate's tree by a relative path is a dependency cargo does not see.
- A crate of its own, `homma-fixture`, taken only as a dev-dependency by every crate whose tests
  plant a script. It depends on nothing of homma's, so any crate at any layer may take it, and
  nothing ships with it: it is `publish = false` and no normal dependency names it.

Decision: the crate. It holds what a test needs to stage the world outside the code under test,
and nothing else. `cmd::planted` is removed and its callers use the crate.

## The writer that is a command's own

`answers::hook::place` writes the hook it places and modes it in process, and its test then runs the
hook. The writer is the command's, and in the command it is right: the command is one process that
starts nothing while it writes. Writing it through a child in the command for a test's sake would
change shipping code to fit a test runner. Running the hook through `sh` in the test would leave
untested what mockspace relies on, that the hook runs when executed.

Decision: the test calls `hook::place` in a child of the test binary that runs that one test alone,
so the write happens in a process this one never forks from, and the test then executes the hook as
mockspace does. The cache test of round 202611261602 already reruns itself in a child to set
`GIT_DIR` only there; the rerun becomes the crate's second helper, and both tests use it.

## What stays

The skills corpus test that modes a fixture file never runs it: it checks the mode survives a copy,
so no exec can find the file busy. The busy-handle demonstration in `what/mock_tests.rs` holds a
write handle on purpose, and the non-text blob in `what/sources_tests.rs` is never run. Decision:
the three stay as they are.

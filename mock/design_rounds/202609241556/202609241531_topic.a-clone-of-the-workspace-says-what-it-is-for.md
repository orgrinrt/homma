# a clone of the workspace says what it is for

## Where this comes from

The lead designer, 2026-09-24, asking for a page on his account that shows any
workspace's state without asking the session running it, generated from data
and kept current by scripts rather than by an agent writing prose:

> there has to be a local, git ignored file called homma.local.toml or
> something (it should be a homma utility) that allows setting up configuration
> for this very thing for this specific workspace instance.

> This means each needs a local homma config that describes their current
> workspace, the full set of work, and whatever metadata needed for this allll
> to work.

The page and the scripts behind it are the workspace's own tooling and are not
homma's. What is homma's is the file, because what it describes is a property
of one clone of a workspace, and homma is the thing that knows what a workspace
and its clones are.

## What is missing

`homma.toml` is committed and shared by every clone of the content repository,
so it can only say what is true of the workspace everywhere. The same content
repository is cloned once per body of work, and the directory it sits in is
the only record of which one a clone is for. A tool wanting to know that has to
guess from a path, and a tool wanting its own settings for this clone alone has
nowhere to put them that git will not try to share.

## The shape

A file beside the manifest, `homma.local.toml`, never committed. Two tables.

`[instance]` is homma's and is typed: what this clone is for. `work` names the
body of work and is the one required key. `title` is what to call it. `repos`
narrows which members the work spans, all of them when empty. `state` and
`goal` are paths, relative to the workspace root, to the document carrying the
work's current state and to the one carrying what it is trying to reach. None
of these is invented for the page: a state file per body of work and a goal
recorded verbatim are what this workspace already keeps, and the file only says
which ones are this clone's.

`[tools.<name>]` is the workspace's own tools' and is not typed, for the reason
`[[status.inject]]` gives: homma carries a tool's settings without growing an
opinion about them. The page's generator keeps its published address there.

## The commands

`homma local init --work <name>` writes the file with the keys in it, refusing
to overwrite one that exists, and adds `/homma.local.toml` to the workspace's
`.gitignore` where no line already names it. Ignoring it is part of making it,
because a file described as never committed that is one `git add -A` from being
committed is a file that will be.

`homma local show` prints it, the document whole with `--output json`, so a
script reads it through homma's parser rather than growing a second one.
Absent is exit 1, a command that ran and reported, since a script asking has to
tell no file apart from homma failing.

`homma local set <table.key> <value>` writes one string, and only under
`instance` or `tools.<name>`. It exists so a hook can record what it learned
without an agent editing a file, which is the whole of what makes the page cost
no tokens to keep. It rewrites the value and keeps every comment around it, and
refuses a result that would not parse.

`homma status` carries the instance: a line in the human output and the table
whole in the document, `null` where there is no file. The document grows a
field rather than changing shape, which is what the status section already
promises its readers.

## What loads it

The manifest's loader, beside the manifest, anchored the way everything else in
`from_path` is anchored. A file that is there and does not parse fails the load
naming itself, the same as the manifest does, since a setting silently ignored
is worse than a command that refuses. A file that is not there is the ordinary
case and nothing notices.

## What this does not do

It does not decide what a body of work is, where state files live or which
goal is current. Those are the workspace's conventions and the file points at
them. Nor does it read the workspace tools' tables, validate them or know what
any key in them means.

# capture-agent-fields-rounds-and-session

## What the third review of the capture command found

A fresh reviewer read the pull request after round `202609241954`. Every finding
of the review before it holds as fixed. Three new ones block, and each was
checked against something that ran or against real transcripts.

**The agent's single-line fields reach the margin.** The title, a question's
header and an option's label are written as they arrived. A line break followed
by `>` in any of them puts a line at the margin that the voice tool reads as the
person's, which is exactly what the design says a capture never does. The probe
got four such quotes out of one capture, the label twice because it is written
under the options and again under what was chosen. Descriptions, previews, the
question and the turn before are safe, since they are fenced or indented.

**An answered round is recognised by the shape of its result, and another tool's
result can have that shape.** Any tool result with an `answers` key is read as a
round, and one without `questions` beside it is refused. The transcript is read
whole on every run, so a single such line stops every later capture of that
session for good. The reviewer made one with a planted line; the dashboard work
in the workspace now has agents reading a page collection named `answers`. The
harness does say which tool a result belongs to: the result's content block
carries `tool_use_id`, and the assistant line that made the call carries the
same id with the tool's `name`, `AskUserQuestion` for an ask round. Checked on
this session's own transcript: two ask results, each id found on an assistant
`tool_use` block named `AskUserQuestion`.

**"The newest transcript" is not the session running the command.** Headless
sessions wrote into the same project directory as the interactive session this
afternoon, three of them, and a run in those windows reads one of those instead,
reports nothing new, and the skill then says there is nothing to capture. The
harness exports the running session's id to every shell it starts, as
`CLAUDE_CODE_SESSION_ID`; checked here, it names this session's transcript. A
session started inside a member repository keeps its transcript under that
repository's project directory, not the workspace's, which the newest-file
default cannot find at all.

## Where the design itself drifts

The design says nothing about the workspace homma was born in is compiled in,
and every path has a default and an override. The store's directory is a
constant, `.data/op-responses`, overridable per run by `--into` and not by
configuration. `[paths]` in the manifest is where every other such directory is
named, so the store belongs there with that constant as its default.

The design also says homma persists through one engine. A capture is not a
record homma persists for itself: it is a file written for another reader, the
voice tool, in that reader's format, and the design's own list of what is not the
record store includes "prose in a generated file". The watermark is read back
out of those files rather than stored beside them, so there is one copy of it.
The design should say so rather than leave the reader to square it.

`tags: [chat]` is written into every capture and the design never mentions it.
The store's convention has it on every capture made from a session, 280 of them,
and the voice tool reads `tags` from the front matter. It stays, and the design
names it.

## Smaller things the review raised

- The locked source changelist of round `202609241954` says `Question` carries a
  `multi` field. The code carries the choice as a local `Takes` read in `round`
  and passed to `answered`, and `Question` has no such field. A locked
  changelist is not edited; this topic is where the correction is written down.
- Tests and comments say `his` and `he` about the person and name the retired
  archivist and "what the review found". The design says the person, and source
  is public, so those go.
- The smoke test makes a symlink through `std::os::unix` with no gate on it.
- A title's slug drops every letter outside ASCII, so `Käyttö` becomes `k-ytt`.
  Finnish titles are the common case here. Folding `ä` and `å` to `a` and `ö` to
  `o` keeps them readable; anything else outside ASCII still goes.
- The reviewer ran the quote round trip exhaustively over short strings and a
  probe of all six places agent text can sit. Both belong in the suite rather
  than in a report.

## Not taken

- A tool rejection line can carry a `userFeedback` field. The only two real
  instances, both on 2026-08-30, hold `Denied by user`, which is the harness's
  label and not anybody's words. Nothing to design against until one holds typed
  text.
- The dashboard's answers arrive through a page's data store, not through the
  transcript's human lines or an ask round, so a capture cannot see them. That
  channel needs its own design once one real answer shows what shape it has.
  Filed as a fresh topic after this round closes.

# capture-what-op-says

## Why this is homma's

The workspace keeps a store of everything its owner says to an agent session,
verbatim, one file per capture under `.data/op-responses/` in the content
repository. Until now a sub-agent wrote every capture: the coordinator pasted
the words into a brief, the sub-agent reformatted them into a file. That spends
a dispatch on a copy, and it copies twice, through the brief and through the
agent, which is two places for a word to change.

muisti's design splits the job, in `.shared/designs/muisti-the-corpus-crate.md`
under "The archivist's job splits, and only half of it is a model's": the
verbatim half is a string operation and stays one, since a span copied from a
transcript and checked by equality is the thing the store exists to get right;
the context half, what was going on and what it bears on, is summarisation a
local model can do through muisti's `answer`. The verbatim half needs no model
at all, and it is the half that spans repositories: the transcript sits under the
person's home directory, the store sits in the content repository. So it is a
homma command, and the model half joins it once muisti can be built where homma
runs.

## What the transcript holds

The agent harness writes one JSON object per line to
`~/.claude/projects/<escaped workspace path>/<session id>.jsonl`, the path
escaped by turning every character outside `[A-Za-z0-9]` into `-`. Read off real
sessions in this workspace:

- A line the owner typed is `type: "user"` with `message.content` a string and
  `origin.kind` set to `"human"`. That marker is the whole test: every other
  string line in the sessions read (hook feedback, compaction summaries, task
  notifications, command output, review prompts the harness sends itself) lacks
  it, and every line carrying it is his, a slash command with its argument and a
  pasted file path included. Filtering on the text instead, by a leading `<` or
  `/`, drops those last two and keeps the review prompts.
- Words typed while a turn runs are queued. The queue's own lines
  (`type: "queue-operation"`) are bookkeeping and are not read. A queued message
  lands one of two ways: as an ordinary typed line once the turn ends, or, when
  the running turn takes it, as an `attachment` of `type: "queued_command"`
  whose `prompt` holds the words, again with `origin.kind` `"human"`. Reading
  both of those and nothing else takes each message exactly once.
- An ask round's answer is a user line whose `toolUseResult` carries
  `questions`, `answers` and `annotations`. The questions come back whole, each
  with its `header` and its `options` (label, description, and a `preview` where
  one was given), so the round is read off that one line without joining it to
  the assistant's `tool_use`. `answers` is keyed by the question's text;
  `annotations` holds his notes, keyed the same way.
- Every line carries `timestamp` in UTC and `sessionId`. A resumed session
  replays lines, so events are deduplicated by their `uuid`.

All of that is the harness's format rather than a contract anybody published, so
the parser refuses what it does not recognise by name rather than guessing, and
the tests pin the shapes read today.

## Decisions

**The words are copied from structured fields, never from rendered text.** Every
quoted span is the exact string the transcript holds, so a capture's blockquote
can be checked against the transcript by equality.

**Only his words are blockquotes.** The voice tool reads every blockquote in a
capture as one of his remarks (`.shared/scripts/voice/src/corpus/remarks.ts`), so
the agent's text around them, the question put to him and the turn before an
unprompted message, goes in fenced blocks. The existing captures quote the
question as a blockquote; this is the correction, and the old ones stay as
written.

**The watermark is derived from the store, never kept beside it.** A capture
names its `source` session and the `through` timestamp of its last event in its
front matter. A run takes only the events after the latest `through` any capture
records for that session, so running it twice writes nothing the second time and
there is no state file to go stale.

**One run is one capture**, holding every new event in the order it happened,
with `kind` saying which: `unprompted`, `ask`, or `mixed`. That matches the
standing rule of one capture per stretch rather than per message. A run with
nothing new writes nothing and says so.

**The title is given, never made up.** `--title` is required; the slug is derived
from it. The title decides whether the voice tool reads the capture, so it is the
one piece of judgement, and the caller is the one holding it.

**The context is extractive until the model half lands.** For each event the
capture carries the last text the agent wrote before it, verbatim, in a fence.
That is longer than the archivist's summary and it is exact. The summary through
muisti's `answer` replaces it once muisti builds here, and is marked in source as
the gap it is.

**`bears_on` is what the caller names plus paths the words mention that exist**
under the workspace root. Nothing else is inferred.

**`when` is local time**, as every capture already carries it, taken from the
first event; the file name is that stamp plus the slug.

**It writes the file and nothing else.** Committing and opening the pull request
stay with the caller, who is already on a branch in the content repository; a
command that pushes on its own is an outward act nobody asked of it.

## What it replaces

Once it lands, the `capture-op-input` skill says to run it rather than dispatch
the `log-archivist`, the persona is retired, and the store's readme names the
command as the author. That is a workspace change and lands after this round.

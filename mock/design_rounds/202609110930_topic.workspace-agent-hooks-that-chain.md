# workspace-agent-hooks-that-chain

## What op asked for

From `.data/op-responses/202609110910_muisti-bench-guard.md` in the workspace
repository, verbatim:

> Write a script to disallow running the muisti side benches or such on this macos. Last time we just simply crashed the entire system. It's not doable here, shouldn't even try to. Use the lifebook. Keep the repo decoupled from the remote though, so just make it a homma thing, that isn't  visible in the muisti repo itself, so it transfers always when working on muisti, but doesn't leak that to anyone reading or using the muisti repos itself

> Use git-shook here, obviously

Then, asked whether the guard should be a `cargo` shim with an agent hook in
front, an agent hook alone, git-shook carrying an installer at `post-checkout`,
or a git-shook entry at commit and push:

> Oh right I mistook git hooks from agent hooks. We want homma to handle the agent hooks I suppose, and do similar thing for the mockspace generated hooks as git-shook does for the git ones, as in, properly chain and preserve, never replace or drop. So it's a thing to add to homma upstream I think

The intent, as I read it: homma owns the workspace's agent hooks the way it
already owns the git hooks it installs, so a workspace can declare one and every
session in it carries it. And the aggregation of the hooks mockspace generates
per repository keeps every one of them, in the event and matcher it was written
for, and never removes or overwrites a hook it did not write. "I suppose" and "I
think" are hedges on the placement, which the reading of the code below bears
out rather than contradicts. The "similar to git-shook" is the vehicle, and the
part of it that carries over is the preservation, not the dispatcher; see below.

## What the code does now

All in `mock/crates/homma-engine/src/cmd/aggregate.rs` and `gates.rs`, read on
`dev` at the time of writing. These are claims about code, not about design:
the design is silent on agent hook aggregation entirely, since the only design
text mentioning it is the containment paragraph at
`mock/crates/homma-org/DESIGN.md.tmpl:196`, and that is about where the pass may
write rather than what it writes.

- **A repo hook with no registration is dropped without a word.**
  `aggregate_hooks` writes the wrapper for every `*.sh` under the repo's
  `.claude/hooks/`, then takes matchers from the repo's `settings.json` or from
  an `@matchers:` line, and a hook with neither gets a wrapper and no entry
  (`aggregate.rs` around line 193). The regen reports it as aggregated.
- **Every event becomes `PreToolUse`.** `read_settings_hooks` walks every event
  in the repo's `settings.json` and keeps only command-to-matcher pairs, and
  `merge_settings` writes all of them under `hooks.PreToolUse`. A repo's
  `PostToolUse`, `Stop` or `UserPromptSubmit` hook lands at the wrong event.
- **What is homma's is decided by a filename.** `clean_stale` deletes every
  `<repo>--*.sh` in the workspace's hooks directory and `merge_settings` sweeps
  every entry whose command's basename starts `<repo>--`, so a hand-written hook
  that happens to carry the prefix is removed. Everything else hand-written is
  kept, which the test `merge_settings_preserves_hand_authored_entries` pins.
- **Only `.sh` files are aggregated**; a hook in another language is skipped.
- **A Bash call is scoped by the hook process's `$PWD`**, not by the `cwd` the
  host hands the hook. The wrapper reads `tool_input.file_path`, `path`, then
  `tool_input.cwd`, and a Bash call carries none of the three, so a session
  rooted at the workspace running `git -C muisti commit` never reaches muisti's
  own gate.
- **There is no way for a workspace to declare an agent hook of its own.** The
  one workspace hook homma writes is the mockspace bootstrap gate. Anything else
  is a hand edit to a generated file, which works because of the preservation
  above and is found by nobody.

## What the host does, which changes what "chain" means

From `https://code.claude.com/docs/en/hooks`, fetched 2026-09-11: "All matching
hooks run in parallel. If you define the same handler in more than one settings
file, it runs once." The page does not say how a deny and an allow from two
hooks on one call are reconciled.

So the problem git-shook solves does not exist here. Git runs one program per
event, which is why a dispatcher and a registry are needed there; the host runs
every registered entry already. What carries over from git-shook is the rest of
it: what the tool wrote is identified by what it wrote rather than by a name,
anything else is kept, and nothing is registered or dropped without saying so.

A dispatcher per event is still an option and is not free: it puts a homma
process on every tool call, serialises hooks the host runs in parallel, and
buys an order that nothing here needs. The case for it would be that one
settings entry per event is easier to keep correct than one per hook. I lean
against it, and the doc changelist should say which and why.

## What I would propose

- **A table in `homma.toml`**, beside the git hooks table: rows per host event,
  each with a matcher, what to run, and optionally the repositories it is scoped
  to. homma writes each as a managed entry. The first row is the workspace's
  `.shared/scripts/lifebook/guard` at `PreToolUse` on Bash, which is registered
  by hand today.
- **Ownership by marker.** A wrapper homma writes carries a marker line, the way
  mockspace's hooks carry `# mockspace-managed`, and a settings entry is homma's
  only when its command is a file carrying that marker. A hand-written file that
  collides with a managed name is refused with its path rather than overwritten.
- **Every event kept.** A repo hook is registered under each event and matcher
  its repository declares for it.
- **Nothing dropped quietly.** A repo hook with no event or matcher anywhere is
  an error in the regen report naming the file, and the regen exits non-zero,
  rather than a wrapper nobody calls.
- **The Bash scope reads the host's `cwd`**, then the path fields, and `$PWD`
  last.

Open for the doc changelist: whether non-`.sh` hooks are aggregated or refused
out loud, and whether the table's `run` is a string like the git table's or an
argument list like git-shook's.

# a-member-on-a-version-line-of-its-own

## The ask

A release carries one version line per repository: the root's version, or a
virtual workspace's primary's, with every other member riding it. A member
that is a library of its own, versioned for its own users, has nowhere to go.
tomlfuse is the case at hand: `tomlfuse-parse` is a TOML reader any crate can
take, at `0.0.1-rc.1` on `dev`, with its own `release.toml` saying
`shared-version = false`, beside `tomlfuse` and `tomlfuse-core` at `0.0.5`
since `v0.0.4`. `release plan tomlfuse --version 0.0.1-rc.1` refuses it as no
step above `v0.0.4`, and `--level patch` would publish all three at `0.0.5`.
The work, as the coordinator put it: homma's release tool releasing one crate
of a workspace. The question of which way tomlfuse-parse goes is op's and
still open (`tomlfuse_parse_s_first_release_its_own_version_line_or_the_w`,
options: its own line in homma release, the whole workspace on one number, a
repository of its own); this round builds the first, which the other two do
not need.

## Taken

A member keeps a version line of its own where its directory holds a
`release.toml` with `shared-version = false`, the key cargo-release reads for
the same thing and the one the repo already writes. Nothing else declares it,
and a member without the file stays on the repo's line, as now. A virtual
workspace's primary cannot be on a line of its own, since its line is the
repo's; that refuses the plan by name.

An own line has its own tags, `<crate>-v<version>`, cargo-release's name for a
crate's own tag. The repo's tags never read them, since none names a version
as `tag_version` reads it, so the repo's last tag, its steps and its checks are
untouched by them. The member's last tag is its newest tag of that shape.

Its version is its manifest's, set by hand on `dev` as a rider's is. It moves
where the manifest at the head differs from its version at its last own tag,
one step above it as `semver.gaps` reads it; with no own tag yet the
manifest's version is its first release as it stands. Its changelog block is
written into `<member dir>/CHANGELOG.md`, from the commits since its last own
tag that touch its directory, and it gets its own forge release on its own
tag, a pre-release for a pre-release version as the route already makes one.

`main` holds nothing unreleased, so the release has to account for every line
whose files changed. A member on its own line whose directory changed since
its last own tag and whose version did not move refuses the plan, naming it:
its change would land on `main` with no release carrying it. A rider stays as
it is, a warning, since its change rides the repo's release.

The repo's own line is what is left: the commits since the repo's last tag
that touch anything outside the own lines' directories, which is what its
block lists. A run names a level or a version for it, as now, and then every
own line that moves rides the same run: one bump commit with every manifest
and changelog the run writes, one merge onto `main`, and each tag on that one
merge commit. A run that names neither is allowed where the repo's line has
nothing since its last tag: the repo's version stays, no repo tag is made, and
only the own lines that move are released. With nothing on the repo's line and
no own line moving there is nothing to release, and the plan says so.

What the bump and the merge are named by is the release's name: the repo's
next version where it moves, else each moving line as `<crate> <version>`,
joined by `, `. The bump commit is `chore: release <name>`, the merge
`release: <name>`, the branch a refused bump is pushed as
`release/<repo>-<name>` with spaces and commas made `-`. A stopped run is read
back by that name, as it is read back by the version today.

The check reads each own line against its own tags: every version of it on a
registry has an own tag, the newest own tag is published, and its working
version is not below what is published. The repo-tag checks that read every
crate, `reg.orphan` and `reg.unpublished`, leave own-line members out, as they
leave riders out. `main.unreleased` reads `main` against its newest tag of
any line, since a release of own lines alone leaves `main` at a merge the
repo's tags do not name. An own tag is no stray tag.

Options weighed:
- A `--crate <name>` flag that releases one member alone, the rest of the repo
  left as it is: merging `dev` onto `main` carries the rest too, unreleased,
  which the rule on `main` forbids.
- Per-line targets on the command line, `--line <crate>=<level>`: the rider
  precedent already sets a member's version by hand on `dev`, and a second
  way to say the same thing is two mechanisms for one.
- The line declared in homma's own config: the repo already declares it in
  cargo-release's own key, and a second declaration could disagree with it.
- The member's own line, declared by `release.toml`, riding the repo's run or
  released alone where the repo's line has nothing (taken).

## What the design says

The release deep dive gains a section, `A member on a line of its own`, after
the virtual workspace, with what is above. The run section's level becomes
optional exactly where the repo's line has nothing to release, and the
surface lists `run <repo>` with no level. The check section names the own
tags and the own-line findings.

## Left for later

A sweep across the workspace with no repo named still takes one `--level` and
releases each repo's own line with it; own lines ride as they do in a named
run.

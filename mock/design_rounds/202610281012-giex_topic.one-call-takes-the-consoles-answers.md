# one-call-takes-the-consoles-answers

Op, 28 October 09:02, verbatim: "When I answer shit on the console, it should be just a single cli tool call away from being in the right places in the registry and in op sayings in data as a custom local hook when mockspace detects we are working within a homma workspace and that workspace has the capture tools and in that case just delegates in full. It should be automated. Most everything should be automated honestly. And stdin footprint, token spend, minimized."

The intent is that an answer or a note op gives in the console reaches the registry row it answers and the workspace's capture store with one call, and that the call says nothing when it succeeds. The vehicle he sketched is a hook in mockspace that delegates to homma's capture tools. The opening of this topic is that no capture command takes anything but a session transcript, so a console answer has no way in. The topic `202610270717_topic.capture-answers-left-on-a-page.md` waited for the first real answer to be read back before designing; the document the console sends is that answer, and its fields are `id`, `key`, `kind`, `where`, `asks`, `options`, `choice`, `text` and `at`.

## What this round takes

A command that takes answer and note documents from a directory or from a channel, writes one capture in the shape the dashboard's drain writes by hand today, skips what a capture already holds, and attaches each answer to its registry row as `<at>: <capture path>`, through the registry write that mockspace owns. A second entry of the same command is the delegate mockspace's hook point runs, so one `registry-append` of words in a workspace with capture tools lands the words in the store and a pointer in the row.

## Where the vehicle is changed

Op's words put the detection in mockspace. Mockspace is a generic design tool and learning one workspace tool's name would make it a second owner of what homma owns, so the hook point it gets names no tool: a file the workspace places above the repository. The detection op described is then true in effect, because the file exists only where homma installed it, and a repository cloned elsewhere has none and writes the row itself.

## What stays out

Landing the capture and the row change as a branch and a pull request stays with the caller, as `homma capture` leaves it. The dashboard's drain keeps its own copy of the capture text until it calls this command; that change is in the workspace repository and is handed back as a patch.

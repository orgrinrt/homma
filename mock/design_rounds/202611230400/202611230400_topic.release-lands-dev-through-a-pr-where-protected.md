## What the renki run showed

The 0.0.5-rc.4 run on 23 November looped. renki `dev` refuses pushes (GH013, a pull request is required), so each
`dev` commit the run made had to land through a pull request the coordinator made, and each resume then committed
again: the changelog block was prepended a second time over a `dev` that already held it, 7f84fae over 529dd0d.

## What changes

- Round `202611230020` made step 4 a push and nothing else, so a refused `dev` stopped the run with git's words.
  That stands as the first move: a `dev` that takes the push gets the push, and with the protection dropped
  nothing below runs. Where the forge refuses the push outright (`[remote rejected]`), the run now lands the same
  commit itself: `release/<repo>-<version>` pushed at the bump, `forge_route pr <root> <head> dev <title> merge
  <sha>`, the route `land-branch` and the release pull request already use. The pull request is always a merge
  commit and never a squash, so the bump commit stays an ancestor of `dev` and the branch it came from reads as
  landed (the reason round `202611230020` removed the squash).
- The route merges before it returns, so the run waits on it by calling it. The run then reads `dev` back from the
  remote and takes it only where it is a merge of the bump onto the `dev` the gate measured, with the tree the two
  make together, the check the release pull request already has. Another merge landing in between stops the run,
  nothing tagged.
- The branch the pull request came from is dropped through the route's `delete-branch`, best effort, as the squash
  path did before `202611230020`; `ReleaseForge::drop_branch` comes back for it.
- Resume reads what the forge holds, never what the run remembers. A bump the remote's `dev` holds as a merge
  commit titled `chore: release <version>` whose second parent is the bump commit is a pending bump like the
  clone's own: the trunk is set back to the merge's first parent for the check, the gate run and the plan, and step
  4 takes the merge as it is, whether the run's own pull request or the coordinator's landed it, and whether the
  clone's `dev` is at the bump, at the merge, or still at the tip before them.
- The bump is also idempotent by content. A `dev` whose manifest is at the planned version and whose
  `CHANGELOG.md` already holds a `## <version> (` heading gets no commit and no push from step 4; a missing half,
  the block or the version, is written alone. The block's own text is never compared, since the commits since the
  last tag include the bump itself after a resume, which is what duplicated it.
- Branch protection is not touched anywhere. The client (`ByClient`) has no pull request: a refused `dev` stays
  refused with `NoPullRequest`, the bump left on the local `dev` for the rerun.

## Left as it is

A squash the forge made of the bump unseen is still no landing of it (the clone's commit and the remote's are two
commits), as `202611230020` decided.

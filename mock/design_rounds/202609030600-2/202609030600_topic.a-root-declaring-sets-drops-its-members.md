# A root package declaring sets drops every member from the gate

Subject: the branch's `cargo_runs` builds a set-declaring root once per set and
never builds the members beside it, and nothing says whether that is meant.

## Current state

`cargo_runs` splits on whether the declaration carries an entry keyed `None`,
which is the root package's own.

The `None` branch, where the root declares nothing, is careful about members: on
a virtual root it emits `--workspace` with an `--exclude` per declaring member,
so a member that declares nothing is still built by the workspace-wide run and a
member that declares sets is built by its own.

The `Some` branch, where the root declares sets, emits one call per set and
nothing else. `members` is computed just above it and never read there. So in a
tree with a root package that declares sets and members that declare none, the
members are linted, tested and documented by nothing at all.

The function's own doc says a set-declaring root "is built once per set and
never with all features", which is a statement about the root and says nothing
about members either way. So the code and the comment agree and neither answers
the question.

It cannot happen today. `feature_sets` reads `[package.metadata.homma]`, so an
entry keyed `None` needs the root to be a package, and every workspace in this
estate has a virtual root. It goes live the first time a repository has a root
package with sets and members under it, and it fails silently: the gate reports
green having built less than it did the day before.

Found by a reviewer over this branch.

## The decision

Catalogue it rather than fix it, because which behaviour is wanted is a design
question this round is not the place to settle, and the two answers differ:

- The members are built, by a `--workspace --exclude <root>` run beside the
  per-set ones, on the reasoning the `None` branch already uses.
- The members are not built, because a root that declares sets has said which
  builds are legal for the whole tree, and a workspace-wide run would perform
  one it excluded.

The second reading is not absurd, which is what makes this a question rather
than a defect. What is not defensible is the current state, where nobody has
said which and nothing would notice the difference.

So the test asserting the first reading lands red and ignored with a
`catalogue:` reason, per `catalogue-edge-cases-as-tests.md`. The assertion
states the intended behaviour rather than the present one, so it flips green if
the decision goes that way and gets deleted with a sentence if it goes the
other.

## Provenance

Derived, under the autonomous mandate, from a review finding against this

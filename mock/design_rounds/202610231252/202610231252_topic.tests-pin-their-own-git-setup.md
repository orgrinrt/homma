# tests-pin-their-own-git-setup

Seven tests fail on `dev` in a container that exports `GIT_AUTHOR_NAME`, `GIT_AUTHOR_EMAIL`, `GIT_COMMITTER_NAME` and `GIT_COMMITTER_EMAIL` and whose git has no `init.defaultBranch`: `a_commit_carries_the_author_and_the_committer_separately` in `homma-core`, four in `cli_release` and two in `provisioned_commit`. They are not one defect. A git author environment variable outranks every config key, so a commit made by a spawned `git` carries the machine's identity and not the one the test configured, and a `git init` without `-b` makes `master` where the code under test reads `main`.

For the one in `homma-core` and the four in `cli_release` the fault is the setup: the test asks what `GixGit` writes into a configuration, or builds a repository for a release check, and the machine's environment answers instead. Those tests remove the four variables from the `git` they spawn and make their repositories on `main`.

The two in `provisioned_commit` are different, and the first version of this topic was wrong to fold them in. They commit in a workspace that `provision` stood up and assert that the commit carries the registry's identities, which is the seam `homma-org/DESIGN.md.tmpl` closes with six configuration keys against "a commit landing under whoever the machine's global configuration names". The environment is the next tier of that same hole, and the design is silent on it. Removing the four variables from those tests made them pass by taking away the input that shows the gap, so the removal is reverted in round `202610231408`, the tests set hostile values for the environment tier and are catalogued red, and the open topic `202610231408_topic.how-a-provisioned-workspace-defends-its-identity-against-the-environment.md` carries the question.

The tests are written to be independent of the machine's global config, `provisioned_commit` says so in its own comment and sets `GIT_CONFIG_GLOBAL` to a hostile file for it. The environment is the part of the machine they left open.

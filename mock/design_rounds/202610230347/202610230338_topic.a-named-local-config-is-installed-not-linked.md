# a-named-local-config-is-installed-not-linked


Recorded in the workspace repository by the coordinator of 23 October, from op at about 03:40. His words, whole:

> Also I think we need to serialise the local configs in the clause-dev repo itself as named projects, such as this is for kaski, so when a new session starts for you; you just link the one in the canonical serialised store to workspace root and rename to the local config

and his follow-up:

> Copy is perhaps better than link then. Do the intent, not exactly what I say.

The intent in it: each body of work's local config is kept in the content repository under its name, and a fresh session puts the named one in place at the workspace root as `homma.local.toml` in one step. The link, and the copy he moved to, are the vehicle, kept here for provenance.

The options the vehicle was chosen among, and why:

- A link from the root to the stored file. Every write a tool makes into `homma.local.toml` (the dashboard's publish record, the console's deployed commit, the goal's switch) would become an edit of a tracked file, and each of them would then show as a change in the content repository. Worse, `local set` writes a temporary file and renames it over the original, and a rename over a link replaces the link with a regular file, so the link would end at the first write and nothing would say so. The topic was checked by running `set` on a linked file before it was written here.
- A copy at install time, and the copy is then the clone's own file. Writes land in the copy. This is the option taken.
- Two files, the stored one read as a base under the clone's. Every reader of the file, including the shell tools that read it with their own parser, would have to merge the two.

Config and written state split by where they live and nothing in homma has to know which key is which: the store holds what is declared, and what a tool records is written only into the installed copy. A value that proves durable is moved into the store by editing the stored file, which is a deliberate change reviewed like any other.

Settled here without asking, because the canon is silent and the existing `local` verbs already decided their neighbours: the store is `.shared/local/<name>.toml` under the workspace root, beside the other authored sources homma reads (`.shared/rules`, `.shared/skills`, `.shared/agents`); a stored file's name is its `instance.work`; installing where a file of the same work already exists adds the keys it lacks and overwrites none, so a re-run is safe and a goal switched on locally is not switched off; installing over another work's file, or over a link, is refused unless `--replace` is given, and then the old file is moved aside rather than deleted.

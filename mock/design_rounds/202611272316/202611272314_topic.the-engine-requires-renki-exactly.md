# The engine requires renki exactly

## The ask

homma takes renki in two places that must be one renki: the launcher, which every operator installs, and the engine, which hosts the tools. Both now take renki from the registry, renki 0.0.5-rc.4 with renki-config and renki-dirs 0.0.2, where they took one git revision before.

The launcher's manifest says why its requirement is what it is: this is the launcher every operator installs, and it moves when the number in the manifest moves. A bare `0.0.5-rc.4` does not say that. It is a caret requirement, and on a prerelease it takes rc.5 and 0.0.5 as well, so a fresh resolve would move what every operator installs while the manifest's number stayed put. A bare `0.0.2` is exact for a `0.0.x` release and says so only to a reader who knows the rule.

Both manifests now require the renki crates with `=`. The launcher has a test over its own manifest: a `renki*` requirement that does not start with `=` fails it, with a control showing the caret, bare and path-only shapes. The engine's manifest names renki only under `cfg(unix)`, and nothing tests it: the two halves could drift apart again at the requirement, the one place the lockfile test does not look, since it compares what each lockfile resolved and not what each manifest allows.

## Taken

The engine's manifest is held to the same rule as the launcher's, by the same predicate and not a copy of it. The predicate sits beside the launcher's tests, which own the rule, in a file that is no test target of its own, and the engine's `one_renki` test reads it by path, as it already reads the launcher's lockfile. The predicate reads every dependency table of a manifest, the target-specific ones included, since that is where the engine names renki.

The engine's tests gain two cases. One reads the engine's own manifest and fails on a `renki*` requirement that is not exact. The other is its failing control: the engine's manifest shape, with the requirement bare.

Options weighed:
- A public function in `homma-fixture` or `homma-core` for both tests: a new declared item in a crate for what is only a test's check, and the launcher would take another dev-dependency.
- A second copy of the predicate in the engine's test: two predicates that must change together, which is what the rule of one renki is against.
- One predicate in the launcher's tests, read by path by the engine's test (taken).

## What the design says

The tools section says the engine and the launcher take one renki. It gains that they require it exactly, `=`, and that a test holds each manifest to it.

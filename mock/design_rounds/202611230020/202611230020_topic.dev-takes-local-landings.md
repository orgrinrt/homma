# dev-takes-local-landings

Tickets `some_landings_reach_dev_squashed_and_unreviewed_so_branch_ti`, `8c29e38b9e1d`, and, where they touch
this code, `a_landing_re_runs_the_whole_pre_push_gate_each_time_dev` and
`merge_dev_leaves_git_s_default_merge_subject_which_breaks_th`.

Op, 22 November, verbatim: "we'd prefer to make all repos compatible with local landing dev work and only gate
trunk to default (ie release) would need a pr".

## What changes

- A landing into `dev` is a local merge and a push. Only `dev` into `main`, the release, is a pull request.
  Step 5 keeps its release pull request, merged with a merge commit; nothing else in `homma release` opens one.
- Step 4 pushed the bump commit to `dev`, and where the forge refused that outright, it pushed the commit as
  `release/<repo>-<version>` and squashed it into `dev` through a pull request. That is the one path in homma that
  lands on `dev` through a pull request, and the one that squashes: the squash is a single-parent commit on a
  new sha, so the branch tip it came from reads as unlanded to every later check. It goes. A refused push of
  `dev` stops the run with git's own words, the bump stays on the local `dev`, and the rerun takes it back and
  pushes the same commit once the forge takes it. The remedy for a ruleset that wants a pull request on `dev` is
  on the forge, not a second landing path here.
- What only the squash needed goes with it: `Merge::Squash`, and with it the `Merge` choice itself, since the
  release pull request is always a merge commit; `ReleaseForge::drop_branch` and the deletion of
  `release/<repo>-<version>`; the bump's `NotLanded` check; the pending bump's `squashed` head and the resume
  of a squash the forge made unseen. A bump the remote's `dev` already holds as the clone's own commit is
  still taken as it is.
- Where the trunk and the release line are one branch there is no dev to land on, and a refused push stops
  the run the same way.

## The two tickets beside it

- The pre-push gate re-measures every tip pushed, and a landing whose push loses the race to a moving `dev`
  pushes again. A tip the record already holds a green run for is not measured a second time in the hook: the
  run is the gate's answer for that commit, whatever moved around it. The gate a plain `homma release gate`
  runs by hand still measures, since it is asked for. The larger idea in the ticket, gating only what the new
  `dev` commits touch, is the mockspace hook's and the landing script's, not homma's, and stays on its ticket.
- `merge-dev` is a workspace script, `.shared/scripts/remote/merge-dev` in clause-dev; homma holds no code
  that merges `dev` into a branch, so that ticket has nothing here and is bumped with that said.

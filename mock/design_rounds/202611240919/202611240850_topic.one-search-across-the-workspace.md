# one-search-across-the-workspace

## The question

Every member that keeps a repository index answers its own questions, and the content repository
keeps corpus indexes of its own, one per `muisti.toml`. Nothing answers one question across all of
them. Running each member's search on the command line and reading what it prints would make homma
a second, weaker reader of output formats it does not own; the indexes themselves are files homma
can open.

The intent, as the ticket states it: homma's search across the workspace is an optional layer over
each repository's own index, opened through the shared index crate, and no repository names it,
needs it or calls it. Each repository's search keeps working alone.

## What is the index crate's and what is homma's

The index crate (`muisti`, its `layer` module, designed in its own round on its own branch) owns
opening a file of either kind it writes, asking it by its own ranking, and fusing several answers by
rank with each hit naming its index. That is generic and depends on nothing of homma's, so any tool
holding several indexes uses it the same way.

homma owns what only the workspace knows: which indexes exist and what each is called, and the
verb. So homma writes no ranking, no fusion and no index reading of its own.

## Decisions

- **Which indexes.** The corpora are the `muisti.toml` files the content repository tracks, the
  root's and any nested one, each named by the content repository's name and the directory below
  it. Each one's index is the `corpus.index` its own file sets, or the default where it sets none.
  The members' indexes are under each member's own git directory at the path the members' search
  keeps it, named by the member's directory.
- **Members are an opt-in.** A member clone is ignored by the content repository and belongs to
  itself; homma opens its index only where `members = true` under `[search]` says so. Without it
  the verb asks the content repository's corpora alone.
- **Every place is a key.** `[search]` in the manifest holds `members`, `corpus_config`
  (`muisti.toml`), `corpus_index` (`.muisti/index.sqlite`) and `member_index`
  (`mockspace/search.sqlite`), each with that default, so no path is a literal in the verb.
- **Scoping.** `--in <name>` (repeatable) asks only the indexes named, so a question about one
  member opens one file. Unscoped, the indexes are opened one at a time, which the crate does.
- **Staleness.** How far an index is behind its files is the owner's to say, since only the owner
  lists its files. homma says when each file was last written, which needs nothing of the owner.
- **Meaning.** The member indexes are word indexes today (model `words`); the corpora carry
  vectors. The verb brings no embedder in this round and every index answers by its words, each
  report naming its model. Bringing one is left as a ticket: it puts an embedding runtime into
  homma's engine, a cost of its own to weigh.
- **Optional at build time too.** The index crate is private and homma may not be. The verb sits
  behind the engine's `search` feature, on by default, so a build without access to the crate
  turns it off and loses the verb and nothing else.

## Not this round

A corpus reusing the indexes of the corpora below it instead of walking their files again; a
dense arm across indexes of one model; an index that follows its files as they land.

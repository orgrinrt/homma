# The precondition has no type, which is why three rounds found three gaps

**Phase:** TOPIC
**Scope:** `homma-api`, `homma-core`, `homma-org`, `homma`

Four reviews, four refusals. The fourth was asked directly whether three rounds
introducing new instances of the class they were fixing had a structural cause or
was three coincidences. It has one, and it is the whole of this round:

> **the precondition has no type.** `Git` takes `&Path` on all seven methods;
> only one implementation of one method checks absoluteness, at runtime, and both
> fakes must hand-copy it, which is why both copies are dead. Every sibling
> method accepts a relative path silently... Until the trait boundary takes a
> type that cannot be relative, the next round will place the check somewhere new
> and the round after will find the gap somewhere else.

That is exactly right and it is the workspace's own rule, `harness-the-type-system.md`,
applied to a precondition that was left as a comment and then as a runtime check
in one place out of seven.

## The proof it was structural, found by the same review

The branch is named for a path that is not absolute reaching git. The previous
round fixed the route through `--config` and the route through the registry's
`workspace` field was still open:

```
$ homma org add r ... --workspace hands/rel
$ cd <a committed repository>
$ homma --config <absolute path> org up r
  workspace  hands/rel (cloned)
exit=0
$ git -C <that repository> status --porcelain
?? hands/          <- a nested repository in somebody else's tree
```

Deny item 2, by a field the round never looked at, with no guard and no test.
**Every integration test passes an absolute `--workspace`**, so nothing could
have caught it.

And the runtime check that was added is dead: replacing both fakes'
`assert!(path.is_absolute())` with `assert!(false)` fails **no tests**, because
`provision` never calls `enclosing_repo` and the one fixture that would reach the
`local` branch uses a URI instead. The previous round's summary claimed those
assertions meant "a fake that accepts what the real one refuses fails loudly".
They are unreachable.

## What this round does

**`AbsPath`, a path that cannot be relative, at the trait boundary.** Every `Git`
method takes one. A relative path then does not fail a check; it fails to compile.
The fakes need no assertion because there is nothing left to assert, which is the
difference between a discipline and a type.

A configured path becomes one by being **resolved against the workspace root**,
which is where a relative `workspace = "hands/rel"` was always meant to be
anchored and never was.

## The rest, and one of them is the fourth round of the same failure

**Five of seven mutation counts in the last summary were wrong.** The comment
carrying them said "here is the method rather than an assurance". It was neither.
Numbers in this round's summary are pasted from the command that produced them and
the command is named beside them.

**The security test does not pin the fix it was written for.** It asserts
`.failure()` without asserting why, so with the root resolution removed it still
passes on a different failure. It goes red only when two mechanisms are removed
together, which is not what it claims to guard.

**A third copy of `global_config_paths` was added by the round that fixed the
second copy.** And `local_smoke.rs` imports the shared module under
`#[allow(dead_code)]` and uses none of it, so "verified in both binaries" was one.

**`remote.rs` still fails open twice.** `.git` is stripped before a local path is
canonicalised, so a bare repository and the working tree beside it are one
repository; and splitting a host on `:` turns an IPv6 literal into `[`, so two
different hosts compare equal. It fails closed once more: the owner is folded and
the name beside it is not, so one correct workspace is refused permanently.

# agent-hooks-on-one-call-per-event

The agent hooks a session at the workspace root runs move onto a chain runner, one call per hook event,
the way the git hooks moved onto git-shook in round 202611270101. homma stops registering agent hooks of
its own: `homma agent regen` writes what it gathers as a manifest for claude-shook, the Claude Code front of
shook, and has that front register it.

## What the design says now, and what moves

The design, The agent hooks, says the host runs every hook registered for an event in parallel, so the
dispatcher git needs is not needed here and one registration per hook is what homma writes; a dispatcher
"would put a homma process in front of every tool call and serialise hooks the host already runs side by
side". The first half of that cost is real only of a dispatcher that is homma, which is a launcher that
may build the engine before it answers. claude-shook is a small binary of its own and the shook base a
POSIX script. The second half is the price this round pays on purpose: an event's entries run one after
another, in the chain's order, because one call per event whose order, conditions and error propagation
the chain runs is the point of the change, and the host's own parallel run buys an order nothing here
depends on in the other direction either.

What one registration per hook costs today is a bash process and three `jq` processes per hook on every
call the matcher lets through, most of them declining because the call lands in another repository. The
narrowing moves into the front: an entry names the directories it is for under `paths`, and the front reads
where the call lands once, by the same rules the wrappers read it, and runs only the entries it lands in.

## Where the base lives and which base a front runs

Settled here, as the review of git-shook 23c5ded asked before this job. The base is the `shook` script in
git-shook's repository, and the one implementation there is. A second implementation, when one is written,
lives in the same repository, is held to the same suite, and installs under the same name, so no front ever
chooses between two bases. A front finds the base by an order of its own that is only about which copy:
git-shook takes the `shook` beside its script, else the first on `PATH`, and copies it into the git
directory; claude-shook takes `SHOOK_BASE`, else the `shook` beside its binary, else the first on `PATH`.
claude-shook is Rust and lives in the same repository, as `claude-shook/`, beside the base it runs on and
the suite it is held to, and depends on nothing of homma.

## What claude-shook is

Recorded in its own README; what this round relies on:

- A manifest under the project's `.claude/shook/manifests/` holds an array per event of rows with `name`,
  `run` (an argument list), `matcher`, `paths`, `dir` and `timeout`. `{root}` in an argument is the project
  root, so a manifest naming programs under the project stays right when the project is moved.
- `claude-shook install` writes the entries and one registration per event into the project's
  `.claude/settings.local.json`, keeping every hook it did not write. A manifest it refuses leaves
  everything as it was.
- At a call it runs the entries whose matcher and paths take it, each in the session's directory unless
  `dir` says otherwise, with the payload replayed to each, and folds their answers as the host folds hooks
  run side by side. An entry exiting 2 blocks and stops the chain. One that fails another way or runs out
  of time is named to the person and the chain goes on.
- Where claude-shook is not on `PATH`, or no base is found, the registration says so in one line and the
  call goes ahead.

## Decision

- `homma agent regen` writes every agent hook it carries as a row of one manifest,
  `.claude/shook/manifests/homma.toml`, then runs `claude-shook install` at the workspace root. It writes
  no registration and no wrapper of its own.
  - A member's hook is a row named `<repo>--<hook>`, run as `<program words> {root}/<repo>/.claude/hooks/<hook>
    <argument words>`, with the member's directory under `paths` and the event and matcher its registration
    gave. A hook the member registers twice at one event is two rows.
  - A declared row is a row named `_declared--<slug>`, running `{root}/<run>`, with its `repos` under
    `paths`.
  - The workspace gate is a row, `_workspace--mockspace-gate`, at `PreToolUse` for `Bash`, running the gate
    script homma still writes under `.claude/hooks/`, since that script is the gate.
  - The nudges are one row per event, `_nudges`, running `homma agent nudge <Event>` from the workspace root.
  - The sweep of the git hooks from round 202611270155 is a row at `SessionStart`, `_git-hooks`, running
    `homma hook install` from the workspace root, so a session start puts back what a clone lost.
  - A member's and a declared row run through `{root}/tools/hookdedup/hookdedup run` where the workspace has
    that file executable, as the wrappers did.
  - Every row's timeout is the one its member's registration gave, else 600 seconds, the host's own default,
    so no hook that ran before is cut off by the move.
- A program or an argument that is a line of shell rather than words is refused as the runner already is:
  the row could only run it as something else. Quotes in a registration's arguments are refused the same
  way, since a row's argument list is split on whitespace.
- Before it writes anything the hooks stage asks for claude-shook on `PATH`. Where there is none, the stage
  refuses with one line saying to install it, and every registration, wrapper and file stays as it was, so
  a clone keeps the hooks it had. Only after `claude-shook install` has written its registrations does the
  regen sweep homma's own registrations from both settings files and its wrappers from `.claude/hooks/`.
- The sweep takes every registration of homma's shape, visited repository or not: nothing homma writes
  is registered by homma any more, so keeping an unvisited member's registration brings nothing back.
- Retired: the aggregated, declared and nudge wrappers, the scope check they carried, which is the front's
  `paths` now, and the registrations homma wrote.

## Landing order

Nothing moves for a running workspace until each step is in place:

1. git-shook `work/shook-chain-3` lands, and claude-shook is installed on `PATH` beside `shook`.
2. This lands on homma `dev`.
3. The next `homma agent regen` in a clone moves its hooks: it writes the manifest, claude-shook registers
   one call per event, and only then are the old registrations and wrappers swept. A clone whose regen runs
   before step 1 refuses the hooks stage and keeps the hooks it had.

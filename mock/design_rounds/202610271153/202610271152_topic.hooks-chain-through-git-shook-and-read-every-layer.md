# Hooks chain through git-shook and are read from every layer

Op, 27 October, verbatim: "We need to properly hook up git-shook as part of homma proper if not already so we can properly chain and easily expand the hooks"

The coordinator added, op's words, verbatim: "If mockspace needs anything added to support shook (it shouldn't, other than shipping an optional shook toml for the hooks it generates, which is easily generatable too) then that is also their work. And furthermore, homma.toml is not enough alone, we should map homma.*.toml I think"

The intent is in three parts. Hooks homma has a hand in reach git through git-shook, so they chain with every other tool's rather than competing for `core.hooksPath`. Adding a hook is a declaration in a toml and nothing else, so the hooks expand without touching code. And the declarations are read from every `homma.*.toml` the workspace has, not from `homma.toml` alone. The vehicles below are proposals.

## What exists today, as code and not as design

- `shook.toml` at homma's root declares `homma hook run pre-commit` and `pre-push` for `git shook install` to register. Its comment says the registration is optional and homma installs its own entrypoints into the common git directory's `hooks/` regardless (`shook.toml:1`).
- `hooks::reach` answers `Reach::Shook` when `core.hooksPath` is git-shook's dispatcher directory and reports the entrypoint as not reached, saying a manifest is the way in (`homma-core/src/hooks/install.rs`, `Reach::Shook` and `reach`). So with shook installed, `homma hook install` writes files nothing runs and exits non-zero.
- `shook.toml` is static. It names two events. `[hooks]` in `homma.toml` can name any of git's events, so an event added to the table has no registration until somebody edits `shook.toml` by hand, which is the opposite of expanding by declaring.
- git-shook discovers manifests with `git ls-files`, so only a tracked `shook.toml` is found (`git-shook`, `find_manifests`). A hook declared in `homma.local.toml` is per clone and untracked, and no tracked manifest can carry it.
- `Config` is read from `homma.toml` alone, `hooks` and `agent.hooks` included (`homma-core/src/config.rs`, `Config`). `Local` is `deny_unknown_fields` with `instance` and `tools` only (`homma-core/src/local.rs`, `Local`), so a `[hooks]` table in `homma.local.toml` is refused today.

## Layers: `homma.toml` and the files it names

`homma.toml` stays the workspace manifest and the only file that declares anything but hooks. Beside it, hooks, git and agent alike, are read from an ordered list of overlay files in the workspace root. Each overlay holds the same two tables the manifest holds for hooks, `[hooks]` and `[agent.hooks]`, and an overlay contributes to the event arrays and replaces nothing: the base entries run first, then each overlay's in list order. Appending is the only merge, so no layer can silence another's hook, and a clone's local file adds checks to the shared ones and never removes one.

Glob or declared list, decided: a declared list. `layers = ["homma.local.toml"]` in `homma.toml`, with that one value as the default when the key is absent. The reasoning, in the order it weighed:

- A hook is code that runs on every commit for everyone who has the file. A glob makes that set whatever happens to sit in the directory, so a stray `homma.bak.toml`, an editor's copy, or a file arriving through a merge changes what runs, with no step where anyone chose it. git-shook rules the same way for the same reason: discovery happens at install and never when a hook fires (git-shook README, "Why you install it once per clone").
- Order matters here, since entries run in layer order and stop at the first refusal. A glob orders by the alphabet, which is the thing git-shook's own `Ordering` section calls out as not an order anyone can reason about. A list is the order.
- A list is still a map of the `homma.*.toml` files, which is the part of the ask that holds: `homma hook doctor` lists every `homma.*.toml` in the root as read, or as present and not named. A stray is reported, never read.

A named overlay that is absent is skipped, since the ordinary case is a clone with no `homma.local.toml`. A named overlay that does not parse is an error naming the file, in the same words `Local::load` uses, because a hook silently dropped is worse than a refusal.

`homma.local.toml` has its own reader with its own tables. The layered reader takes `hooks` and `agent` out of any overlay and ignores the rest, which belongs to whichever reader owns that file; `Local` gains the two keys as untyped values so `deny_unknown_fields` accepts a file carrying them, the way `Config` carries `paths` and `org` for `homma_api::Workspace`. An overlay that is not `homma.local.toml` and carries any other table is refused naming the table, since nothing reads it and silent is the failure.

The set and order are `homma.toml` first, then `layers` in order. That is the list the workspace's `auto-regen` helper watches as sources for the agent surfaces, so it is sent to it on the channel.

## git-shook: a manifest in the git directory

git-shook gains a second place to find manifests: `<git-common-dir>/shook/manifests/*.toml`, read by `install` and `doctor` beside the tracked ones. It is local to the clone like the registry it feeds, it needs the operator to run `install` to take effect, and it runs from the repository root. This is what a tracked file cannot do, and the only way a per-clone declaration reaches the dispatcher without a flag or a registry hand-edit.

homma generates exactly one such file, `homma.toml` under that directory, naming `homma hook run <event>` for every event the merged table names, from every layer. That is how a hook declared only in `homma.local.toml` is installed and runs: the layers decide which events have an entry, the entry calls `homma hook run`, and `homma hook run` reads the layers again at fire time to decide what the event runs. The repository's tracked `shook.toml` stays as the static, shareable declaration for the two events a plain clone needs, and the generated manifest carries the same name so the registry has one `homma` entry per event and not two.

What `homma hook install` does by `Reach`:

- `Direct` and `Chained`: as today, an entrypoint in the common git directory's `hooks/`.
- `Shook`: write the generated manifest, then run `git shook install --yes`, since the operator running `homma hook install` is the consent git-shook asks for, and report the entries as reached.
- Any other path, `Foreign` or `Missing`: as today.

mockspace chains through its own durable gate, which sets `core.hooksPath` to its own directory, and that is a separate owner. Whether mockspace registers on git-shook instead is the mockspace part below.

## mockspace

Not changed in this round of homma's design. mockspace's own change, an optional `shook.toml` for the hooks it generates, is carried in `hiisi-digital/mockspace` on `work/homma-shook`, with `src/agent_builtin/` updated beside it. This document records only that homma's `Reach::Chained` keeps working while that lands: a repository with mockspace's gate still reaches the entrypoint through it.

## Open points

- Whether `homma hook install` should call `git shook install` itself or print the command. Chosen: call it with `--yes`, because the verb is the operator's explicit act and a printed command left half the install undone on every `Shook` repository.
- `git-shook` stays dependency-light POSIX shell; the manifest directory is a new reading path, not a new format.

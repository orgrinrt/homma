# the-rules-half-is-behind-the-skills-half

The corpus round landed two halves of one job, rules and skills, and the skills
half is finished in two places the rules half is not. Both gaps were found by a
reviewer reading the two files against each other rather than by anything the
suite could report, which is the shape worth naming: the rules code is not
wrong on its own terms, it is missing what its own sibling already decided.

The first is the list parser. `parse_list` splits on every comma, and `paths`
is the field that carries globs, where a brace group is the ordinary way to
write one. `"src/**/*.{ts,tsx}"` becomes two entries with unbalanced quotes,
and the card generated from them declares two patterns matching nothing rather
than one matching something. The scalar side of the same parser has a test for
a colon inside a value; the list side has none, and both fixtures feed lists
with no comma in any element, which is setup that only feeds what the
implementation handles.

The second is reaping. `render_cards` creates the destination and writes one
file per rule, and nothing anywhere removes a card whose rule is gone. The
destination is the always-loaded corpus, so a deleted or renamed rule keeps
being injected into every session with nothing reporting it. The skills side of
the same pull request removes each skill's generated directory before writing
it and reports the directories no authored skill claims, with tests for both,
and the rules side has neither the behaviour nor the tests.

The question the round settles is what the rules half owes to match, and in
particular whether the deleted-rule case is the skills side's remove-what-we-own
case or its report-what-we-do-not case, since a flat file has no directory to
own and the destination holds files this pass never wrote.

# The aggregation pass is denied the one workspace it exists for

**Date:** 2026-08-24
**Phase:** TOPIC
**Scope:** `homma-api`'s deny list, and `agent regen`'s use of it

A review of the branch found `homma agent regen` refused in the workspace the
shipped configuration names. This is the record of what is wrong and what the
fix is.

## What happens

`denied_for_aggregating` starts from `Denied::from_env`, which carries two
home-derived entries: the harness's own `.claude`, and `<home>/Dev/clause-dev`,
denied because the central clone is read and never written.

It then walks the registry and adds every participant's workspace, skipping the
one being written into, because that one is the actor's own. The doc comment
above the function states the reasoning in exactly those terms: the central
clone is one participant's workspace, denied to every other and permitted to its
owner.

The skip applies only to the registry-derived entries. The home-derived
`Dev/clause-dev` is not reached by it, so aggregating into that workspace is
refused by an entry describing it as somebody else's. Reproduced against the
real API:

    ".../Dev/clause-dev/.claude is under .../Dev/clause-dev, and nothing may be
    written there: the central clone is read, never written."

That is the configuration this workspace ships. The pass has been unable to run
in it.

## Why the test did not catch it

`a_participant_may_aggregate_into_their_own_workspace` is the test for this
case. Its fixture puts the workspace at `dir/mine`, and the only path the
home-derived list hard-codes is `<home>/Dev/clause-dev`, so the fixture cannot
enter the branch its own comment describes.

It also asserts only that one sentence is absent from stderr, and never that the
run succeeded or wrote anything, so it passes when regen fails for any other
reason at all.

## The shape of the fix

The permission is a property of the workspace being written into, not of where
the entry came from, so it belongs beside the entries rather than in the loop
that adds some of them.

`Denied` grows a way to drop an entry denoting the same place as a given path,
and it compares the same two ways `check` does. A denied place spelled through a
firmlink, or spelled with different case on a folding filesystem, is the same
place, and a permission that missed either would leave the refusal standing
under a spelling nobody typed.

Same place, not under it. An entry *inside* the workspace stays denied: the
harness's own `.claude` under a home that happens to be the workspace is still
the harness's.

## What the test becomes

Pointed at `<home>/Dev/clause-dev`, which is the only path that reaches the
branch, and asserting the run succeeded and wrote a wrapper rather than
asserting one sentence is absent. It fails before the fix, which is the finding.

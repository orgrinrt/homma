# The milestone tests can fail on what they name

The second review of `work/homma-milestone` at `5c06fac` found two tests that cannot fail on the property they name, and a list of smaller defects, each verified by mutation. This round makes the tests fail when the property goes, and takes the coordinator's call on which files a stand-in is read from.

The calls, with the options each chose among:

- Which files stand-ins are read in. Options: every file but documents (the round before, which read research toml, patches and design round histories), source files only (which would miss the `# FIXME(stand-in)` lines kaski keeps in `content/*.toml`), or everything but a named set of places. The coordinator's call, taken: nothing under `mock/research/` or `mock/design_rounds/`, no `.patch` and no `.history` is read; documents are not read; every other file, data and configuration included, is. Two arms, not one policy.
- The comment anchor of a block comment continuation. Options: any line starting with `*` (reads `*self.relaxed = true;` as a comment), or a `*` followed by a space. The second.
- Which `git merge-base` outcomes are `unrelated`. Options: any failure, or exit 1 only. Exit 1 only; any other failure is `unreadable` with git's words.
- Where `base` reads the record. Options: the working tree (a clone checked out on a branch answers with that branch's record), or the trunk's committed file. The trunk's.
- How the `unreadable` call is tested. Options: a fixture that makes git fail (none was found: a binary conflict and a criss-cross both exit 1), or the classification of git's exit as a function tested with a synthetic 128, plus a shim of `git` on the path of the binary that fails one subcommand. Both of the second.

The deep dive's introduction says four reports and lists three, which it corrects. The skill text in the content repository gets the two new calls and the cost of `branches` on a repository with many branches, in a pull request there. The three older open topics need nothing from this round.

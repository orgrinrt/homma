# a-cut-write-is-recovered-only-where-nothing-whole-is-dropped

## What review found

Round `202610091645` made `cut::ending` read, from a line that does not parse
whole, the first object from which the rest of the line is one object, and drop
the bytes before it, refusing only when those bytes parse as a whole value. Read
by the reviewer against the code, that check is too wide in two ways, and both
were confirmed by reading `mock/crates/homma-engine/src/cmd/capture/cut.rs`
before this round was opened.

- Three whole lines run together are recovered as the third. The bytes before the
  last object are two whole values side by side, which `serde_json` refuses as
  trailing characters, so the check that was meant to refuse them sees an error
  and lets the line through. Two whole lines were the only case it refused.
- A whole line, then a cut write, then a whole line is recovered as the last one,
  dropping the first, for the same reason: the bytes before the object begin with
  a complete value and then something cut, and that is an error too.

Both drop a complete record, which can be the person's words, behind a notice
that reports bytes and nothing else. The test written for the one byte case used
`x` in front of the object, and so pinned the wide check: text that is not the
start of an object is recovered too.

## The rule

A line is read as the object that ends it when the bytes before the object begin
with `{` and the parser, given those bytes alone, fails because the input ended.
Nothing else is a cut write. A prefix that is a whole value, a whole value
followed by more, text that is not an object's start, and a prefix the parser
refuses for a reason other than its end all stay refused by number.

serde_json says which it is: the error on the prefix has a category, and the end
of input is `Error::is_eof()`. Complete lines run together fail with trailing
characters, which is a syntax error, and a cut write fails with end of input, so
the one test separates them without counting objects.

The options were: keep the guard and add the missing cases by listing them;
count the whole values in the prefix; or read the prefix's failure. The first
lists what is wrong instead of what is allowed, the second needs a second parser
over the prefix, and the third states what a cut write is.

## The scan

The scan tried every `{` by parsing the rest of the line into a `Value`, which
builds the whole tree of each candidate that parses. It only needs to know
whether a candidate parses, so it asks `serde::de::IgnoredAny`, which checks the
syntax and keeps nothing, and the one object it chooses is parsed into a `Value`
afterwards.

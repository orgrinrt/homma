# an-answer-whose-question-was-cut-is-never-lost

## What review found

An ask round is read off a tool result only when the `tool_use_id` on its content
block names a call to `AskUserQuestion` found on an earlier assistant line
(`mock/crates/homma-engine/src/cmd/capture/transcript.rs`, `answers_an_ask`, and
`mock/DESIGN.md.tmpl` where it says "and only then"). Before round
`202610091645` that was safe, because a call was always on a line of its own.
With a cut write read as the object that ends its line, the assistant line that
carries the call can be the one that was cut, and the answer on a later whole line
then names a call nobody holds. It is skipped, with no refusal and no word, and
what the person said in answering is not in the capture.

That is the failure the reader's own module documentation names as the reason to
refuse rather than pass over: it drops the person's words without a trace.

## What the real session shows

Read off the transcript of the session that failed, through `jq`: its answered
asks all have `toolUseResult` as an object with `questions` and `answers`, and the
rest are the harness's strings for a rejected or abandoned ask. One tool result in
the main conversation names a call that is on no assistant line, and it is the
result of launching a sub-agent, with `agentId`, `status` and `prompt` in it and no
`questions`. No answer lacks its question in that file, so the case the cut write
makes possible is not one the file holds. That was an uncommitted `jq` run over a
file that is still growing, no committed probe stands behind it, and no figure
from it is written here.

The shape of an ask result is therefore the harness's own and stable enough to
recognise: `toolUseResult` is an object, `questions` is an array of objects with
`question`, `header`, `multiSelect` and `options`, `answers` is an object keyed by
the question text, and `annotations` may be there.

## The decision

The coordinating agent decided, in the brief for this round and not as the
person's word, that the person's answers are never lost. The design carries that
as follows.

- A tool result that names a call which some earlier line holds as a call to any
  tool other than `AskUserQuestion` is not read, whatever keys it has. That stays
  as it was, and it needs the reader to remember every call it has seen, not only
  the asks.
- A tool result that names a call no earlier line holds is read as a round when
  its own `toolUseResult` is an object that has `questions` or `answers` and the
  round reads from it as strictly as any other. The run says so on stderr, naming
  the line, since a result is being read without its call.
- When it has either key and cannot be read as a round, nothing of it is read, it
  is not a refusal, and the run says on stderr which line holds it and that its
  words are not in the capture. A refusal would stop a capture over a line the
  reader cannot tell is an answer; saying so keeps the loss in the output.
- A result of an unknown call with neither key is nobody's words and passes
  without a word, as the sub-agent launch in the real session does.

The options were: leave it, which loses the answer silently; refuse the whole
capture on any result of an unknown call, which stops a capture over results that
are nothing to do with the person; read by shape and say so; and say so only.
Reading by shape recovers the words, and saying so is what the other three had in
common. The first and last of the four were rejected for losing the words, the
second for the reach of its refusal.

What this reverses is a deliberate rule, pinned by
`only_a_result_answering_an_ask_call_is_read_as_a_round`, whose last assertions
said a round whose call the transcript never shows is not read either. That one
assertion changes, and the rest of the test stays: another tool's result is still
not a round.

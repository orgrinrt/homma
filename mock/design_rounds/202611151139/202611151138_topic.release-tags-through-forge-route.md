# release-tags-through-forge-route

## Current state

`homma release run` makes the tag with `git tag -a` and pushes it with `git push` (step 6), and makes the forge release through the forge's token client (step 7). In a cloud session the git proxy refuses every tag push with HTTP 403, and no forge token is handed to the session, so a release run there stops at step 6 after the merge to `main` is pushed: the release is half done, with no tag and no forge release. The workspace has several releases standing like that.

## Op's words

Op, 15 November 2026, verbatim: "Also make sure that everyone knows via rules or clear tooling in clause-dev how to push the tags needed and remove branches, when attempting those outside the existing tooling. Or point to existing tooling so nobody attempts to do things that require those actions manually. Then make sure all the tooling that needs it uses it, namely, release always wants a tag and we already have several releases without a tag or a release on GitHub ..."

And the same day: "there's no gh cli available in cloud or it is heavily restricted there, so any gh cli calls should be optional predicated on it existing, and on error or failure or miss, so a fallback if the forge write key exists, through it. Never fail, always try fallbacks until works, scripted, silent as possible not to waste tokens etc".

The intent: a release always gets its annotated tag and its forge release, from a cloud session too, by the one chain of routes the workspace keeps for those writes, and never by a route of its own beside it.

## Changes proposed

The workspace's manifest names the command every tag, release and remote branch deletion goes through, `forge_route` under `[paths]`, a path from the workspace root. The workspace's command tries `gh` where it is on the system, then git, then the console's forge Worker, and moves on from any route that fails; homma does not mirror that order in its own code, it calls the command, so the order is kept in one place.

Where the key is set, step 6 asks that command for the tag, `forge_route tag <repo root> <tag> <sha> <tag>`, and step 7 asks it for the release, `forge_route release <repo root> <tag>`, with the changelog block as `FR_NOTES` for the route that takes a body. The command makes a tag the remote already holds on that commit a success, and a release that exists one too, so a rerun after a half-done release finishes it. Where the key is not set, a workspace with no such command, steps 6 and 7 are what they are today: the tag made and pushed with git, the release through the forge client.

The key is read as the manifest's other paths are, contained in the workspace root, and the command is run through the release's `Runner`, so the suite can see exactly what was asked and prove the git push of the tag never ran.

`homma release check` cannot yet name a version tag the remote holds with no forge release on it: the `Forge` trait has no read of releases. That id, and the read it needs, are a ticket rather than part of this round.

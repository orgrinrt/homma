# The launcher owns the name, so the engine gives it up

**Date:** 2026-08-24
**Phase:** TOPIC
**Scope:** `homma` (the binary crate), and a new package outside `mock/`

## What is being built

`homma` gets the same launcher `mock` has. A thin published binary resolves the
engine this workspace pins, builds it once per version into a shared cache, and
runs it with an absolute working directory from wherever it was invoked.

The launcher machinery is `renki` and none of it is written here. What is
written here is a const descriptor naming this tool's config file, pin keys and
cache namespace, and a two-line entry that hands it to `renki::run`.

## Why the engine has to be renamed

`renki` runs the binary named by the descriptor's `engine_crate`, and the
launcher installs under `launcher_crate`. Those are two different binaries and
they cannot share a name.

`mockspace` never had to decide this because its two names already differed: the
engine package is `mockspace`, the launcher is `cargo-mock` installing as `mock`.
Here the engine package is `homma` producing a binary called `homma`, and
`homma` is exactly the name an operator types, so the launcher must own it.

So the engine becomes `homma-engine` and the launcher becomes `homma`. That
mirrors the shape `mockspace` already has rather than inventing a second one:
the engine stays unpublished, and the launcher is the one crate in the repo that
publishes, because it is the thing anybody installs.

## What the anchor buys, which is more than it looks

`renki` has an `Anchor::ConfigFile` variant that no consumer uses yet, and its
own documentation describes this tool:

> Right for a tool whose config sits above a pile of repositories rather than
> inside one. Anchoring on `.git` would stop at the first repository walking up
> and never reach the config.

Today `homma` reads `./homma.toml` and therefore works from the workspace root
and nowhere else. Under this anchor it walks up to the config from anywhere,
including from inside a member clone, which is where the operator actually is
most of the time. That composes with the absolute anchoring `from_path` already
does, so a config found three directories up still yields absolute member paths.

## The claim this round makes and has to test

**No hooks.** `mockspace` needs six, for a lint-rules dependency pinned to the
engine's revision, a durable git-hook gate, a retired alias to refuse, and a
legacy lock pin. None of that is this tool's, and if it needs none then the
extraction did what it was for.

A hook turning out to be necessary is a finding, not a defeat, and it goes in as
a named hook rather than as a line inside `renki`.

## What is decided here rather than derived

`homma.toml` gains a pin. `renki` already fixes the key shape from the
descriptor's `pin_prefix`, so what is left is which ref this workspace tracks,
and `dev` is what every repo here already tracks in practice.

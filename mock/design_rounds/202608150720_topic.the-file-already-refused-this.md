# The file already refused this, in the same test module

Fifth review. Sixteen mutations run against the diff and all sixteen caught, the
class grep from the previous round confirmed complete, no tautologies, spec
parity on both units. The engineering is in good shape.

And then the round's own regression, which is the worst kind available: the thing
it did had already been considered and refused, in the same file, by an earlier
round of this same branch.

`git_impl.rs:502` says:

> Snapshotted rather than redirected. Mutating the environment to point the
> global config elsewhere is racy across test threads and needs an unsafe call;
> the requirement is that the real global file does not change, so that is what
> is asserted, directly.

The previous round set `GIT_CONFIG_GLOBAL` with an `unsafe` block, 140 lines
above that paragraph, to fix a different test. It did not read it. The changelist
does not mention the conflict.

## The race is real and the SAFETY note is false twice

`testing.rs:15` reads `GIT_CONFIG_GLOBAL`, and `the_identity_is_written_to_the_local_config_file_and_nowhere_else`
calls it, in the same binary, which libtest runs on many threads. When the
variable is live for one snapshot and dead for the other, that test fails
comparing a global config that "changed".

The note claims a single-threaded test: the binary holds seventy-two tests. It
claims `gix` reads the variable only when opening a repository: `testing.rs`
reads it, and `std::process::Command` snapshots the parent environment for every
`git` child.

And `remove_var` after the assertions is not unwind-safe. A failure anywhere
between leaves the variable pointing at a deleted temporary directory for every
later test in the process.

## The fix is placement rather than synchronisation

The guard is load-bearing. The reviewer confirmed by mutation that this test is
the **only** thing catching `identity` switching to the merged view, so deleting
it is not available.

An integration test is its own binary and its own process, so a variable set
there races with nothing. That is the reviewer's suggestion and it is better than
a lock, because it makes the race unexpressible rather than merely avoided.

## The gate that still has one escape

The struct literal forces a new field to be given a value, and every value in
that entry must carry a control character. Both were verified. What neither
catches is `None`: `E0063` is satisfied, `skip_serializing_if` removes the field
from the serialised value, and the hostile-value check never sees it.

So the third iteration of this guard shipped a third wrong absolute, in the PR
body and in the changelist. What closes it is the compile-time enumeration the
previous round deleted, kept **alongside** the literal rather than instead of it:
naming every field forces a classification, the literal forces a value, and the
hostile-value assertion forces that value to be hostile. A field added as `None`
then has to be named, and naming it in the free-form list makes the reported set
disagree.

The `_` patterns go with it. A field can still be classified wrongly on purpose,
which is the bar; it can no longer be classified by omission.

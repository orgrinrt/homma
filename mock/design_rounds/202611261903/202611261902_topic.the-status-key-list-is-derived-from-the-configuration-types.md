# the-status-key-list-is-derived-from-the-configuration-types

# The status key list is derived from the configuration types

## The ask

The status lists, under `reads`, the manifest keys an older engine refuses, from a constant kept by hand beside the configuration types. A later key that an older engine refuses can be added to a table with nothing failing when the constant is not touched, and the list then tells a reader that an engine does not read a key it reads. A review asked for the list derived from the configuration types, or a test that fails when the two differ.

## What the list is for

The list answers one question by command: does the running engine read a given key. A manifest sets a new key only once every engine reading it answers yes. A list of only the newest keys answers it only for keys someone remembered to put there, and it must be pruned by hand when no engine in use predates them, so it can go wrong in two directions.

Decision: `reads` lists every key this engine reads, derived from the types that read the manifest. A key added to any of those types is listed with no other edit, and nothing leaves it. The question is still answered by asking whether the key is in the list; an engine older than the list prints none, as before.

Options weighed:
- Keep the constant and add a test that compares it with the keys the types read less a frozen list of keys every engine in use knew. The frozen list is hand kept too and grows the constant forever with every key, so it is the whole list by another route with two hand-kept lists.
- Derive the whole list (taken).

## How the keys are found

A serde type says the names of its fields when it is deserialised: the derive passes them to `deserialize_struct`. A deserialiser that records those names and descends into every field's value, naming a map's keys `*`, an array's elements by the array's own name and an option by what it holds, reads every key a type reads without a manifest at all. Fields skipped on read are not passed, so they are not listed, which is right.

Where a field's type asks for whatever value is there (`deserialize_any`: a `toml::Value`, an untagged enum), the probe cannot see its shape; it records the key as read and does not descend. The configuration holds several tables as `toml::Value` because a second parser, the api's, reads them; so the list for a manifest is the probe of `Config`, with each of those tables replaced by the probe of the api type that reads it: the workspace catalogue type for `paths`, `org`, `offices`, `lease`, `deny` and `content_repo`, and the search, summary and ask types under their tables.

A key whose value the probe cannot see is a hole in the list only if it is a table whose keys an engine refuses. The test that keeps that true: the derived list's opaque keys are a fixed, named set, so a new `toml::Value` table, or a type that reads any value, fails the test until the api type that reads it is grafted in or the key is named as a value, not a table. Its failing control: drop one graft and the test fails on that table's name.

Options weighed for the probe:
- `serde-reflection`, which traces a type's format the same way. It refuses `deserialize_any`, which the configuration needs at seven tables, and its default values fail a checked type such as the workspace name, so each needs a sample. A probe of its own is about a hundred and fifty lines and handles both.
- The probe in homma-api (taken), where the configuration types live; the core graft beside `Config`, which knows which api type reads which table.

## The human output

The list is long once it is whole. The human output says how many keys the engine reads and that the document lists them; the document carries the whole list. The precondition check against the document is unchanged.

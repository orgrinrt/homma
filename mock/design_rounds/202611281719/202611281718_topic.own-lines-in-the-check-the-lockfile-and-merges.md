# own-lines-in-the-check-the-lockfile-and-merges

## The ask

The review of round 202611281607 (`.shared/research/202611281710_review-of-four-ready-branches/README.md`
on the workspace's `main`, section 4) handed it back with three findings. Op
answered the route question in between, "Own line stands", so its finding 2
is void.

1. `release check` never reads an own line's tag: `tag.reachable`,
   `tag.annotated`, `tag.pushed`, `tag.sha.agrees` and `tag.local` run over
   the repo's version tags alone, and the design said so ("the checks over
   the repo's tags leave own lines out"). A release tag sits on `main` only
   and the check names each violation, so an own tag off `main`, lightweight
   or unpushed must be named too.
2. A repo that commits its `Cargo.lock` changes it when an own line's version
   is moved by hand, so the commit touches something outside the own lines'
   directories and a release of own lines alone always refuses.
3. With a pathspec, `git log` simplifies history and drops a merge that is
   the same as one of its parents for those paths, so a pull request's merge
   subject and number leave the repo's block wherever the repo has own lines.

## Taken

Every release tag is checked as a release tag, the repo's and each own line's
alike: on `main`, annotated, pushed, at the same commit on the remote, and
fetched. `tag.dupes` names two tags of one line on one commit; the repo's tag
and own lines' tags on the one merge a release makes are what that release is,
not duplicates.

Which line a commit belongs to is read off what it changed: a commit's paths
against its first parent, so a merge counts by what it brought onto the line it
was merged into, as it does without a pathspec. A commit touching anything
outside the own lines' directories is the repo's; one touching an own line's
directory is that line's; one touching both is both. The root `Cargo.lock` is
the one file outside them that an own line's move changes by itself: a change
to it counts for the repo's line only where it changes a package that is not
on an own line, read by comparing the lock before and after with the own
lines' packages and the references to them taken out. A lock change that only
follows an own line's version is that line's alone.

Options weighed:
- `--full-history` on the pathspec walk: it keeps merges that differ from
  every parent, and still drops a merge whose change came whole from its
  second parent, which is the shape of a pull request.
- Leaving `Cargo.lock` out of the repo's line altogether: a dependency bump
  that only moves the lock is unreleased work on the repo's line and would go
  unsaid.
- The commit's own paths against its first parent, and the lock read by
  package (taken).

## What the design says

The deep dive's section on own lines: the check sentence is replaced by the
tag checks over every release tag and the `tag.dupes` reading; the repo's line
is read per commit against its first parent, and the lockfile rule is added.
The check section's `tag.dupes` line names the one merge of a release.

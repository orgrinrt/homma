# The machine answered the test, and nobody checked how git resolves a name

The exit test written to prove that configuration reaches a commit was answered
by the machine it ran on. Reproduced here rather than taken on the reviewer's
word: with **both** author writes deleted, so homma configures no author address
at all, the test still passes.

It asserts `%ae == "ort@hiisi.digital"`. That is this machine's global
`user.email`. The author half of the assertion measures nothing homma does.

The round that shipped it said, in its own topic file, that asserting the commit
rather than the config was the whole point, because "config that never reaches a
commit is the defect this exists to prevent". It then wrote a test that cannot
tell the difference.

## The root, which is one thing and produces three findings

**Nobody checked how git actually resolves an identity.** Three consequences,
each verified by the reviewer and each a real hole:

**A global `author.email` beats a local `user.email`.** So the `author.email`
write is not redundant, it is the only thing defending the case the trait's own
documentation claims to cover. It is also pinned by nothing: deleting it leaves
all 364 tests green.

**`author.name` and `committer.name` are never written, and a global one
overrides the local `user.name`.** On a machine carrying those, a provisioned
workspace commits under a name homma did not configure, and `provision`'s
read-back reports success. That is precisely what the trait documentation says
cannot happen.

**The read-back is half-blind.** `Git::identity` still returns only
`user.name` and `user.email`, so a `set_identity` writing the committer nowhere
passes it. The write half was widened and the read half was not, in a guard whose
own comment says it exists because a write that never reached disk survived a
round.

## And a class rather than a row

`committer_email` was added without reaching `unsafe_strings`, which is the
registry's control-character check. The test written to prevent exactly that
recurrence, `every_field_that_reaches_generated_output_is_checked`, is a
hand-written enumeration, so it could not see the field that slipped past it.

Its own comment says it exists because dropping fields "left the whole suite
green". The second occurrence went the same way, one iteration later, past the
test written for the first.

**So the fix is the mechanism rather than a tenth row.** A check derived from the
serialised form sees every field, including the ones nobody has added yet.

## The unit was under-built as well

U-3.2's Produces names an optional committer **name and email**. Only the email
shipped, git expresses `committer.name` as a first-class key, and nothing in the
round recorded a reason. That is a divergence from the unit rather than a
decision.

## One for op rather than for this round

The reviewer flagged `README.md`'s "setting the git identity inside that clone",
singular, where this branch's headline is that one clone carries two. Not false,
so not a blocker, and it is a taste call about how much the Status section
tracks. It goes to op rather than being settled by silence.

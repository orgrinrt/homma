# A negative answer is only evidence if a positive one was possible

`verify --forge` asks each forge whether a repo is there under the owner and
name the manifest gives it. It is the only check that sees a wrong `owner`,
which is why it was added: four entries in this workspace's own manifest sat
wrong for weeks, and the rules table grew the same four errors independently,
and neither caught the other.

The first run of it reported all twenty-four repos absent. Every repo here is
private, and GitHub answers `404` for a private repo exactly as it does for one
that is not there, so an unauthenticated question cannot tell the two apart.
The check was gated on a token being present, and that fixed the run.

A review of that gate found it covers one of four ways the question goes
unanswerable, and the remaining three all reproduce the original failure with a
token set.

## What a token being present does not establish

An expired token, a revoked token, a token belonging to another account, and a
token without the scope to see private repositories all produce the same `404`
that no token produces. So `has_a_token` answers "is there a credential" when
the question is "could this credential have seen the repo if it were there".

The fix is to make the forge answer that question directly, before any repo is
asked about. `GET /user` is the endpoint both forges answer only for a
credential they accept: `401` is the rejection, and `403` counts as accepted,
because it says the credential was recognised and the account is not permitted,
which is a different problem than the one being asked about.

That turns one silent failure into three findings that name different things to
go and fix: no token in the environment, a token the forge rejects, and a forge
that could not be reached to ask.

## The redirect, which is the same defect arriving by another route

GitHub answers `301` for a repository that has been renamed, redirecting to
`/repositories/{id}` on the same host. `ureq` defaults to dropping the
`Authorization` header on every redirect, so the followed request arrives
anonymous, a private repository answers `404` to it, and the answer comes back
as "not there".

A rename is the ordinary reason an owner or a name goes stale, so this is the
motivating case for the whole check rather than an edge of it. One repository in
this workspace's own table was renamed upstream this week.

`SameHost` is the setting that keeps the credential where the redirect stays on
the host it was issued for and drops it where it does not, which is the property
worth having rather than `Always`.

## Why none of it was catchable

The two branches that matter, a repo reported absent and a credential the forge
rejects, were reachable only against the live API, because the function built
its client inline. So the only test that existed pointed at a closed port and
proved that `--forge` reaches *something*: it could not distinguish an
implementation that reports the defect from one that can only ever warn.

Taking the client as a parameter is the change that makes the rest testable, and
it is the defect underneath the missing tests rather than a convenience.

## The forge nothing uses

The token warning ran over every declared forge profile. This workspace declares
`codeberg` and no repository names it, so a run without that variable warned
about a forge nothing was going to ask about. That is the same noise the
`local_path` warning was removed for, arriving on a different axis, and the
answer is the same: only forges some repository actually references.

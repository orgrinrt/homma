# capture-reads-the-object-that-ends-a-cut-line

## What happened

`homma capture` stopped with `error: transcript line 39105 is not JSON: expected
`,` or `}` at line 1 column 1422` on the transcript of the session that was
running it, so no capture of that session could be made. Four lines of that
file fail to parse as a whole: 39105, 41831, 48752 and 83343 of 84280. Each is
the start of one JSON object cut off inside a string, with a complete object
following on the same line, and each complete object begins `{"parentUuid"` and
parses on its own. The cut heads are 1419, 431, 3878 and 562 bytes long. Three
of them are assistant or tool result lines of the harness and one is a
`queue-operation` enqueue; none of the four is shown by its visible part to be a
line the person typed, though a cut head hides whatever came after the cut.

The shape is two writers appending to one file at once: the first write is
interrupted after part of its bytes, the second lands whole, and the newline
that would have ended the first never comes. The harness writes lines of several
megabytes, which is where an interrupted write is likely, and the transcript of a
long session holds many of them. Nothing in this repository writes that file.

## What the design says

The design is the stand-in for a canon here, since `mockspace.toml` names no
`canon_paths` and the generated `canon-design-code-chain.md` says so at line 25.
It is silent on a line in the middle of a transcript that will not parse. What it
does say about reading the transcript:

- `mock/DESIGN.md.tmpl:188` says a last line with no newline is still being
  written and is not read. That is the unterminated final line, which is not
  this defect: the four lines here all end in a newline.
- `mock/DESIGN.md.tmpl:247` says a `through` the transcript does not hold is
  refused rather than guessed around. That is the watermark, and a recovered
  line keeps its `uuid`, so the watermark still finds it.
- `mock/design_rounds/202609241737/202609241729_topic.capture-what-op-says.md:53`
  says the parser refuses what it does not recognise by name rather than
  guessing. That sentence is about the shapes of lines the harness writes, a
  `type`, an `origin`, a `toolUseResult`. A complete object at the end of a line
  is recognised by name like any other line, and taking it guesses at nothing.
- `mock/crates/homma-engine/src/cmd/capture/transcript.rs:11` is the code
  stating why a line of a read shape with a field missing is refused by number:
  passing over it would drop the person's words without a trace. That is a claim
  about the code and the reason it gives is the one to keep.
- `mock/crates/homma-engine/src/cmd/capture/tests/transcript.rs:171` is the test
  that a line which is not JSON is refused by its number. It pins what the code
  does and is not a statement of the design.

Nothing found requires a capture to be refused whole when a line is cut. Silence
is not permission, and the decision below is the person's own instruction for
this defect, recorded as a proposal for the design to carry and not read out of
the canon.

## Options

The choice was among five, recorded so the decision can be read without the
conversation that made it:

1. Keep refusing, so a session with one cut line can never be captured. That is
   the defect.
2. Skip the whole line and say so. Cheap, and it also drops the complete object
   the line carries, which can be the person's words.
3. Read the last complete object on the line, drop the bytes before it, and say
   on stderr which line and how many bytes. A line with no complete object
   ending it is refused by its number as now.
4. Read every complete object on a line. Asks for a shape nobody has seen: the
   four real lines hold one cut head and one whole object.
5. Repair the transcript in place. The file is the harness's and is read only.

## Decision

Option 3. `transcript::read` takes a line that does not parse as a whole and
looks for the earliest `{` from which the rest of the line is one JSON object;
that object is the line. The count of bytes before it is reported with the
line's number on stderr by `run`, one notice a line recovered, so the cost of the
recovery is visible on every run that meets the line and the capture's stdout
stays the report that something parses.

A line is not recovered in two cases, and both stay refused by number.

- No `{` on it starts an object that runs to the end of the line, which is the
  line that is simply not JSON.
- The bytes before the object are a whole JSON value themselves. That is two
  complete lines run together, not a write that was cut, and reading only the
  second would drop a complete record without anything in the cut shape to
  explain it.

What was in the dropped bytes is not in the capture, and cannot be: a cut head
may have been a line the person typed, and its words are gone from the
transcript itself. The notice is the trace. The recovered object is read as an
ordinary line, with its own `uuid` in the watermark, its own type and its place
in the file's order.

## The tools' own record

`typed.rs` reads `<session>.typed-by-tools.ndjson`, and it does not take the
same recovery. Its only writer is `tools/self-compact/hooks/self-compact-inject.sh`
in the workspace repository, which appends one `jq -nc` object a call, a line
of well under a kilobyte, from the one process injecting for that session. That
is not the harness's megabyte lines written by several writers, and no cut head
has been seen in it. The consequence of skipping a record there is also the
reverse of the transcript's: a record dropped leaves a tool's typed line to be
quoted as the person's, which `mock/DESIGN.md.tmpl` already calls visible in the
file. So a record that will not parse stays refused by its number. A test pins
that, so a later reading of this round does not carry the recovery across
because the two readers look alike.

## Correction: the file does not show a second writer

The first section says the shape is two writers appending at once and that the
harness writes lines of several megabytes. Checked against the transcript before
the doc changelist was locked, neither holds up, and the section stays as it was
written, as the record of what was believed.

- The longest line in the file is 1362496 bytes, from
  `awk '{ if (length($0) > m) m = length($0) } END { print m }'`, so lines of
  several megabytes are not what the file holds.
- The ids of the two cut assistant messages, `msg_011Cffd2AKKs3Su8mBDxUX6v` on
  line 39105 and `msg_011CfruqkmyC4Qi5VPj3i2RX` on line 83343, occur on those
  lines and nowhere else, so neither message was written again whole.
- `jq -R 'try (fromjson|0) catch 1'` fails on the four lines and no other. Two
  complete writes interleaved would leave the rest of the first somewhere after
  the second, as a fragment of its own, and none exists.

So the file shows a write left cut off, each time with the next line written
straight after it and no newline between. What made it stop is not known: a
writer that died, a write that failed on a full disk and a second writer are each
consistent with it and none is shown. Option 3 does not depend on which, since
the complete object is read and the cut head cannot be. What changes is the text.
The design paragraph and the module documentation describe the shape and say the
file does not name the cause.

The section on the tools' own record leaned on the same cause, saying its one
writer cannot produce such a line. What was read is
`tools/self-compact/hooks/self-compact-inject.sh`, which appends one `jq -nc`
object a call with `>>`, and whether that append can be cut the same way turns on
the cause that is not known. The decision to keep refusing there stands on the
other ground alone: a record skipped leaves a tool's line quoted as the person's,
which holds whatever cut the line.

# a-cut-transcript-is-known-by-the-line-it-lost

A review of the capture fix for a resumed session's cut transcript found four things. The cut was recognised by a boundary with no `parentUuid`, which every boundary the harness writes has, mid-file ones included, so only "first object" decided. The field that points at the lost line is `logicalParentUuid`, and a transcript is cut when its first object is a compaction boundary whose `logicalParentUuid` names a line the file does not hold. The reason given for passing a capture over, that none of its words are in the file, does not hold for a message the harness wrote twice with the copies on either side of the cut, so the design now says the second copy is taken again and never dropped. The pass-over was silent, so the run now counts the captures it passed over on stderr beside the recovered and unasked lines. The absent and null `logicalParentUuid` shapes and the reader's own `cut` flag get tests.

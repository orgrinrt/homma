# the-tool-dispatch-is-gated-to-the-targets-renki-builds-on

A reviewer's recheck of pull request 74, relayed to this round verbatim where it states the intent:

"`cmd/tools/dispatch.rs:130` and `:148` use `std::os::unix` ungated, and `homma-engine/Cargo.toml:38-40` adds renki, `renki-dirs` and `notko` for every target, while the engine used to build off unix. Move those three dependencies under `[target.'cfg(unix)'.dependencies]`, put `#[cfg(unix)]` on the tools dispatch, and add a non-unix arm that refuses with a message saying why (renki is unix only). Do not add a cargo feature for tools; that call is op's."

"`cmd/tools/cache.rs:28-75` copies renki 0.0.3's `pub(crate) cache_root`. Add a greppable `// FIXME:` there naming the upstream renki change, so it cannot drift silently."

The intent in them: the engine builds on every target it built on before the tools landed, and the part that reaches renki, which builds on unix only, is carried by the target that can. A tool command on another target is refused saying why, instead of the engine failing to build there. The dependencies are gated by target and nothing else: no feature is added, since whether the tools are optional is op's to say. A stand-in for renki's cache root is marked where it sits with the upstream change that removes it. The wording of the findings beyond that, and the line numbers, are kept for provenance.

Settled here without asking, because the findings decided the direction: the portable part of the tools module is the word handed on by a group, the root of the workspace and how a tool was asked for, and the rest is unix. `homma tools`, `homma tools check`, `homma tools run` and a group's handed word refuse off unix naming renki as the reason, and `homma <tool>` at the top level does the same.

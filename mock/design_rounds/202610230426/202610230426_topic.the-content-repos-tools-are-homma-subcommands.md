# the-content-repos-tools-are-homma-subcommands

Op, 23 October 04:14, verbatim: "The tools in homma content repo act as though real homma sub commands". At 04:20, asked whether the tools and their discovery needed a fix: "Yeah homma needs a fix for the tools and tool discovery then".

The intent in it: a tool in the content repository's `tools/` directory, described by its `tool.toml` with `promote = true`, is reached as `homma <tool> <verb>`, so `homma rules show`, `homma msg kaski board` and `homma checkup run squareup` answer, and a person or an agent never types the path of the tool's script or relies on it being on `PATH`. The rest of the 04:14 message, that the tools "act as though" subcommands, is how op put the intent and is kept for provenance.

What was measured before this round, in this container with the installed homma: `homma checkup`, `homma msg` and `homma tools` answer `unrecognized subcommand`, and `homma rules show` fails because the built-in `rules`, which has `about` and `render`, shadows the tool of the same name. No code in this repository reads `tool.toml`; the descriptor format is renki's, whose README says a host reads descriptors out of its own configuration and that `promote` means the host exposes the tool as a top level subcommand. So the dispatch is missing in the host, not broken in the tools.

Settled here without asking, because the canon is silent and the descriptors already decided them: the tools are found in `tools/*/tool.toml` of the workspace root, the descriptor's `name` is the directory's own name, a tool whose backend is not the workspace itself is listed and not run, a command named like its tool is the tool's default command and takes everything after the tool's name (which is how `msg` already works: the channel follows it), and a built-in command wins over a tool of the same name except that a built-in group hands the verbs it does not know to the tool.

# root-markers-declared-in-homma-toml

## What happened

A push from a `dotfiles` clone was refused by the pre-push hook homma installs
there. The gate decides what a repository is by looking for `Cargo.toml` and
`deno.json` at its root, and a root carrying neither is an error,
`no Cargo.toml or deno.json at <root>`, which the hook turns into a refused
push. The repository holds configuration and a `polka.toml`; there is nothing
in it to format, lint, test or publish, and the gate had nothing to say about
it except no.

## What op said

> okay so all of my dotfiles and other content repos would have either
> polka.toml or homma.toml or mockspace.toml, so polka.toml should be in the
> dotifles even though polka is still wip and not used

> I think there hsould be a config field in homma.toml to configure this. Like
> which files are considered valid root marker files and what do they signal
> about the repo

The intent is the second message: the set of root marker files, and what each
one says about the repository carrying it, is workspace configuration rather
than a constant in the binary. The first message is the list this workspace
needs on day one.

## What that changes

Today `RepoKind` is three variants derived from two fixed file names, and the
gate's step table branches on `has_crate` and `has_deno`. Two things fall out
of the intent.

The marker list moves to `homma.toml`. A table, one row per file name, each
row saying what the file signals. The two names the binary knows today become
the default rows, so a workspace declaring nothing keeps the behaviour it has,
and a workspace adding a row extends the set without a release of homma.

What a marker signals has to be a closed vocabulary the gate can branch on,
because the step table is written against it. The vocabulary is the set of
toolchains a step can call plus the one that calls none: `cargo`, `deno`, and
`content`. A repository's kind is then the set of signals its root markers
carry, not one of three variants, and the step table reads the set: a `cargo`
signal adds the cargo calls, a `deno` signal the deno calls, and `content`
adds nothing, which leaves the notices step, since that one keys on
`ante.toml` rather than on the kind. A repository whose markers carry only
`content` runs a gate of skipped steps and a green verdict, and the record
says so.

A root with no declared marker at all stays an error. That is the case the
error was written for: a repository homma has never been told about, which is
not the same thing as a repository it has been told holds only content.

The `mockspace.toml` row is the interesting one. A mockspace repository keeps
its manifests under `mock/`, and the design already owes reading that shape.
Declaring it as a marker does not settle what it signals: this workspace's
mockspace repositories are cargo workspaces under `mock/`, but the marker
itself says only that mockspace manages the tree. So the row for it in this
workspace's `homma.toml` says `content` for now, and the owed
`homma-release-reads-a-manifest-under-mock` catalogue entry is where the
manifest under `mock/` gets read for its real kind. Until then a mockspace
repository with nothing at its root is gated as content rather than refused,
which is strictly more than it gets today.

`homma.toml` itself is a marker for the workspace's own content repository.

## The shape

```toml
[markers]
"Cargo.toml"     = "cargo"
"deno.json"      = "deno"
"polka.toml"     = "content"
"mockspace.toml" = "content"
"homma.toml"     = "content"
```

The first two rows are the defaults and need not be written. A signal outside
the vocabulary is a config error at load, naming the row.

Release and publish are unchanged: they already branch on `has_crate` and
`has_deno`, and a content repository has neither, so `homma release run`
on one has no version to bump and no registry to publish to, which the check
step reports as it does today for anything else it cannot release.

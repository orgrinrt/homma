# a-foreign-hook-in-gits-own-directory-is-not-reached-by-the-table

A seventh review of the shook branches found that `homma hook doctor <repo>` reports an event as reached, and exits zero, when the file in git's own hooks directory is somebody else's hook. With no `core.hooksPath`, git runs that file and not homma's entrypoint, so the table never runs, while `hook install` refuses to overwrite it. The two verbs disagree about the same file.

An event is reached directly only when the file in git's own directory is exactly the text homma writes. A file that is anything else is reported as somebody else's hook that git runs in place of the entrypoint, with what to do: move what it does into the hooks table, or remove it, and install. That is a failure for `doctor`, as for any event the table does not reach.

The reach text for the install under git-shook also says what a failed registration leaves: the manifest is as it was, and the registry may already hold what `git shook install` wrote before the failure, so the message names `git shook doctor` as the way to see which.

## Left as they are

The test that deletes the `post-merge` entrypoint by hand before asserting it is absent, and the entrypoint path not pruning an event a layer has stopped declaring, are recorded in the report: the leftover file runs `homma hook run <event>`, which finds nothing to run, so the harm is nil, and pruning there would be a new behaviour that no one has asked for.

The module document's "whatever `core.hooksPath` says" is corrected in the source comment, which carries no design.

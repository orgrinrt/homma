A follow-up to round 202611151139, which made `homma release run` ask the workspace's `forge_route` for a release's tag and forge release. The review at `mock/research/202611151300_release-forge-routes-review/review.md` read that branch at `65efe47` and returned MERGE AFTER FIXES. This round carries the fixes it owes.

## Current state

- Step 6 asks the route for the tag where `Setup::forge_route` is set and tags and pushes with git where it is not; step 7 asks the route for the release or the forge client. Both branch on an `Option<&Path>` (`run.rs:241`, `run.rs:278`).
- When the route makes the tag, it is on the remote and not in the clone. `plan::last_tag` reads the clone's tags only and nothing in a release fetches, so the next `homma release run` from the same clone plans from the tag before, plans the version just released again, pushes a second bump and a merge of `main`, and only then the route refuses a tag the remote holds on another commit (review finding 1).
- The test of the routed release asserts the tag is absent from the clone, which pins that defect as intended; its fake route answers success and makes no tag anywhere, so the state a real route leaves is never entered (finding 2).
- The engine reads `forge_route` for every repo of the loop, while `forge_for` picks GitHub or Forgejo per repo; the route reaches GitHub alone and derives the slug from the clone's origin, so a Forgejo repo's tag would be asked of GitHub (finding 3).
- `forge_route_of` reads the manifest with `.ok()?`, so a manifest that cannot be read as a workspace's is taken as "no route" and the release falls back to the git tag push, the 403 path in a container, after `main` was pushed (finding 4).
- The backlog cites a workspace ticket that was not filed (finding 6), and `DESIGN.md.tmpl` carries the key as an unwrapped sentence on the release paragraph rather than with the manifest's `[paths]` text (finding 7).

## Changes proposed

### The forge writes of a release are one contract with two implementations

- A release makes two writes on its forge: the annotated tag on the release commit, and the release on that tag. They become one contract in the release, `ReleaseForge`, with `tag` and `release`, and the run holds a `&dyn ReleaseForge` in place of the forge client, the owner, the name and the optional route.
- `ByClient` tags with git in the clone and pushes the tag to the remote, and makes the release through the forge client, `Forge::create_release`, on the owner and name. This is what a release did before the route.
- `ByRoute` asks the workspace's `forge_route` for both, `tag <root> <tag> <sha> <tag>` and `release <root> <tag>` with the block as `FR_NOTES`, through the release's runner, and a failure of every route is `ReleaseError::Route` with the route's words.
- The engine chooses per repo, beside `forge_for`: `ByRoute` where the repo's forge is GitHub and the manifest names `forge_route`, `ByClient` otherwise. A Forgejo repo never reaches the route.
- Why a contract of the release and not one more method on the client-wide `Forge` trait: `Forge` is the REST client's contract, which migrate, verify and the gate's status read through, and in the client case the tag is a git push in the clone, never a forge call. A route as a `Forge` would have to delegate every read to a wrapped client and take the clone's path besides. The release's own contract keeps the two writes it makes together, behind one trait object, and the runtime match on an optional path goes.

### The clone holds the tag it released

- After either implementation reports the tag made, the run fetches it from the remote into the clone, `refs/tags/<tag>:refs/tags/<tag>`, and refuses where it names a commit other than the one the release tagged, `ReleaseError::TagElsewhere`. For `ByClient` the fetch finds the tag it pushed; for `ByRoute` it brings in the tag the route made, so the next plan starts from it.
- One fetch for both, so neither implementation can leave the clone behind the remote.

### A manifest that cannot be read is an error

- `forge_route_of` returns an error where the manifest does not read as a workspace's; only an absent `forge_route` key is no route.

### Tests

- The fake route writes the tag into the fixture's bare origin, as the Worker would, with its own message, and the routed test asserts the clone holds that tag on the tag sha afterwards.
- A second release in a row from the same clone, through the route, plans the next version and not the one just released. Shown failing without the fetch.
- A tag the remote holds on another commit than the release's refuses with `TagElsewhere`. Shown failing without the check.
- The engine's choice: a GitHub repo with `forge_route` named gets the route, a Forgejo repo with it named and any repo without it get the client; an unreadable manifest is an error.

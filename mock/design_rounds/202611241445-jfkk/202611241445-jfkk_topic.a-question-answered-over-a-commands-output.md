# a-question-answered-over-a-commands-output

Follows the closed round `202611241355-edoa`, which made the summarising pass.

## The question

An agent that wants one answer out of a large output, a search, a file read whole, a directory
dumped to stdout, pays for every line of the output in its own context before it can answer. The
summarising pass can read the output instead; what is missing is a verb that runs the command,
puts the question to the pass, and hands back only a short summary framed by the question and the
answer, each line naming where it came from. Asked again over output that has not changed, it
should not pay for the same reading twice.

## Decisions

- **The verb.** `homma ask --run <command> <question>` in the engine, beside `search`, since it
  reads its output through the index crate's chunker and so sits behind the same `search`
  feature. It runs the command, and prints the summary and the answer. With the pass off, or a
  call failing, it prints no answer, says why in one line, and exits 1: printing the output whole
  would hand the caller exactly what it asked not to read, and the caller can run the command
  itself.
- **The command goes through the session's own checks.** A session's permission rules and its
  hooks see `homma ask ...`, not the command inside it, so the verb puts the command through them
  itself before running it: the `Bash` rules under `permissions.deny` in the user's
  `~/.claude/settings.json` and the workspace's `.claude/settings.json` and
  `.claude/settings.local.json`, matched against the whole command and against each command of it
  split at `&&`, `||`, `;` and `|`, and then every `PreToolUse` hook those files register for
  `Bash`, run with the payload a `Bash` call of that command would carry. A deny rule matching, or
  a hook exiting 2 or answering `deny` or `block`, refuses the command with its reason, and nothing
  is run. The allow rules are not read: the session already allowed `homma ask` to run, and an
  allow list asks a person, who is not there.
- **Chunks are cut on content.** The output is cut by the index crate's own paragraph chunker,
  each chunk keeping its line span, and keyed by the digest of its text. A record of the output (a
  search hit, a paragraph) is a chunk, so the same record at another position is the same chunk.
- **Two caches, under the git directory.** A question-neutral partial summary per chunk, keyed by
  the chunk's digest, the rules' version and the model; and an answer, keyed by the question, the
  rules' version, the model and the chunk digests in order. They live under the workspace root's
  git directory, `homma/ask/`, so nothing of them is ever tracked. A partial cites lines relative
  to its own chunk and is moved to the output's lines when used, so the same chunk at another
  place cites its new place.
- **Two kinds of call.** The chunks with no partial are sent in as few calls as the budget allows,
  each chunk headed with its number, and the answer is read back as one section per chunk; a
  chunk the answer has no section for gets no partial and fails the ask, since an answer missing
  part of its input would read as whole. Then one call takes the question and every partial in
  order, at their output lines, and gives a summary framed by the question and the answer, every
  line naming its place. Partials that do not fit one call go through the summarising pass first,
  with the question as the brief.
- **What reaches the caller.** The summary and the answer, the command's exit status, how many
  chunks there were and how many came from the cache; never the output.

## Not this round

Ranking the chunks by meaning so the nearest go to the model raw: homma brings no embedder yet.
Keeping the partials in the index itself as one more aspect of each chunk, so a search can return
a hit's summary with no call: that is the index crate's to offer, and a ticket for it.

# Preserving an unvisited repo's entry preserved the shape that cannot work

**Date:** 2026-08-24
**Phase:** TOPIC
**Scope:** `homma` (the binary crate)

## What was measured

After the two rounds above, a regen in a workspace holding two of the manifest's
repos leaves `settings.json` carrying:

```
  19 "${CLAUDE_PROJECT_DIR}"/.claude/hooks/<name>
   1 /Users/<the operator>/.claude/hooks/<name>
  82 /Users/<someone-else>/Dev/<their workspace>/.claude/hooks/<name>
```

The nineteen are this run's. The single user-level path is hand-authored and is
correctly left alone. The eighty-two are the retired shape: a managed command
naming an absolute path into whichever workspace generated it. They are
preserved because their repos were not visited, which is the rule the previous
round introduced, and preserving them is wrong.

## Why the preservation rule is still right and this is still wrong

The rule exists because a workspace clones a subset of the manifest, so a repo
that aggregates nothing on this run has a registration that will work again the
moment that repo is cloned. That reasoning holds for a command naming
`${CLAUDE_PROJECT_DIR}`, which is resolved per clone.

It does not hold for an absolute one. That path names one machine and one
workspace, so there is no clone in which it starts working, and cloning the repo
does not change it. It is residue in the same sense the retired bash
aggregator's `imports/<repo>/` form is residue, and it is swept on the same
grounds: nothing writes it any more.

Left in place it is worse than inert. In the workspace measured, the paths it
names exist, because they belong to another workspace on the same machine, so
the host runs another workspace's hooks against this one's edits. Those hooks
then check their own baked root, match nothing, and approve.

## The rule

A managed command is swept when it names an absolute path, whatever repo it
names and whether or not that repo was visited. Only the placeholder form is
preserved for an unvisited repo, because only the placeholder form can come
back to life.

A hook command that is not managed is untouched by this, exactly as before. The
user-level entry in the measurement above is hand-authored and its basename
matches no repo.

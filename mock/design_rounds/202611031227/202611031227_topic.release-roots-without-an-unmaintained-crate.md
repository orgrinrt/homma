# Release roots without an unmaintained crate

The closed round `202611030733` took the system's roots for the registry and forge requests by turning on the `native-certs` feature of `ureq` 2.12.1. The pre-push gate of this repository then refused the branch: `cargo deny` reports `rustls-pemfile` 2.2.0 as unmaintained (RUSTSEC-2025-0134, no safe upgrade), reached as `rustls-native-certs` 0.7.3, `ureq` 2.12.1, `homma-core`. `ureq` 2 pins `rustls-native-certs` to 0.7, so no update of the lock clears it.

The intent of the closed round stands and is not reopened: the requests trust the system's roots and the ones `SSL_CERT_FILE` or `SSL_CERT_DIR` name. Only the way the roots are read changes, and the advisory is not put in the ignore list, since the gate is what keeps an unmaintained crate out of the lock.

## The way out

`rustls-native-certs` 0.8 reads the same places and parses them with `rustls-pki-types`, with no `rustls-pemfile` in its dependencies. `ureq` 2 takes a ready `rustls::ClientConfig` through `AgentBuilder::tls_config` and re-exports `rustls`, so the config is built here from the roots 0.8 returns, with the provider and protocol versions `ureq` itself picks (`ring`, TLS 1.2 and 1.3), and no second `rustls` enters the lock.

The registry requests are the only users. The forge clients take their agents from their own code and are not part of this change.

## Tests that must fail

The test of the closed round is the check: a request trusts the roots `SSL_CERT_FILE` names and only those. It already carries its control, a refusal as an invalid peer certificate without the file. It stays as it is and has to keep passing on the new loader, and it is run against a loader that reads no environment to show it still fails then.

## Correction found while writing the source: the forge clients are users too

The section above says the registry requests are the only users and that the forge clients are not part of the change. That is wrong. `forge/github.rs` and `forge/forgejo.rs` each build an `ureq` agent of their own, with their own headers, and until now all three got the system's roots from the one dependency feature, which is what the closed round's doc text says of the forges. Taking the feature out would have put the forges back on the bundled roots without any test noticing, since the test of the closed round asks through the registry agent only.

So the roots are read in one place and the three agents start from it: a crate-private module `tls` holds `agent_builder`, which returns an `ureq::AgentBuilder` that already trusts the system's roots, read once per process, and each of the three adds what it had before (user agent, timeout, redirect policy). The claim that every agent starts there is enforced by a test that scans the crate's source for `AgentBuilder::new` outside the module and names the files that have it, with a control that the scan finds a planted one.

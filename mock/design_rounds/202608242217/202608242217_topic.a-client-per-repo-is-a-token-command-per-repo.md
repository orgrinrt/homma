# A client per repo is a credential resolution per repo

**Date:** 2026-08-24
**Phase:** TOPIC
**Scope:** `homma` (the `verify` command)

## The finding

`verify --forge` constructs a forge client inside the per-repo loop. The
constructor resolves the credential, and once a credential can come from a
command rather than only from the environment, resolving it means spawning a
process.

So the cost is one spawn per repo rather than one per forge. A reviewer measured
it with a token command that appends to a log: eight repos produced ten
invocations, which is one for the presence check, one for the credential probe,
and one for each repo. The manifest this runs against has twenty-four.

The shape was invisible while a credential was only ever an environment
variable, because reading one twenty-four times costs nothing and looks the
same in the code.

## What is actually per-forge and what is per-repo

The credential belongs to the forge. Every repo on a forge is asked about
through the same credential and the same base url, so nothing about a repo
changes which client would be built for it.

The client is therefore a per-forge object that the per-repo loop borrows. It is
already built once per forge for the credential probe, and thrown away.

## The rule

Build one client per forge in use, keep it, and ask it about every repo on that
forge. A forge whose credential is missing or rejected has no client, which is
also the existing signal for not asking about its repos, so the two collapse
into one thing rather than being tracked separately.

## What would have caught it

Nothing does. Every existing test counts findings, and a finding is produced
whether the client was built once or once per repo, so the whole suite is blind
to the difference. The test this round owes is one that counts constructions.

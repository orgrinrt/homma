# agent-identity-from-a-character-file

Op, 29 October, relayed by console-coord at 20:15, verbatim: "the identities go in the hands directory (.shared/hands/), the old concept that ended up close to this. So hands/coord and hands/console-coord, character.md as the existing ones." He called generating each agent's identity file from its hands character a top priority.

The intent is that an identity is authored once, as `.shared/hands/<name>/character.md`, and a session is launched as that identity from it. The front matter (`name`, `role`, `memories`) belongs to the workspace and the `## Personality` section belongs to whoever edits it, the console among them. The path of the file was settled by op; how it becomes the agent file a session loads, and how a session says which identity it is, were left to the round.

What exists in homma already. `homma-org::generate::definition` is the one owner of what a generated agent definition holds, and `Layout::harness_memory` already places an agent's memory at `.claude/agent-memory/<name>` as a link to the memory kept under `.shared/hands/<name>/memory`. What did not exist is a reader for a character file with front matter, and a command that renders and launches from it.

Options for the generator.
- a: a second renderer for characters beside `definition`. Rejected: two owners of one concept.
- b: read the character through the front matter reader that rules and skills already share, and hand its body to `definition` as the character fragment, with a variant of `definition` that takes the description from `role`. Chosen.

Options for the memory mapping.
- a: copy the memories into `.claude/agent-memory/<name>`. Rejected: two copies drift, and `project install` already shows the cost.
- b: a frontmatter field naming a custom location. Not available: the agent file documentation of 30 October lists `memory: user|project|local` and no path field (`.shared/research/claude-code-agent-file-format-2026-10-30.md` in clause-dev).
- c: keep the first memory directory under `.shared` and link it relatively at the harness path; further directories are named in the definition to be read in place. Chosen.

Options for the list spelling. The shared reader refuses the block form of a list by design, so `memories` is written inline, `[a, b]`, and the two existing characters were changed to that spelling in clause-dev.

Launch. `homma identity launch <name>` renders the one definition, then replaces itself with `claude --agent <name>`, with `HOMMA_IDENTITY=<name>` in the environment as the way a session and its tools know which identity it is. `HOMMA_CLAUDE` names another program, which is how the test runs without a model. Memories must be relative, under `.shared`, with no `..`, and a real directory at the harness path is never replaced.

Not decided here, and left for a later round: whether `role` should also feed a registry row, and how the console's reader treats the inline list.

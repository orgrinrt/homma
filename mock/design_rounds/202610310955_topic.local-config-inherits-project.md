# A clone's local config inherits its project's config

## What op said

Verbatim, 27 October: "Also I think we might have to kind of rethink the homma.toml vs homma.local.toml vs the project configs (currently just copied to be the local configs but that's a blurred line bound to cause problems and issues in future) so we might want a "project" line on the homma.local.toml that corresponds to a homma.toml we have for projects like now, and without copying or linking, it kind of acts as though inheriting from full from it, and any additions add to that base and overrides override."

The intent is that a clone's `homma.local.toml` names its project in one line, homma reads that project's stored config as the base, nothing is copied and nothing is linked, what the local file adds is added, and what it sets again overrides. The rest of the quote is kept for provenance. The line's name, where the stored configs live and how the merge reads are the vehicle, and are proposed below.

## The state today

`homma local install <name>` copies `.shared/local/<name>.toml` to `homma.local.toml`, and a second install only fills the keys the copy lacks. So a copy is a snapshot of the store from the day it was made, and a change to the store reaches no clone that already holds one. Tools also record into the copy (a publish digest, a deployed commit), so declared and recorded values sit mixed in one file with nothing saying which is which.

The reading has one owner, `Local::load` in `homma-core`. `Scope` asks it for `repos`, the layers read the same file's text for the two hooks tables, and `status` and `local show` take the whole. The layers read the text a second time and parse it themselves, which is the one place a base would be missed.

## The vehicle

The line is `project` under `[instance]`, a stored name. The base is `.shared/local/<project>.toml`, where the store already is, so no store moves. The effective config is the base with the local file applied over it, built in `Local::load`, which every command already asks. The layers stop reading the file's text on their own and take the merged table from the same function, so a `[hooks]` row declared in a stored config reaches `hook run` in an inheriting clone.

The merge rule, over the parsed tables and before anything is typed:

- A table in both is merged key by key, recursively.
- A scalar in both: the local value wins.
- An array in both: the local array replaces the base one whole. Arrays are values, as `fill` already treats them, and a merge that interleaved two lists could not be undone by reading the local file.
- A key only in the local file is added. A key only in the base is inherited.
- A value of one kind over a value of another (a scalar over a table, a table over a scalar): the local one wins whole.
- Removing an inherited value: `unset` under `[instance]`, a list of dotted paths. Each path is removed from the base before the local file is applied, a table path removing the table. A path the base lacks is nothing to remove and is not an error, because the store changes under a clone. The local file may set the same path again, which then counts as local. `instance.project` and `instance.unset` cannot be unset.

`work` becomes inheritable. A local file that names a project need not repeat it, and the effective `work` is the base's unless the local file sets it. A local file without a project needs `work`, as before.

A stored config is a base and not a clone, so it may not carry `project` itself: no chain, no cycle to detect. The console contradiction check runs on the effective config, which is what lets a clone that names a console remove the project's dashboard with `unset = ["tools.dashboard"]`.

A project that is named and absent from the store, or whose stored file does not load, is an error naming the project and the file, handled as a file that does not parse is today: the scope is everything and `status` says so.

## What status shows

`status` gains a line under the instance, `inherits kaski: 14 keys inherited, 3 set here, 1 overridden, 2 unset`, and the document carries a `project` object with the name and the four lists of dotted leaf paths. A leaf is a scalar or an array. A clone that holds a full copy of a stored config, with no `project` line, is told so: `holds a copy of the stored kaski; homma local install kaski makes it inherit`. That line is also how every clone now holding a copy finds out it needs migrating.

## The install and the migration

`homma local install <name>` writes a file of one line, `project = "<name>"`, under `[instance]`, and ignores it as before. Where a file exists:

- naming the same project: nothing to do, and it says so.
- a copy of the same work with no project line: migrated. The `project` line is added, every key whose value equals the base is dropped, and every key that differs or is absent from the base stays as an override or an addition. A key the base has and the copy lacks is inherited from then on, which is the point. The migrated text is written through the same staged rename as every other write.
- for another work, not parsing, or a link: refused as before, and `--replace` moves it aside and writes the project line.

`homma local show` prints the file as written; with `--effective` it prints the merged document, and `--output json` is always the effective one, because a script reading a tool's setting through homma wants the value that is in force.

## Left to the file and not decided here

Nothing writes `unset`; it is authored by hand, like a list. `local set` writes strings only and is unchanged, and what it writes lands in the local file, which is where a recorded value belongs.

## What the round owes

The merge rule written and tested for tables, arrays and scalars, including removal. The status lines. The migration. The two rules and the install skill in clause-dev updated to the new shape in the same change.

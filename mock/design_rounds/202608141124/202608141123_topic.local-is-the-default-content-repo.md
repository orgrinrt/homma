# `local` is the default content repository

**Phase:** TOPIC
**Scope:** `homma-api`, `homma-org`

Op, mid-round:

> it should also allow answer "local" and default to exactly that. just inits a
> local git repo in the same dir where the homma.toml is.

The source landed in the round that was open. The documentation did not, because
that round's doc window had already closed, and the gate refused the commit. This
round carries the documentation.

## What it means

`content_repo` accepts a git URI or the literal `local`, and `local` is the
default, so **the key can be omitted entirely**. A directory holding a registry is
then already a workspace: the directory itself is the content repository, and
homma initialises it if it is not a repository yet.

That is the shape a workspace starts in before it has a remote, which is most of
them at the moment one is created, and requiring a URI up front would mean
inventing a remote before there is anything to put on it.

**An existing repository is left alone.** Initialising over one would discard its
history, and standing up twice has to stay the same answer.

## Why this is worth a round rather than a footnote

It removes the last required key. `spec.md` R1 says a workspace is configured by
exactly one required key; there are now none, and every path, including the
content repository itself, has a default homma will create.

## The gate refusing the commit was correct

The doc changelist was locked before op's message arrived. Editing a design
document after its window closes is exactly what the phase gate exists to catch,
and it caught it. The source was in-phase and landed; the documentation waited for
a window of its own, which is this one.

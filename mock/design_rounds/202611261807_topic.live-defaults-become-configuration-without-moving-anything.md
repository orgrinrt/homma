# live-defaults-become-configuration-without-moving-anything

Five defaults compiled into homma name the workspace homma was developed in, its maintainer or
its owner: the role file a session's role is read from, the environment variable that marks a cloud
session, the capture store, the speaker `homma answers` gives words to, and the prefix of the
keychain service a publish credential is kept under. Each is read by a running workspace today.

## What constrains the move

- A running workspace reads every one of them now, so a default that changes under it moves where
  its role, its captures, its credentials or its cloud mark are found.
- homma refuses a configuration field it does not know, and that stays: the top level of the
  manifest, `[workspace]` and `[auth]` are all refused field by field. An engine older than the key
  refuses a manifest that sets it.
- The workspace's pin follows `dev`. The launcher asks the remote for the branch's head on every run,
  so an engine run through it is current, but three kinds of run are not: a run offline, which falls
  back to the last resolved head; a run held to the last head that built, when the newest does not;
  and an engine that something else calls by its path, which `homma answers hook` does by baking the
  engine that placed it into the hook it writes. A container stood up earlier holds such an engine
  for a while.

So a manifest that sets a new key breaks every older engine that still reads it, and an engine whose
default changed moves everything for every manifest that does not set it. No single landing does
both.

## Two of the five need no key

The role file's directory is the workspace's own name, which `[workspace] name` already states and
every manifest must have. The speaker of words left on the page is the person, which the catalogue
already says: the one entry whose role is `king`. Deriving each from what the manifest holds names
nothing in the code, and for the workspace it is the value it has today, so neither moves anything
for any engine or any manifest.

Alternatives rejected: a key for each. A key would hold a second copy of a fact the manifest already
holds, and would need the three landings below for nothing.

Decision: the role file is `.config/<workspace name>/role` under the home directory, and a
workspace name that is not one plain path component is refused when the manifest is read, as a
handle is, since it now becomes a directory name. The speaker of
the page, and the default of `--from`, is the handle of the catalogue's king; with no king, `--from`
must be given and the page's speaker is "someone".

## Three need a key, and three landings

The cloud variable and the keychain prefix are facts the manifest does not hold. The capture store is
already the key `captures` under `[paths]`, which every engine in use reads.

Alternatives rejected:

- One landing that adds the keys with neutral defaults. A manifest that does not set them yet moves
  at once.
- One landing that adds the keys with today's values as defaults and nothing more. Nothing moves, and
  nothing becomes neutral either.
- Keys under a table older engines happen to read without refusing. `[paths]` reads unknown keys
  today, which is a defect of its own, and a cloud variable is not a path.
- A second environment variable the containers export beside the old one, read by a new engine
  only. A container stood up before the change has only the old one, and its new engine loses the
  cloud mark.

Decision: three landings, in this order.

1. homma, this round. `[session] cloud_var` and `[auth] service_prefix` exist, and each defaults to
   the value compiled in today. The role file and the speaker are derived as above. The capture
   store's default does not change. Every engine reads every manifest as before: an older engine
   reads the manifest it reads today, and this one reads a manifest without the keys as it reads it
   today.
2. The workspace. Its manifest sets the two new keys and `[paths] captures`, each to the value in use.
   `captures` alone may be set at any time, since every engine in use knows it. The two new keys
   land only when no engine older than landing 1 reads the manifest: landing 1 on `dev`, a hook that
   bakes an engine placed again in every clone that has one, and every container either standing on
   an engine of landing 1 or later or stood up again. An older engine refuses this manifest, which
   is why the order is the one fixed point of the move.
3. homma, a later round. The three defaults become neutral: the cloud variable `HOMMA_CLOUD`, the
   keychain prefix `<workspace name>-release`, and the capture store `.data/captures`. Every manifest
   of landing 2 sets all three, so nothing moves for it. It lands only once landing 2 is on the
   workspace's trunk.

## Small notes

The design names each default by what it is, and none by its value, so nothing of the workspace
homma was developed in reaches the rendered design.

# review-findings-on-the-hooks-table

## What was found

The review of round `202609031916`, the hooks table, before its pull request
merged. Nine findings, read against the design in
`homma-core/DEEPDIVE_release.md.tmpl`, section "Hooks", and the source under
`homma-core/src/hooks/` and `homma-api/src/hooks.rs`. Three are defects in
what the design says, and the rest are the design being said more loosely
than the code kept it.

The install reports how git reaches the entrypoints once, for the whole
install, and mockspace's chain is per event: its durable gate writes
`pre-commit`, `pre-push` and `commit-msg` and nothing else, so under its
hooks path an entrypoint for any other event is written, reported as chained,
and never run. The report also decides "mockspace's" off the spelling of the
path, `mockspace` in it or `target/hooks` at its end, where the hook file git
will actually run sits at `<hooksPath>/<event>` and says in its first lines
what it is.

`post-commit` and `pre-merge-commit` were read as staged-path events, which
the design does not name; `post-commit` runs after the commit, when nothing is
staged, so an entry with globs there never fires and says "no path matches".

`HookError::HooksPathTracked` survived, against the locked changelist that
says it went, and could not fire: the hooks directory comes back with symlinks
resolved and the root does not, so the prefix test that would raise it fails
on every macOS temp path. The test named for it asserts only the other
refusal.

Stdin is read for every event whose stdin is not a terminal; git supplies one
to `pre-push`, `pre-receive`, `post-receive`, `post-rewrite`,
`reference-transaction` and `proc-receive` and to nothing else, and a hook
whose stdin is an inherited pipe at neither a terminal nor its end blocks.

The README's command table does not name `hook`, and the repository's own
test of that table is red on it. A test of stdin replay on `pre-push` never
calls `run`. The install's doc comment promises no partial install where the
pre-check covers refusals alone. And a `HookEntry` built by hand with a glob
that does not parse matches nothing rather than failing, since its fields are
public and only `Hooks::new` checks them.

## What this round does

The reach is per event. For each event the install writes, it says whether
git reads the directory directly, or whether the hook git will run under
`core.hooksPath` is mockspace's and chains, which is read off that file's own
first lines rather than the path's spelling, or whether nothing there reaches
it; one event unreached makes the install's exit non-zero, and the lines say
which.

What an event touches is what the design names: the staged paths for
`pre-commit` and `commit-msg`, the pushed refs' difference for `pre-push`,
nothing for the rest. Stdin is read for the events git documents as supplying
one.

`HooksPathTracked` goes, as the changelist already said; the test that named
it is named for what it checks. A `HookEntry` is built through a constructor
that refuses a glob that does not parse and an empty command, so no entry
exists that `Hooks::new` would have refused. The hand-rolled `pre-push` test
goes, its property being covered through `run` on `pre-commit`. The doc
comment says what the pre-check guarantees: no refusal leaves a partial
install. The README names `homma hook` and says what `status` reports about
hooks: whether `core.hooksPath` is set, and nothing about the entrypoints,
which `homma hook install` reports.

## What was weighed and not taken

Reading stdin for every event and trusting `is_terminal`: rejected on the
review's scenario, a wrapper handing the hook a pipe it never closes.

Keeping the tracked-directory refusal as a belt: it guards a directory git
never tracks and could not fire; a refusal that cannot fire is a claim the
code does not keep.

# `create_dir_all` builds the road to the root, and the root's ancestors are not inside it

Twelfth review. A real escape, exit 0, through the built binary, and the design
document contains a paragraph written last round explicitly claiming it cannot
happen.

## The defect

`Root::create_dir_all` proves a path is inside the root, then hands it to
`std::fs::create_dir_all`. That call creates every missing ancestor, and when the
**root itself** does not exist, its ancestors are among them. Those are above the
root by definition, so containment says nothing about them.

Reproduced against a content-repo URL, so no `git init` masks it:

```
homma --config cfgdir/homma.toml org up r --root $D/a/b/newroot
  exit 0, and $D/a and $D/a/b now exist, both above the root

homma ... org up q --root $D/fakehome/.claude/nested/ws
  exit 0, and $D/fakehome/.claude and .../nested are created
```

With that prefix at a real `$HOME`, the second creates directories under
`~/.claude/`, which the record forbids outright as deny item three.

## The paragraph that said this could not happen

Written last round, in the round whose subject was removing false claims:

> Creating a directory cannot make a prefix outside the root, because a prefix is
> only created when it does not exist, and a path that does not exist resolves as
> its parent's resolution plus the remainder as written. So if the full path
> resolves inside the root, every prefix that gets created does too.

The quantifier is the error. It ranges over prefixes **below** the root, which is
where the argument holds. `create_dir_all` does not stop there.

Three rounds spent narrowing overstatements, and the narrowing itself introduced
one, in the tier that governs the code. That is the third time on this branch
that a paragraph asserting sufficiency has been the defect.

## The two guards nothing pins, again

**The re-prove after `create_dir_all`** is live: replacing the whole tail with
`Ok(())` leaves 339 green. It is deterministically pinnable, and the reviewer ran
both arms.

**The definition-parent containment check** is live: deleting it leaves 339

So the pattern is now well established and worth stating flatly: **on this branch
a guard is unpinned unless somebody deleted it and watched something fail.**
Reading the code has produced a wrong answer about which guards matter, every
single round.

## A totality claim on the README

Added by the previous round:

> Everything that writes does so under a path proven to resolve inside the
> workspace root

False, and false in a way the branch's own tests assert. The workspace clone is
**required** to be outside the root, `provision.rs` creates it with a bare path,
and two more modules write with bare paths elsewhere.

That is the same claim three rounds removed from `contained.rs`, `workspace.rs`
and `DESIGN.md.tmpl`, put back on the page a stranger lands on first.

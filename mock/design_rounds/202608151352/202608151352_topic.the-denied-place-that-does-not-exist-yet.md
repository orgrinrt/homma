# The denied place that does not exist yet

The previous round replaced a component comparison with a component comparison
**or** an identity comparison, and claimed between them they covered everything.
They do not, and the region they miss is the one nobody tested.

`under_by_identity` returns false when the denied location has no inode. So for a
denied place that **does not exist yet**, only the component comparison runs, and
that is the comparison the whole round existed to stop relying on. Absent plus a
folded spelling is answered by neither arm.

Three reproductions at exit 0, one per deny item, and the second is the ordinary
case rather than a contrivance:

- `~/Dev/clause-dev` absent, workspace `$HOME/Dev/CLAUSE-DEV/ws`: created and
  cloned into. `stat` gives one `(dev, ino)` for both spellings.
- Hand `a` declared at `$T/ws-a` and **not yet stood up**, so it does not exist.
  Hand `b` declared at `$T/WS-A/inner`. `org up b` puts `b`'s clone inside `a`'s
  workspace.
- A home with no `.claude` yet, workspace `$HOME/.CLAUDE/ws`: cloned into
  `~/.claude/ws`.

The control is the same command with the denied directory pre-created, which
refuses at exit 1. **Existence is the entire variable.**

## The sentence that was false when it was written

`denied.rs:249`, shipped last round: "A location with no identity is caught by the
component comparison beside this."

It is not, and it cannot be, because the component comparison is what folding
defeats. Fifth consecutive round shipping a guard under a paragraph asserting it
is total, and this one asserts it about the exact hole.

## Why the tests could not have caught it

Every end-to-end deny test routes through `a_home_with_a_real_claude`, which
**pre-creates the denied directory**. The two workspace ones pre-create theirs.
Exactly one test enters the absent-denied-place path, and it uses the identical
spelling.

So the suite samples the region where the identity comparison works and never
names the region where it does not. That is the sampled-law failure from
`the-test-gate.md`, shipped in the round whose subject was this comparison,
roughly an hour after the same class was fixed on the sibling branch. Knowing
about a failure mode is not protection from it; a test that enters the region is.

## The fix, and why it deliberately over-refuses

A deny list is asked whether two paths **could** denote one directory, and the
honest answer where one of them does not exist is that the filesystem has not
been consulted and cannot be. So the comparison stops trying to be exact and
becomes conservative:

- components compared **case-insensitively**, which covers a folding filesystem
  whether or not the target exists;
- **plus** the identity comparison, which covers a location whose spelling shares
  no components at all, the firmlink case.

Over-refusal is the safe direction here and the cost is legible: on a
case-sensitive filesystem an operator who genuinely wants `~/Dev/CLAUSE-DEV` to
be a different directory from `~/Dev/clause-dev` is refused, and told why. That
is a strange thing to want and a cheap thing to lose.

What it still does not cover is Unicode normalisation. APFS folds NFD against
NFC as well as case, and Rust's standard library has no normalisation. Every
current deny entry is ASCII, but a participant's workspace name comes from the
registry and need not be. It carries a `FIXME` naming the condition rather than a
mechanism.

## The refusal that fired after the write

Same bug, different symptom, and it breaks an invariant this branch has now
repaired four times.

`org up r --root $HOME/Dev/CLAUSE-DEV` with `~/Dev/clause-dev` absent: `Root::new`
passes because the denied place has no inode, `git.init` creates it through
`create_dir_all`, `provision` clones the workspace, and only then does
`Layout::new` refuse, **because by that point the directory exists and has an
inode**. The guard succeeds precisely because the forbidden write already
happened. Exit 1, and a git repository sitting in the central clone's place.

One fix closes both.

## The registry writer nobody listed

`org add` writes two files at an operator-supplied path with no deny check at
all: `homma --config $HOME/.claude/homma.toml org add intruder` exits 0 having
rewritten a registry inside `~/.claude`. It is new code on this branch.

The README and the PR body both enumerate the unguarded writers and name only
`cmd/aggregate.rs` and `cmd/gates.rs`. **An incomplete list of known gaps reads
as a complete one**, which is worse than no list.

## What is not decided here, because it is not this branch's to decide

`agent regen` writes hook scripts into `<workspace>/.claude/`, marks them
executable, rewrites `settings.json` to register them, and removes files there.
Pointed at a home it does all of that inside `~/.claude`, which is deny item
three in its exact words, installing code the harness then executes.

That is disclosed and it is disclosed too mildly, so the disclosure is corrected
to say what it actually writes. The **locus** question is not corrected, because
it belongs to the record rather than to this branch: writing under
`~/Dev/clause-dev` is `agent regen`'s designed behaviour and is deny item one for
a Hand, and homma has no notion of who is running it. Putting a check there
without settling that would forbid the tool its own purpose.

So the accurate sentence is the PR body's own: the deny list is at present a
property of one subcommand.

# Git hooks are declared in shook.toml

## The ask

The manifest stops being a place a git hook is declared. Its `[hooks]` table and the `[hooks]` of an overlay go. The git hooks a workspace wants are git-shook manifest entries in a `shook.toml`, which homma works beside. homma never runs a chain of git hooks of its own: git-shook does, on its base, `shook`. Ordering, the paths an event touched and the first refusal stopping the rest all belong to git-shook. git-shook 23c5ded carries `paths` and `{paths}`, which is what `[hooks]` had beyond a plain command.

## What stays homma's

There are two things.

- The release gate. It is the `pre-push` row every workspace has without writing it, so homma registers it itself: a clone-local git-shook manifest named `homma`, holding `[hooks.pre-push]` with `run = ["homma", "release", "gate", "--hook"]`. git-shook hands it git's arguments and replays stdin to it, as the old table did.
- Carrying the workspace's own git hooks into every member, which `[hooks]` did with an entrypoint per member. The workspace now declares them in one `shook.toml` at its root. Where that file sits is `git_hooks` under `[paths]`, `shook.toml` by default. `homma hook install <repo>` copies it into the member as a clone-local manifest under its own name, beside homma's. git-shook then registers both, with `--only` naming the two, so the operator's yes covers these and nothing that arrived through a merge.

  homma reads only the file's `name` from it, to know what to call the copy. With none, it uses the workspace root's directory name, which is git-shook's own rule for a manifest at a root. Everything else in the file is git-shook's to read and refuse. A workspace with no such file registers the gate alone, and the install says so.

Options weighed for the second:

- homma writes git-shook manifests from rows of its own config. Refused: that keeps homma's config a place a git hook is declared.
- Every member carries the workspace's hooks in its own tracked `shook.toml`. Refused: a member does not name the workspace, and the workspace's prose check is the workspace's, not each member's.
- The workspace's `shook.toml` copied into each member as a clone-local manifest (taken). The declaration stays a git-shook manifest, in one place, and homma only places it where git-shook reads it.

## Where git-shook does not hold the hooks path

homma never takes `core.hooksPath`: that key is git-shook's or mockspace's to hold. Where git-shook does not hold it, `homma hook install <repo>` refuses, says to run `git shook install` in that repository first, and changes nothing. The entrypoints an older homma wrote into git's own hooks directory are left where they are by a refusal. Where the install goes ahead, it removes each one that is exactly homma's old text, along with git-shook's kept copy of it where git-shook adopted one. Otherwise git-shook would keep it as `00-existing`, and the gate would run twice.

## The verb that old entrypoints call

`homma hook run <event>` stays only for the entrypoints and git-shook entries an older homma installed. Those run until the clone's next `homma hook install`, and an engine can change under a running session.

- At `pre-push` it runs the release gate exactly as the old table's first row did. A push is therefore never ungated by this landing.
- At every event it says, once on stderr, that the hook was written by an older homma and that `homma hook install <repo>` moves it onto git-shook.
- At events other than `pre-push` it runs nothing and passes. The workspace's prose check is skipped in that window, with that line said.

It goes when no clone carries one. Its removal is a ticket the code's marker names.

## What is said of a `[hooks]` that is still there

A manifest or an overlay still carrying `[hooks]` is not refused, since a running workspace's manifest has one.

- The parse takes the manifest without it. The strict parse runs first and a manifest without `[hooks]` costs nothing.
- `homma status` says once, under the workspace line: `  [hooks] is no longer read: the git hooks are declared in <git_hooks>`, followed by the move.
- The document carries `retired` always, empty where nothing retired is present.
- `homma hook doctor` says the same.

## The order of landings

1. git-shook at 23c5ded or later is what every seat installs. Its `git shook doctor` names a dispatcher an older git-shook wrote.
2. The workspace writes its git hooks into the `shook.toml` at its root, the prose check with `paths` and `{paths}`. It keeps `[hooks]` in its manifest meanwhile: older engines run the table, this one never reads it.
3. This engine lands. In each clone, `homma hook install <repo>` per member moves the hooks onto git-shook. Until then an old entrypoint calls `homma hook run`, which gates the push and says to reinstall.
4. The workspace takes `[hooks]` out of its manifest once every engine in every clone and container answers `homma --output json status | jq -e '.workspace | has("retired")'`. An engine from before step 3 answers no.

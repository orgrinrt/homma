# Topic: the crate taxonomy

**Date:** 2026-08-14
**Phase:** TOPIC
**Scope:** what crates homma is, what each owns, and where the layer boundaries fall
**Status:** open

homma is two crates, `homma-core` and `homma`, split before this repository
adopted mockspace and before the workspace had a stated opinion about layering.
The split is not wrong so much as undesigned: `homma-core` holds configuration,
forge clients and git operations because none of those is a command, and `homma`
holds everything that is. That is a division by "is it the CLI", which stops being
useful the moment anything other than a CLI drives the same work.

Something other than a CLI is about to. The work homma is being grown for needs a
long-running process that owns a message store, and a terminal interface over the
same store, and an MCP surface exposing the same operations to agents. Three
consumers of one body of logic, where today there is one.

## What homma has to do

Gathered from what exists and what the design it is being built for requires, in
rough order of how load-bearing each is.

**Know who exists.** A registry of identities: people, agents, and the roles that
distinguish them. Each carries a name, an email, a workspace, a session, the repos
it holds, and the path to its generated definition. This is configuration, read
constantly and written rarely.

**Own the workspaces.** Create a workspace, clone repos into it, set its git
identity, link its memory, keep it current, and report when it has drifted. This
is git operations plus a layout convention, and it is where the isolation the
whole design rests on actually happens.

**Carry the correspondence.** An append-only message store, channels over it, an
index derived from it, and read state per identity. This is the part with a
concurrency story, and the part that must have exactly one writer.

**Track the work.** Records with typed attributes, kinds declared in
configuration, boards derived by query, and a reference graph extracted from the
text. Two query dimensions: time and relation.

**Reach the forge.** Read metadata, ingest pull requests and third-party issues as
read-only records, mirror rather than couple.

**Generate.** Agent definitions from configuration plus a template plus a
hand-written character fragment; hooks and settings into each workspace.

**Serve.** A daemon owning the store, an MCP surface over the operations, and
later a web interface over the same.

**Present.** A terminal interface, which is the surface a human actually lives in.

## The constraint that shapes everything

**homma must work for a workspace it has never seen.** One required configuration
key names the content repository; every path has a default it will create and an
override for a workspace whose convention differs. Nothing about the workspace it
was born in may be compiled in.

That constraint is what decides the taxonomy, because it means the layout, the
kinds, the roles and the channel shapes are all *data* rather than code. A crate
that knows what a Hand is, as opposed to knowing what a role is, has hardcoded one
workspace's answer.

## The second constraint: three consumers, one body of logic

A CLI, a daemon and a terminal interface will all drive the same operations, and
an MCP surface will expose them to agents. So the operations cannot live in the
command implementations, which is where roughly half of them live today.

This is the actual argument for re-cutting the crates, and it is worth stating
plainly: the current split cannot express "the same thing, driven three ways",
because one of the three ways is what the split was drawn around.

## Options for the taxonomy

### A. Keep two crates, move the operations down

`homma-core` gains everything that is not argument parsing or rendering;
`homma` keeps the CLI. The daemon and the TUI become modules in `homma`.

Cheapest by far, and it is honest about the size of the codebase: seven thousand
lines does not obviously want seven crates. It fails the third-consumer test
though. A daemon inside the CLI crate means the CLI's dependencies are the
daemon's, and the TUI's, and the MCP server's, so every consumer pays for every
other. It also leaves `homma-core` as a bag with no internal boundary, which is
what it is today and the reason nothing in it can be reasoned about separately.

### B. Cut by layer, one crate per boundary

```
L0  homma-api      contracts. identity, handle, ref, record, kind, the
                   attribute types, the config schema. no I/O at all
L1  homma-repo     git operations, workspace lifecycle, identity config
L1  homma-forge    forge clients, ingestion of PRs and issues
L2  homma-store    the append-only record store, the index, read cursors
L3  homma-org      the registry and generation, over api and repo
L3  homma-sauna    channels, tasks, boards, the graph, over api and store
L4  homma-serve    the daemon, the waker, the MCP surface
L5  homma          the CLI and the TUI
```

Eight crates. Each boundary is real and each is a dependency edge Cargo enforces.
The third-consumer problem disappears: `homma-serve` and the TUI both depend on
`homma-sauna`, neither depends on the other, and the CLI is one consumer among
three rather than the place logic lives.

The cost is honest: eight crates for seven thousand lines is a lot of manifests,
and several of them would start nearly empty.

### C. Cut by layer, but only where a boundary already earns itself

The same layering as B, with crates created when something needs them rather than
up front. `kolli` set this precedent explicitly, and its wording is the argument:
an absent crate is deliberate because "an empty crate holding a name is a
directory pretending to be a decision".

So the taxonomy is declared in full, and the round creates:

```
homma-api      because every other crate needs the vocabulary
homma-repo     because the workspace lifecycle is the first slice
homma-org      because the registry is the first slice
homma          because something has to be run
```

and leaves `homma-forge`, `homma-store`, `homma-sauna` and `homma-serve` to the
rounds that build them. The existing forge and git code moves into `homma-repo`
and a `homma-forge` that arrives when the ingestion work does; until then the
forge client stays where it is rather than being given a crate for its own sake.

## The layer labels

Whichever option wins, the labels go in `mockspace.toml` and the lints read them.
The placeholder the adoption round left is `L0 core` and `L1 surface`, which
describes the undesigned split rather than a designed one.

```
L0 contracts     types and traits, no I/O
L1 mechanism     git, forge, filesystem. things with side effects
L2 store         records and their persistence
L3 domain        registry, correspondence, work
L4 service       the daemon and its surfaces
L5 surface       what a human or an agent drives
```

## What this round should decide

The option, the crate set, the layer labels, and which crates exist at the end of
it. What each crate's public surface is belongs to the rounds that build them.

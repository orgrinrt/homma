# A manifest entry an engine does not know

## The ask

`Config` refuses an unknown field, and so does `AgentTable`. A manifest that gains a table or a key a newer engine reads is refused whole by every older engine: every verb of that engine stops, the hooks that call it included, until the engine is replaced. A table or key an engine does not know should stop only what reads it, and say once which engine knows it and what brings the clone to one; the verbs that do not read it go on. A misspelt key inside a table the engine knows stays refused.

## Where the line is drawn

The manifest's top level and `[agent]` hold tables and settings that are each a feature of their own: a new entry there is a newer engine's feature far more often than a misspelling, since each entry is a whole section, and nothing of this engine reads what is under it. Every other table holds the settings of one feature, where an unknown key is a misspelling or a setting this engine would read wrongly without, so those keep refusing, and so does a row of `[agent.hooks]` or `[agent.nudges]`.

Taken: an entry of the top level or of `[agent]` under which this engine reads no key is unread. The parse takes the manifest without it and keeps its dotted name, `later` or `agent.later`, on `Config::unread`. Anything else unknown is refused as before.

Options weighed:
- Every table lenient: a misspelt setting reads as its default in silence, which is what `[paths]` was taken out of.
- A minimum engine key the manifest sets and the engine reads first: the engines already installed do not read it, so it helps only after this landing, as this does, and the manifest's owner keeps it current by hand.
- Unread entries found by the key probe (taken): `homma_core::config::keys` already lists every key this engine reads, so the entries under which it lists none are the unread ones, with no list of names kept beside the types.

## How the parse goes

The strict parse runs first, as today, and a manifest it takes has nothing unread. Only where it refuses is the manifest read again as a raw value: the unread entries are found against the key probe and taken out, and the rest is parsed strictly. Where nothing was unread, the first refusal is returned as it was, with its line. The probe runs only on a manifest the strict parse refused, so a manifest this engine knows costs it nothing.

## What stops

A verb that reads an unread entry stops. This engine has no verb that reads an entry it does not know of, with one exception: `homma agent regen` writes the agent host's registrations from the whole of `[agent]`, and written without an entry it would drop what a newer engine registered for it. So `agent regen` refuses while any entry under `[agent]` is unread. Every other verb goes on, `agent nudge` among them, which reads `[agent.nudges]` alone.

## What is said, and where

Once, by `homma status`, under the workspace line: `  not read by this engine: <entry> ...`, then what to do. The document carries `unread` always, empty where there is none. `agent regen` refuses with the same words. Nothing else prints them: a line on every load would grow every verb's output and every hook's, which is the option the `[paths]` round ruled out for the same reason, and the status is where a clone is checked at the start of a session.

What to do follows from the manifest's own engine pin:
- a branch: a run with the network builds the branch's tip; an entry that engine does not list under `reads` either is one no engine of that branch reads yet, or is misspelt;
- a revision, tag or version: the pin is moved to an engine that lists the entry under `reads`;
- none: a pin is set to such an engine.

The engine that knows an entry is named by what it says of itself: its status lists the entry's keys under `reads`. An engine cannot name a later one, and the revision of the running engine would ask the reader to know which revision brought the entry.

## The order of landings

Engines already installed refuse a manifest with an entry they do not know, and cannot be changed. So:

1. homma, this round: engines from here take such a manifest as above. A manifest without an unread entry reads as today in every engine.
2. A manifest takes a new entry of its top level or of `[agent]` only once no engine older than landing 1 reads it: in every clone and container `homma --output json status | jq -e '.workspace | has("unread")'` holds, since an engine older than landing 1 has no such field and refuses the manifest. An engine from landing 1 on that does not know the entry goes on, and its `agent regen` refuses with the words above until the clone stands on one that does.
3. A new key inside a table an engine knows is refused by that engine still, so it lands as the live defaults did: once every clone's status lists it under `reads`.

## Small notes

- The second parser of the manifest, `homma_api::Workspace`, refuses no unknown entry and is unchanged.
- The overlays `layers` names are read for `[hooks]`, `[agent.hooks]` and `[agent.nudges]` only, and an overlay that does not read is already kept apart as a layer error; unchanged.
- Whether the strict-then-lenient parse belongs to the shared configuration crate is open: every manifest of a tool built the same way meets the same order of landings. This round keeps it in homma, where the key probe and the engine pin are.

# capture-watermark-by-line

A review of `homma capture` before it merged found the watermark loses words,
and three smaller places where the reading of a transcript is wrong. All of it
was checked against real transcripts before this was written.

## The timestamp watermark drops queued words

A capture's `through` is the timestamp of its last event, and the next run takes
events stamped after it. The harness does not write lines in timestamp order. A
message typed while a turn runs lands as a queued-command attachment, and that
line carries the time the message was queued, which is earlier than lines already
written before it. Counted over two sessions of this workspace, 213 and 145 such
inversions. So a capture taken after an ask round, which is exactly when the rule
says to capture, sets `through` past a message that is written to the file later
with an earlier stamp, and the next run skips it for good.

Order in the file is the order the harness read things in, and that is the order
a capture has to follow. So `through` becomes the `uuid` of the last complete line
the run read, and the next run starts after the line carrying that uuid. The
latest capture for a session is the one whose `through` sits latest in the
transcript, not the one with the latest date. A capture naming a uuid the
transcript does not hold is refused, loudly, since the transcript being rewritten
under a store is not something to guess around. `--since` stays an instant, the
floor for a session no capture has come from, and filters by the event's own
stamp after the position filter.

## A queued message can appear twice

When a queued message is taken in by the turn and the turn ends, the harness
sometimes also writes it as a typed human line, whose `uuid` is the attachment's
`source_uuid`. Both are read today, so the words go into the capture twice, or
into two captures. The twin is recognised over the whole transcript, not just the
part after the watermark, since the two halves can fall either side of it, and
the one earlier in the file is the one kept.

## A multi-select answer can carry typed text

The harness joins chosen labels with `, `, wraps a label that itself holds `, ` in
double quotes, and appends whatever the person typed in the free field after the
labels. Seen in this workspace:

```text
~/Dev/staging generally, "~/.meet, properly this time", "loru itself, ...", Just probably worth it to grep any keywords from ~/Dev in general.
```

Today that whole string is treated as typed, so the labels, which are the agent's
words, get blockquoted as the person's. An answer is read as labels first, the
longest label tried first at each position, quoted or bare, each followed by `, `
or the end; what is left is the typed part. So an answer carries both the chosen
labels and the typed remainder, and only the remainder is quoted.

## Smaller

- The workspace path is canonicalised before it is escaped into the projects
  directory name, since the harness names that directory from the real path and a
  symlinked or `/tmp` path otherwise misses it.
- A last line with no newline is a line still being written and is not read.
- `--session` given as a path does not need `HOME`.
- The file is created with create-new, so a capture never replaces one.
- The README row speaks to nobody in the second person.

## Not in this round

The store path and the projects directory are fixed in the source rather than
read from the manifest. That is a question of where settings live, and it is
left as it is.

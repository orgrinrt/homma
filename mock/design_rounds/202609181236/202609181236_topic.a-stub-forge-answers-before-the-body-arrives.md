# a-stub-forge-answers-before-the-body-arrives

Two wire tests in `homma-core` fail on some runs and pass on others:
`a_422_on_create_is_already_exists_only_when_the_body_says_so` in the github
client's tests and `a_409_on_create_is_already_exists_whatever_the_body` in
forgejo's. Run three times in a row on one machine, the first went green and the
next two red, with nothing changed between.

Both use a `status_by_path` stub that reads the request line and the headers,
writes its response, and drops the socket. Creating a repository is a `POST`
with a json body, and the stub never reads that body. When the stub's close
lands while the client is still writing, or with the body still unread in the
socket's receive buffer, the peer sees a reset rather than the response, and the
client reports a transport error instead of the status the test asserts on. So
the test measures a race between two threads on the loopback rather than the
mapping it names.

The two recording stubs in the same files already read `Content-Length` and
drain the body before answering, which is why the status and release tests
beside them have never been seen to flake. The forgejo stub's doc says its arms
"read no body, so none is taken", which confuses the response's body with the
request's: the arms read no response body, and the request still carries one.

The fix is the recording stubs' reading, in both `status_by_path` stubs: take
`Content-Length` off the headers and read that many bytes before answering. The
redirect stub, `renamed_private_repo`, serves `GET`s that carry no body, so
nothing arrives after the headers for it to leave unread; it is left alone.

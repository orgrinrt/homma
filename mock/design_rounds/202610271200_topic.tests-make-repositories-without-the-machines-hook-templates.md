# tests-make-repositories-without-the-machines-hook-templates

`hook_install_writes_one_entrypoint_per_event_and_says_how_git_reaches_them` in `homma-engine`'s `cli_release` fails on `dev` at `tests/cli_release.rs:168`, asserting "no entries, no entrypoint": a `commit-msg` file exists in the hooks directory of a repository whose table names no `commit-msg` entry.

Which side is wrong. `homma_core::hooks::install` writes one entrypoint per event in `Hooks::events()`, and that is the table's keys: the gate's `pre-push` and what the manifest declared. The test's manifest declares `pre-commit` only, so `install` wrote `pre-push` and `pre-commit`, and the code is right by `crates/homma-core` `hooks::install` and by its own unit test (`install.rs`, the `commit-msg` absent case). The file the assertion found is not homma's. The container sets `init.templateDir` globally to a directory holding a `commit-msg` hook (the byline guard the bootstrap installs), and `git init` copies every template into a new repository. `clone_at` in `tests/support/mod.rs` runs a bare `git init`, so the test repository starts with somebody else's `commit-msg`. Measured: `git init` in a scratch directory on this container lists `commit-msg` under `.git/hooks` before homma runs anything.

The design is silent on the git environment the tests run in, as it was for the identity variables in round 202610231252. The test's intent, that an event with no entries gets no entrypoint, is the claim kept, and it is only checkable on a repository that begins with no hooks.

The fix: a repository a test makes is created with `--template=`, so it carries nothing from the machine's template directory. `clone_at` in the engine's test support and the `repo()` helper in `install.rs` do it. No production code changes, and the assertion stays as written.

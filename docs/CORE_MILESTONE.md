# Milestone

How a workspace tells where its current milestone began and records every milestone with the revisions it was made of, and three reports over the range since: how it splits for review, which stand-ins it added, and which branches the trunk does not yet hold. One document because the commands share one idea of a range, the commits from a recorded revision to the tip of a branch, and one rule about what they write.

## What a milestone is

A milestone is a numbered stretch of a repository's trunk, closed by a landing round, and it is recorded with four revisions: the `base` it began from, the `freeze` where the trunk stood when new work stopped, the `head` the review pinned, and the `tip` where the round closed. The tip is the next milestone's base. The epoch a milestone closes is the range `base..freeze`, and the review covers `base..head`. Both are read off the row and neither is stored, since a second copy of a range is a second place for it to be wrong. Nothing about it is a release: a release is a merge onto `main` and carries four things, and a milestone is one table in a file that says where to start reading.

## The record

The record is `.homma/milestones.toml` in the repository the milestone belongs to, one table per milestone, in order:

```toml
[[milestone]]
n = 2
base = "<the previous tip>"
freeze = "<the trunk at the freeze>"
freeze_at = "2026-10-31"
head = "<the pinned head>"
tip = "<the trunk at close>"
at = "2026-11-02"
```

Every date is the commit's own committer date, so a row is reproducible from the repository alone and no clock is read. `freeze_at` is the date of `freeze` and `at` is the date of `tip`. The first row has no `base` where nothing earlier is recorded. A row written before this shape holds `sha` and `at` only, stays readable as it is, and its `sha` is its `tip`; its number is its place in the file where it has no `n`. No tool rewrites a recorded row: a step appends a new table as text, or sets its own keys on the last table by their place in the text, and every other byte of the file stays as it was, a comment, the order of keys, a key this shape does not name, the file's line endings and a leading byte order mark included. A key a step sets that is already there has its value replaced, a basic or a literal string whole, and keeps what follows it on its line, and the lines a step adds end as the file's own lines do. A table header may hold spaces inside its brackets and a comment after it. A step parses the text it is about to write and writes it only where it reads back as exactly the rows it began with plus the change it was asked for, the other rows unchanged and the row it edits holding the keys it set, so a value spread over several lines on the open row is refused and the file left as it was, never written into. A record not written as `[[milestone]]` tables is refused by a step too, since a table added to it would break the file.

It is a tracked file because a branch push is the one write a cloud session is certain to have. A tag push is refused by the proxy of a cloud container, and a record that depends on one cannot be written where the work happens. The file travels with the branch that writes it and lands with the merge it records.

A row is written in three steps as the phases pass, and each commits nothing: the caller commits the file and pushes the branch by name. `freeze` and `pin` print the row they wrote as `show` prints a row; `mark` prints nothing to a person. Each refuses a sha the trunk does not contain, a rev that is no commit, and a step out of order.

`homma milestone freeze <repo>` opens row `n`, the number after the last row's. `base` is the last tip and `freeze` is the tip of `origin`'s trunk, or the local trunk where the clone has no origin copy. It is refused while the last row has no tip, because a milestone is still open, and where the last tip is not an ancestor of the freeze. Where no row is recorded the new row has no `base`, whatever `milestone/*` tags the trunk holds: a tag answers the `base` command and nothing else.

`homma milestone pin <repo> [<sha>]` sets `head` on the open row, the trunk's tip where no sha is given. It is refused with no open row, on a row already pinned, and on a sha that does not contain the freeze.

`homma milestone mark <repo> <sha>` closes the open row by setting `tip` and `at`, and is refused on a row not yet pinned, on a sha that does not contain the head, and on a sha already a tip. With no open row it is refused on a sha that does not contain the last tip, and otherwise appends a row with `n`, `tip` and `at` only, which is the call as it was before the steps. With `--tag` it also makes the annotated tag `milestone/<n>` locally, before the record is written, so a refused tag leaves no row change and a rerun is not met by "already marked". `n` is the row's number, or the next number above that whose tag is free; pushing the tag is the caller's, where a push of tags works.

The record is named in `append_only` and the append merge driver keeps both sides' tables when two branches each opened one. The open row is the one thing edited in place, by the one session running that milestone, and a conflict on it is consolidated by hand.

`homma milestone base <repo>` prints the last tip, which is the sha the current milestone began from while one is open and the one just closed otherwise. It is read from the trunk's committed `.homma/milestones.toml` and not from the working tree, so a clone checked out on a branch answers as the trunk does. A trunk with no tip in its file is answered by the newest `milestone/*` tag the trunk contains, and one with neither is refused saying so and naming `mark`. The trunk is the local branch, or `origin`'s where the clone has only that.

`homma milestone show <repo> [<n>]` prints every row, or row `n`, from the same committed record, each with its `epoch` range `base..freeze` and its `review` range `base..head`, a range left out where one of its ends is not yet recorded. A row with no `base` of its own, one from before the steps, is shown with the previous row's tip as its base. An `n` no row has is refused.

## The range

The three range reports take `<repo> <base> <head>`. `base` must be an ancestor of `head`, or the command is refused. The diff is `git diff` between the two with renames not followed, so a moved file is a deletion and an addition and the partition it left is visible.

`partition` groups the changed files into units. A unit is the crate, which is the directory name after a `crates/` segment of the path, or `(root)` for a path with none. Within a unit a file is a document when it is a markdown file, ends in `.md.tmpl`, or sits under `docs/`, and source otherwise. Each partition reports its unit, its kind, its files and its added and deleted lines from `git diff --numstat`; a binary file counts as a file and adds no lines. The order is changed lines descending, then unit, then kind. It is a split to read and carries no size limit: how big a partition may be is the reviewer's to say.

`stand-ins` reads only the lines the range added, from the diff with no context, and only in files it reads. Nothing under `mock/research/` or `mock/design_rounds/` is read, nor any `.patch` or `.history` file, whatever else its path says, and a document (markdown, `.md.tmpl`, or under `docs/`) is not read. Every other file is read, data and configuration included, since a placeholder left in a `.toml` knob is one; code of any language counts as source. The diff is asked for with its prefixes and external drivers fixed, so a user's `diff.noprefix` or `diff.external` changes nothing. A marker is one of a vocabulary the tool owns and says so. `FIXME`, `TODO`, `todo!(`, `unimplemented!(` and `#[ignore` count anywhere on an added line. `stand-in` and `relaxed` compared without regard to case count only inside a comment, the text after `//`, `/*`, `#` followed by a space, or `<!--`, or a block comment's continuation line, which is `*` followed by a space and then text (a line starting `*self` is code), so the memory ordering `Ordering::Relaxed` is not one. A line is reported once, under the first marker in that order it carries, with its file, its line number in the head and its text trimmed. Files a diff marks binary are not read. A line with no comment opener is never a `stand-in` or `relaxed` marker, in a data file as in code.

## The branches

`branches` takes the repository alone. The trunk is the working branch where the repository has one, read from `origin` when it is there since a local copy may be stale, and the public branch otherwise, the same choice a release makes. A branch is listed when the trunk's tip does not contain it, from `origin` and the local heads, except the trunk, the release line, `badges` and `HEAD`; where a name is both, the remote's tip is read.

For each: the branch, its tip, the commits it holds that the trunk does not, the lines changed against the merge base, the files `git merge-tree --write-tree --name-only` reports in conflict (it touches no tree), and its call. The call is `land` when nothing conflicts, `merge-trunk` when something does, and `empty` when merging the branch into the trunk gives the trunk's own tree, which is decided by the trees and not by a line count, so a branch that changes only a binary file is not empty. A branch git cannot compare is a call of its own and the report carries on: `unrelated` when it shares no history with the trunk, and `unreadable` with git's words when the comparison fails otherwise: `git merge-base` failing with anything but its one "no common history" exit, `git merge-tree` exiting with anything but its clean and conflicted exits, a conflicted exit that names no merged tree on its first line (git's way of refusing a merge it cannot make), and a conflict git cannot name. Such a branch has no lines or conflicts to report and is listed all the same. The call is a reading of those numbers and not a verdict; nothing refuses a landing on it.

## What none of them do

None writes outside `freeze`, `pin` and `mark`, none fetches, none gates, and none exits non-zero for what it found. One branch git cannot read is a finding about that branch and never ends a report. A refusal is an unknown repository, a sha that is no commit, a base that is not an ancestor, a step that cannot be taken. Output is lines for a person and the same report as JSON under `--output json`, in the shape every `release` verb has.

# Milestone

How a workspace tells where its current milestone began, and four reports over the range since: how it splits for review, which stand-ins it added, and which branches the trunk does not yet hold. One document because the five commands share one idea of a range, the commits from the last marked milestone to the tip of a branch, and one rule about what they write.

## What a milestone is

A milestone is a sha on a repository's trunk that was marked as the point a landing round began from. The next round's range is that sha to the trunk's tip, or to a branch's. Nothing about it is a release: a release is a merge onto `main` and carries four things, and a milestone is one line in a file that says where to start reading.

## The record

The record is `.homma/milestones.toml` in the repository the milestone belongs to, one table per mark, appended in order:

```toml
[[milestone]]
sha = "<full sha>"
at = "2026-10-27"
```

`at` is the commit's own committer date, so a mark is reproducible from the repository alone and no clock is read. The last table is the current milestone.

It is a tracked file because a branch push is the one write a cloud session is certain to have. A tag push is refused by the proxy of a cloud container, and a record that depends on one cannot be written where the work happens. The file travels with the branch that marks and lands with the merge it records.

`homma milestone mark <repo> <sha>` appends a table and commits nothing; the caller commits the file and pushes the branch by name. It refuses a sha that is not a commit, one the trunk's tip does not contain, and one already marked. With `--tag` it also makes the annotated tag `milestone/<n>` locally, before the record is written, so a refused tag leaves no mark and a rerun is not met by "already marked". `n` is the count of marks including this one, or the next number above that whose tag is free; pushing the tag is the caller's, where a push of tags works.

The record only grows, so the project names it in `append_only` and the append merge driver keeps both sides' marks when two branches each marked.

`homma milestone base <repo>` prints the sha of the last table. A repository with no file is answered by the newest `milestone/*` tag the trunk contains, and one with neither is refused saying so and naming `mark`. The trunk is the local branch, or `origin`'s where the clone has only that.

## The range

The three range reports take `<repo> <base> <head>`. `base` must be an ancestor of `head`, or the command is refused. The diff is `git diff` between the two with renames not followed, so a moved file is a deletion and an addition and the partition it left is visible.

`partition` groups the changed files into units. A unit is the crate, which is the directory name after a `crates/` segment of the path, or `(root)` for a path with none. Within a unit a file is a document when it is a markdown file, ends in `.md.tmpl`, or sits under `docs/`, and source otherwise. Each partition reports its unit, its kind, its files and its added and deleted lines from `git diff --numstat`; a binary file counts as a file and adds no lines. The order is changed lines descending, then unit, then kind. It is a split to read and carries no size limit: how big a partition may be is the reviewer's to say.

`stand-ins` reads only the lines the range added, from the diff with no context, and only in files that are source: a document, a research note or a page of data is prose or records and is never a stand-in. The diff is asked for with its prefixes and external drivers fixed, so a user's `diff.noprefix` or `diff.external` changes nothing. A marker is one of a vocabulary the tool owns and says so. `FIXME`, `TODO`, `todo!(`, `unimplemented!(` and `#[ignore` count anywhere on an added line. `stand-in` and `relaxed` compared without regard to case count only inside a comment, the text after `//`, `/*`, `#` followed by a space, or `<!--`, so the memory ordering `Ordering::Relaxed` is not one. A line is reported once, under the first marker in that order it carries, with its file, its line number in the head and its text trimmed. Files a diff marks binary are not read.

## The branches

`branches` takes the repository alone. The trunk is the working branch where the repository has one, read from `origin` when it is there since a local copy may be stale, and the public branch otherwise, the same choice a release makes. A branch is listed when the trunk's tip does not contain it, from `origin` and the local heads, except the trunk, the release line, `badges` and `HEAD`; where a name is both, the remote's tip is read.

For each: the branch, its tip, the commits it holds that the trunk does not, the lines changed against the merge base, the files `git merge-tree --write-tree --name-only` reports in conflict (it touches no tree), and its call. The call is `land` when nothing conflicts, `merge-trunk` when something does, and `empty` when merging the branch into the trunk gives the trunk's own tree, which is decided by the trees and not by a line count, so a branch that changes only a binary file is not empty. A branch git cannot compare is a call of its own and the report carries on: `unrelated` when it shares no history with the trunk, and `unreadable` with git's words when the comparison fails otherwise, a conflict git cannot name included. Such a branch has no lines or conflicts to report and is listed all the same. The call is a reading of those numbers and not a verdict; nothing refuses a landing on it.

## What none of them do

None writes outside `mark`, none fetches, none gates, and none exits non-zero for what it found. One branch git cannot read is a finding about that branch and never ends a report. A refusal is an unknown repository, a sha that is no commit, a base that is not an ancestor, a mark that cannot be made. Output is lines for a person and the same report as JSON under `--output json`, in the shape every `release` verb has.

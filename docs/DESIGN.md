# homma

homma orchestrates a multi-repository workspace: it knows which repositories the
workspace contains, who works in it, where each participant's work happens, and
how they correspond.

It is deliberately small. Designing and building inside a repository belongs to
that repository's own tooling; homma's job is what spans repositories and what is
true of the workspace rather than of any one member.

## What it must be

**General.** homma runs against a workspace it has never seen. **No key is
required**: the content repository defaults to the configuration's own directory,
and every path has a default homma will create plus an override for a workspace
whose convention differs. So a fresh directory with a registry in it is already a
workspace. Nothing about the workspace homma was born in is compiled in, which is
why layout, roles and record kinds are data rather than code.

Membership follows from that. A directory under the workspace root that is its
own repository is a member, and nothing lists it. Which forge it lives on and
who owns it come from its `origin` remote, which is the thing that decides
where a push lands and is therefore the only honest source for either. A
workspace that renames a repository, clones a new one, or drops one is correct
the moment the tree is, with nothing left saying otherwise.

**Minimal, and delegating.** Where a member repository has its own tooling, homma
drives it rather than reimplementing it.

## The four primitives

Everything else is a view over these, a kind declared in configuration, or prose
in a generated file.

**The record store.** One engine for everything homma persists. Kinds declare
what attributes a record has and whether it may be edited, so correspondence and
structural work share a write path and differ by a flag.

**The daemon.** Sole writer of the store, sole waker of participants, sole arbiter
of who may act on whose behalf. Three verbs: append a record, deliver what is
waiting, grant a dispatch.

**The registry.** Identity as configuration rather than as a process, so a
participant outlives whatever was running it.

**The generation pass.** Configuration and templates into definitions, settings,
hooks and links; the sole writer of the agent configuration in every workspace it
manages, **the workspace's own rules and skills included**.

## The layers

```
L0 contracts     types and traits, no I/O
L1 mechanism     git, forge, filesystem. things with side effects
L2 store         records and their persistence
L3 domain        registry, correspondence, work
L4 service       the daemon and its surfaces
L5 surface       what a human or an agent drives
```

Crates arrive when something needs them. An empty crate holding a name is a
directory pretending to be a decision.

## What exists

`homma-api` carries the vocabulary. `homma-store` persists records.
`homma-org` holds the registry, the workspace lifecycle and generation.
`homma-engine` is the command surface, and `homma` is the launcher that finds
the workspace, reads the version of the engine it pins, and runs that one.
`homma-core` still holds forge clients and git operations in a pre-adoption
split that a later round dissolves.

## The rule corpus

A workspace's rules are injected into every session it runs, sub-agents
included, so their size is paid before any work starts. They are authored as
templates and generated, like everything else the generation pass owns.

**Three artifacts per rule, one of them generated.** A full template carrying the
meta as frontmatter and the reasoning as its body; a card template beside it; and
the always-loaded card, written by the pass and never by hand. **The meta lives
once, in the full template**, and both render against it, so a trigger typed once
appears in both.

**The meta is what makes a rule findable without its name.** Topics stated in the
words a reader arrives with, and the moment the rule fires. A session about to
write a README asks the subject and gets the governing set; asking by filename
only works for somebody who already knows the answer.

**Which skills bear on a rule is derived rather than declared**, from citations
in both directions, because a hand-kept list goes wrong the first time a skill is
renamed and nothing reports it.

## The command surface

```
homma org      who exists
homma work     workspaces and what is in them
homma rules    the corpus: what governs a subject, and generating the cards
homma sauna    correspondence and work
homma serve    the daemon and its surfaces
```

A call with a terminal attached should print for a human, and a call without one
should print its result and nothing else, because something is parsing it. That
split is decided and **not yet built**: nothing in the tree senses a terminal, and
`homma org` prints the same way either way.
